## 3部構成

読み手が3種類いるため、1つの文体では成立しない。

| 部 | 読み手 | 書き方 |
| --- | --- | --- |
| 概要 | 非エンジニア | 専門用語を使わない。各ラベル1〜2行 |
| 詳細 | エンジニア | 技術的に厳密に。分量の制限はしない |
| 確認点 | 確認する人 | チェックボックス。検証と期待を対で書く |

3部目の「確認点」が最も省略されやすい。省略されると読み手が全文から確認項目を組み立てることになる。**確認コストを書き手側に寄せる**のがこの構成の目的。

## 見出しを変えない

見出しの追加・削除・改名を禁止する。GitLabにはGitHub Issue Formsのような構造化機能が無いため、見出し文字列が機械読解の唯一のアンカーになる。

先頭の `**種別**:` トークンも必須。値は `feature` / `chore` / `bug` / `research` / `trivial` の5つで、これ以外を使わない。

`## 概要` の中だけは見出しではなく `**ラベル**: 値` の固定ラベルで構成する。見出しを増やすと小さいIssueで負担になるため。ラベル名もテンプレートごとに固定で、追加・改名しない。

## 固定語彙

空欄を残さない。空欄は「未検討」「不要」「未確定」のどれか判別できず、機械読解で誤った前提を作る。

| 語彙 | 意味 | 誰が解消するか |
| --- | --- | --- |
| `N/A` | 検討した上で該当なし | 解消不要 |
| `(実装後に記載)` | 起票時点では書けない | 起票者自身 |
| `要確認: <質問>` | 利用者に聞かないと決まらない | 利用者 |

切り分けの基準は**回答者が誰か**。自分で調べれば分かること・実装すれば決まることは `(実装後に記載)`。利用者の意向や外部の事情に依存するものだけが `要確認:`。

### `要確認:` の解消

`要確認:` が1つでも残っているIssueは、**実装に着手できない状態**として扱う。

1. **提示** — ブランチ作成の前に利用者へ提示する
2. **解消** — 利用者の回答を得る。**推測で埋めてはいけない**
3. **記録** — 該当行を次の形に書き換える

```markdown
要確認(解消済YYYY-MM-DD): <質問> → <回答>
```

行を削除せず残すのは、後から「なぜその判断になったか」を追えるようにするため。

## 着手前の現状

概要の `**現状**:` は**起票時にしか書けない**。実装が進むと元の状態は再現できない。

- UI変更 — 着手前の画面のスクリーンショットを貼る
- バグ — エラーメッセージの原文、不具合が見えている画面。要約しない
- 設定・環境 — 変更前の設定値、バージョン

**この節は実装後も書き換えない**。仕様やスコープが変わっても、現状の記述は起票時のまま残す。変わったのはこれから何をするかであって、着手前の事実ではない。

Issueが着手前 (Before) を持ち、MRが結果 (After) を持つ。この対応を崩さない。

## 受入基準の検証

受入基準には検証方法を必ず添える。2つの形式を認める。

```markdown
- [ ] (何が満たされれば完了か)
  - 検証: `<コマンド>`
  - 期待: (出力・状態)
```

```markdown
- [ ] (何が満たされれば完了か)
  - 検証: (目視確認) <確認する観点>
  - 期待: (どうなっていれば合格か)
```

目視確認を使ってよいのは、機械検証が原理的にできない場合に限る。

- ドキュメントの内容の妥当性 (存在の有無は `grep` で機械検証できる。中身が適切かは目視)
- 設計判断の妥当性
- UIの見た目 (レイアウト崩れ、配色、文言)
- 文体・トーン

`grep` で形だけ確認する検証は書かない。形骸化するだけで、目視確認と正直に書いた方が良い。

検証を書けない項目は受入基準に置かない。詳細側の実装計画へ移す。

書式だけを変えるIssueの期待は、「意味を変えない補足 (つなぎの語句など) は許容する」と書き添える。書かないと、文言が少し増えただけで期待を満たさなくなる。

## チェックボックス

チェックボックスは2種類あり、**更新条件が異なる**。

| 場所 | チェックを付けてよい条件 |
| --- | --- |
| 実装計画 (詳細節) | 対応するタスクのコミットが作成された時点 |
| 受入基準 (確認点節) | 対応する検証が成功した時点 |

受入基準を「実装が終わった感触」で付けない。実装計画の方は進捗の記録なのでコミット単位で付けてよい。

## スクリーンショット

画面に変更があるIssueでは、**着手前のスクリーンショットを貼る**。文章だけでは非エンジニアの読み手が何が変わるか判断できない。

撮影条件 (URL・操作手順・ビューポート) を `### 検証方針` に書く。同じ条件で撮らないとBefore/Afterの比較にならない。

撮影はPlaywrightで自動化する。手作業の撮影に頼らない。撮影と貼付の手順は `codex-ext:gitlab-screenshot` が持つ ([gitlab-screenshot](../../gitlab-screenshot/SKILL.md))。

## Mermaid図

GitLabのIssue・MR・noteはmermaidフェンスで図を描画する。**図にすると分かりやすくなる場合は入れる**。非エンジニアの読み手には特に効く。

入れる価値がある場面:

- 処理の流れ、状態遷移がある
- 複数のコンポーネントの関係を説明する
- 構造が変わる (Before/Afterを2つ並べて対比する)
- 判断の分岐が多い

入れない場面:

- 単純な変更。図にしても文章以上の情報が増えない
- 図の方が読みづらい (ノードが多すぎる、関係が複雑すぎる)

必須ではない。**図にしても情報が増えないなら書かない**。

## 起票後の扱い

`docs/issue/issue-<IID>.md` が**以降の作業中の正本**になる。`docs/issue/` はリモートへpushしない (`.git/info/exclude` で除外する)。**`<IID>`はSKILL.mdの起票応答、または着手skill (`codex-ext:gitlab-develop`) で数字だけであることを確認済みの値を使う**。ここでは確認し直さない。

| 段階 | 何をするか |
| --- | --- |
| 作業中 | ローカルMarkdownを更新する。APIは叩かない |
| 切りが良いとき | ローカルMarkdownの全文をGitLabへpushする |
| 後片付け時 | ローカルMarkdownを削除する |

pushはローカルファイルの全文をそのまま渡す。ローカルが正本なので、GitLab側から取り直す必要はない。

```bash
glab api projects/:id/issues/<IID> -X PUT --field "description=@docs/issue/issue-<IID>.md"
```

**ローカルとGitLabが食い違ったら、ローカルを正とする**。GitLab側をUIから直接編集した場合は、その内容をローカルへ取り込んでから続ける。

更新とpushのタイミングは着手skillの担当。このskillは起票までを行う。

## ラベル・マイルストーン・期限

Issueの進捗と期日をトラッカー側で持つ。プロジェクトがこの運用を採っている場合、起票時に設定する。運用の有無は `glab label list` と `glab api "projects/:id/milestones"` で確認する。プロジェクトに既存のラベル体系があれば、それに合わせる。以下は、体系が無く利用者が運用を望んだときの例である。

### ステータスラベル

作業Issueには、進捗を表す次の5つのうち1つを付ける。

| ラベル | 意味 |
| --- | --- |
| `ToDo` | 未着手 |
| `Doing` | 進行中 (着手してブランチ・MRがある) |
| `OnHold` | 保留 (顧客回答・データなど外部依存の待ち) |
| `Review` | レビュー中 (MRを出しマージ待ち) |
| `Done` | 完了 (closeと対で付ける) |

遷移は開発サイクルに合わせる。起票時に `ToDo`、着手で `Doing`、MR提出で `Review`、マージ・close時に `Done`。外部依存で止まったら `OnHold`。

フェーズ全体を束ねる親Issue (roadmap的なIssue) にはステータスラベルを付けない。子の作業Issueだけが持つ。親には束ねるラベル (`roadmap` など) とマイルストーン・期限を付ける。

### マイルストーン

プロジェクトの運用に合わせて切る (例: 月末単位で `9月末` = その月の末日が締切)。起票時に、その作業を完了させる期間のマイルストーンへ紐付ける。マイルストーンidは次で引く。

```bash
glab api "projects/:id/milestones"
```

### 開始日

テンプレートの概要にある `**開始日**: YYYY-MM-DD` の行を、起票時に着手予定日で埋める。GitLab Freeには開始日のフィールドが無いため、description内の行として残す。外部のガントチャートなどがこの行を読む運用でも通るよう、書式はハイフン区切り・ゼロ埋めに限る (`2026-01-15`)。`2026/01/15` のような書き方はしない。着手予定日が決まっていなければ起票日を入れる。終了日はこの行に書かず、次節の期限 (due date) に入れる。

### 期限 (due date)

マイルストーン内で、依存関係とフェーズ順から逆算して個別のdue dateを置く。先行Issueより後ろへ、後続Issueより前へ収める。直列に依存するIssueが同日にならないようにする。`OnHold` は外部依存が解けないと動かせないため、期限はマイルストーン末日を暫定で置く。

### 設定

`glab issue update` はdue date未対応のため `glab api` を使う。ラベルとマイルストーンもまとめて設定できる。ラベルを `glab api` の `labels` で渡すと完全置換になるため、既存のラベルを取得してから混ぜるか、`add_labels` を使う。
