# feature / choreテンプレート

`chore` も同じ構成を使う。種別トークンと「スコープ」の記述で区別する。

以下をコピーして埋める。見出しを変えない。

```markdown
**種別**: feature

## 概要

**現状**: (着手前に何がどうなっているか。今は何ができないか、今どう回避しているか。UI変更ならスクリーンショットを貼る)

**何が変わるか**: (利用者から見て何ができるようになるか。利用者への影響が無い変更なら「開発者から見た変化」に読み替えて書く。例: 内部構造を整理し、以後の変更が安全になる)

**なぜ必要か**: (現状のどこが問題か。1〜2行)

**影響範囲**: (誰に、どこに影響するか。1行)

## 詳細

### 背景

技術的な文脈、既存実装との関係、この対応に至った経緯。

### スコープ

対象:

- ...

対象外:

- ...

### 仕様

振る舞い、入出力、制約。表や箇条書きで具体化する。

### 実装計画

- [ ] 1タスク = 1コミット粒度、依存順に並べる

### 技術判断・代替案

採用した方針と、採らなかった選択肢の理由。

### 検証方針

ユーザーが明示した場合にどうテストするか。単体テストの範囲、check.shの実行内容、手動確認が要る部分。明示がなければ未実行理由を残す。
確認点の「確認手順」とは役割が違う。ここは書き手が採るテスト戦略、あちらは確認者が実行する手順。

UI変更がある場合、スクリーンショットの撮影条件 (URL・操作手順・ビューポート) もここに書く。UI変更が無いなら「UI変更なし」と明記する。

### リスク・未確定事項

ブロッカー候補、前提が崩れる条件。

## 確認点

### 受入基準

- [ ] (何が満たされれば完了か)
  - 検証: `<コマンド>`
  - 期待: (出力・状態)

### 確認手順

確認する人が上から順に実行すれば済む形で書く。

## 実装後追記

実装中に随時追記する。

### 試したこと

| 試したこと     | 結果 | 採否 |
| -------------- | ---- | ---- |
| (実装後に記載) |      |      |

### 起票時の想定との差

想定通りなら「想定通り」。違ったら何がどう違ったか。

### 調査で分かったこと

次に効く事実。無ければN/A。
```
