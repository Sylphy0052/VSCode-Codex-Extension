# リポジトリの規約ファイル (`CLAUDE.md`・`AGENTS.md`)

[setup.md](setup.md)から参照される。リポジトリに規約が書かれていないときに、最小のものを提案するための雛形。

## 何のために書くか

`codex-ext:gitlab-*`のskillは、ブランチが`<type>/<IID>/<slug>`で切られていること、作業ドラフト (`docs/issue/`・`docs/mr/`) がpushされないことなど、規約が守られている前提で動く。規約がどこにも書かれていないと、skillが既定値で動くだけで、リポジトリ固有の事情 (確認コマンド、触らない場所) が伝わらない。

## 作る前に

- 既にある場合は上書きしない。不足している項目だけを提示し、追記するかを利用者が決める
- `CONTRIBUTING.md`に開発の進め方が書かれているなら、それを読んで足りない分だけを提案する
- どのファイルを作るかは利用者の使うエージェントで決める。Claude Codeは`CLAUDE.md`、Codexは`AGENTS.md`を読む。両方使うなら`AGENTS.md`に本体を書き、`CLAUDE.md`には`@AGENTS.md`の1行だけを置く (Claude Codeが`AGENTS.md`を読み込む)
- 書くのはリポジトリ固有のことだけ。一般的なコーディング規約、gitの使い方、個人の好みは書かない。長くしない。読まれなければ意味が無い
- 推測で埋めない。スタックや確認コマンドは、`package.json`・`Makefile`・`pyproject.toml`・CI設定などを読んで確かめた値だけを書く。分からない項目は利用者に聞くか、空欄のまま提案する

## 雛形

```markdown
# <リポジトリ名> 開発規約

<1行で何のリポジトリか>

## スタック

<言語、フレームワーク、パッケージマネージャ。無ければ「ドキュメントのみ」>

## 変更時の確認

- 型チェック: `<コマンド>`
- テスト: `<コマンド>`
- lint: `<コマンド>`

## 触らない場所

<生成物、外部から同期されるもの、別の人が作業中のもの。理由も書く>

## GitLab運用

- 1 Issue 1 Branch。ブランチ名は`<type>/<IID>/<slug>`
- MR本文に`Closes #<IID>`を書く
- コミットはConventional Commitsの短形 (`<type>: <説明>`)
- マージ方式: <merge / squash / rebaseのどれか。プロジェクト設定に合わせる>
- マージ後にソースブランチを削除する: <する / しない>
- Issue・MR・コメントの言語: <日本語 / 英語など>
- `docs/issue/`・`docs/mr/`はローカルの作業ドラフト。リモートへpushしない
- 自己マージ: <してよい条件。無ければ「利用者がその場で明示許可した場合のみ」>
```

## 書くときの注意

### 「触らない場所」を埋める

省略されやすいが、事故が起きるのはここ。

- 生成物: 手で直しても次の生成で消える
- 外部から同期されるもの: 同期元を直さないと戻る
- 別のセッションや別の人が作業中のファイル

理由を書く。「触らない」だけでは、なぜ触ってはいけないかが分からず、必要になったときに判断できない。

### 自己マージの扱いを明示する

GitLab CEには承認機能が無く、自己マージを設定で止められない。自己マージしてよい条件を規約ファイルへ書いておく。書かなければ、利用者がその場で明示許可した場合だけ例外にする。

### 確認コマンドが無い場合

テストもlintも無いリポジトリでは、代わりに何で確かめるかを書く。「確認不要」で終わらせない。ドキュメントだけのリポジトリなら、文体の機械チェックやリンク切れの確認がそれにあたる。
