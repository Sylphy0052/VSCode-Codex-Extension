# MR本文とnoteのテンプレート

implement.md / [self-review.md](../../gitlab-review/references/self-review.md) から参照される。

## 共通規約

- **見出しを変えない**。追加・削除・改名を禁止する。GitLabには構造化フォーム機能が無く、見出し文字列が機械読解の唯一のアンカーになる
- **空欄を残さない**。固定語彙は `N/A` (検討した上で該当なし) / `(マージ後に記載)` (今は書けない) / `要確認: <質問>` (利用者に聞かないと決まらない) の3つ
- **`Closes #<IID>` を必ず入れる**
- **図にすると分かりやすいならMermaidを入れる**。処理の流れ、状態遷移、Before/Afterの構造比較。図にしても情報が増えないなら書かない
- **3部構成** (概要は非エンジニア向け / 詳細はエンジニア向け / 確認点はレビューする人向け)
- 本文の言語は、リポジトリ規約に従う。定めが無ければ利用者との会話の言語で書く。見出しの文言を訳す場合も、構成と固定語彙の意味は変えない

**IssueがBefore、MRがAfter**。過程はIssue、結果はMR。試して不採用にした案はIssueの `### 試したこと` に書き、MRには書かない。レビューする人が見たいのは最終形だから。

UI変更がある場合、**Issueに貼った着手前のスクリーンショットと、変更後のスクリーンショットを並べて貼る**。撮影条件はIssueの `### 検証方針` に書いてあるものを使う。同じ条件で撮らないと比較にならない。

撮影と貼付は `codex-ext:gitlab-screenshot` ([SKILL.md](../../gitlab-screenshot/SKILL.md)) が担う。撮影条件の形式、実行経路の判定、uploads APIでの貼付はすべて向こうにある。

## MR本文

```markdown
## 概要

**何が変わったか**: (実際に何ができるようになったか。利用者への影響が無い変更なら開発者から見た変化)

**Issueの予定との差**: (予定通りなら「予定通り」。違ったら何がどう違ったか)

**影響範囲**: (誰に、どこに影響するか)

## 詳細

### 変更点

ファイル・モジュール単位で何をどう変えたか。差分を読まなくても構造が分かる粒度で書く。

### 技術判断

実装中に決めたこと。Issueの起票時点では決まっていなかったもの。

### 既知の制約

このMRで対応しなかったこと、残った課題。無ければ `N/A`。

## 確認点

### 受入基準の充足

- [ ] (Issueの受入基準をそのまま転記)
  - 結果: (検証コマンドの実行結果、または目視確認の結果)

### 確認手順

レビューする人が上から順に実行すれば済む形。環境構築が要るなら、その手順から書く。

### 特に見てほしい点

判断に迷った箇所、影響が広い変更、レビュアーの専門が要る箇所。無ければ `N/A`。

## レビュー記録

(self-reviewの巡ごとに1行追加する。詳細はnoteを参照)

Closes #<IID>
```

## 自己レビュー結果のnote

各巡で投稿する。**指摘が無かった巡も投稿する**。

```markdown
## self-review <N>巡目

**見方**: 4 agent並列 (`review-spec` / `review-robust` / `review-style` / `security-auditor`)

**結果**: (指摘N件 / 指摘なし)

### 観点別

- 受入基準の充足: (指摘N件 / 該当なし)
- 先祖返りと巻き込み: (指摘N件 / 該当なし)
- セキュリティ: (指摘N件 / 該当なし)
- 異常系とエラー処理: (指摘N件 / 該当なし)
- テストの充足: (指摘N件 / 該当なし)
- 可読性と規約: (指摘N件 / 該当なし)

### 指摘と対応

| severity | 証拠 | 箇所 | 指摘 | 対応 |
| --- | --- | --- | --- | --- |
| critical | コード確認 | `path:line` | ... | 修正済み (`<hash>`) |
| high | コード確認 | `path:line` | ... | 修正済み (`<hash>`) |

### 次巡で見る点

(直した差分に対してもう1巡回すか、レビュー依頼へ進むか)

### 見送り一覧 (累積)

(この巡までに見送りと決めた指摘の累積。無ければ `N/A`)

- `path/to/file.ext` / `<見出しまたは関数名>` — <要約1行> — 見送り (low、別Issue予定)
- `path/to/file.ext` / `<見出しまたは関数名>` — <要約1行> — 見送り (low、#<IID>へ切り出し済み)
```

行の要素は次の4つ。

- **ファイル**: リポジトリ相対パス
- **見出し**: Markdownなら見出し文字列、コードなら関数名など、行番号より動きにくいアンカー (行番号は修正のたびにずれるため使わない)
- **要約**: 1行
- **状態**: `見送り (low、別Issue予定)` / `見送り (low、#<IID>へ切り出し済み)` / `解消 (<hash>)` のいずれか

**見送り一覧はMR本文には置かない**。MR本文の `## レビュー記録` には巡ごとの1行だけを書く (下記「投稿後」の節を参照)。

2巡目以降のagentへは、この節をそのまま「次の項目は見送りと決めたので再指摘は不要」として渡す。見送った `low` を別Issueへ切り出すときも、この節から書き写す。

**6観点すべてを書く**。4つの担当が返した「該当なし」も残す。書かないと、見ていないのか該当が無かったのかが後から分からない。

agentが使えず本体が逐次で見た場合 (Codexなど) は、`**見方**:` にその旨と見た観点名を書く。

### 投稿後

投稿後、MR本文の `## レビュー記録` へ1行追加する。

```markdown
- self-review 1巡目 (4並列): 指摘7件 (critical 0 / high 1 / medium 4 / low 2)、medium以上は対応済み
```

## 投稿前の自己チェック

- [ ] `Closes #<IID>` がMR本文にある
- [ ] 概要の「Issueの予定との差」が埋まっている
- [ ] Issueの受入基準がすべて転記され、`結果:` が書かれている
- [ ] UI変更があるなら、着手前と変更後のスクリーンショットが並んでいる
- [ ] 空欄が無い
- [ ] `## レビュー記録` の巡数と、投稿したnoteの数が一致している
- [ ] 見送りがある巡は、noteの「見送り一覧 (累積)」に4要素 (ファイル・見出し・要約・状態) で記載している
