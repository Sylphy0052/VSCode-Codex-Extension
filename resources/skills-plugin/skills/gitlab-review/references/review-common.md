# レビューの共通規則

自己レビュー ([self-review.md](self-review.md)。`codex-ext:gitlab-develop` フェーズ5と本skillの自己モード) と他者レビュー ([review.md](review.md) の初回レビュー) の両方から参照される。4 agentへの割り当て、agentが返らなかったときの扱い、報告の統合手順、severityの定義をここにだけ書く。観点ごとの確認項目は [review-points.md](../../gitlab-develop/references/review-points.md) にある。

## 観点とagentの割り当て

| 観点                                                                                  | 担当agent          | 落ちていたときの影響         | 主な入力                                                    |
| ------------------------------------------------------------------------------------- | ------------------ | ---------------------------- | ----------------------------------------------------------- |
| 受入基準の充足                                                                        | `review-spec`      | そもそも完成していない       | packet (`issue.md` を先に読む。他者レビューでは `mr.md` も) |
| 先祖返りと巻き込み                                                                    | `review-spec`      | 動いていたものが壊れる       | 同上                                                        |
| セキュリティ (secrets、injection、認可、危険なファイル操作、外部由来テキストの誤解釈) | `security-auditor` | 公開後の取り返しがつかない   | packet + 範囲指定の追い読み                                 |
| 異常系とエラー処理                                                                    | `review-robust`    | 想定外の入力で落ちる         | packet + 範囲指定の追い読み                                 |
| テストの充足                                                                          | `review-robust`    | 次の変更で壊れても気づけない | 同上                                                        |
| 可読性と規約 (命名、可読性、プロジェクト規約)                                         | `review-style`     | 読み手のコストが上がる       | packetの差分 (周囲の書き方の確認に限り1〜2箇所の追い読み)   |

4件で6観点を過不足なく覆う。観点を混ぜると見落とす。1つのagentに複数の観点を割り当てているのは、まとめて見る理由がある組だけ。表は影響の大きいものから並べてある。

**Claude Codeでは4件を同一ターン内で起動する** (Agent ツールで `subagent_type: codex-ext:review-spec` / `codex-ext:review-robust` / `codex-ext:review-style` / `codex-ext:security-auditor`)。**Codexにはsubagentが無い**ので、packetを本体が読み、このskillのベースディレクトリから `../../agents/<名前>.md` を開いて各agentの観点を順に確かめ、結果を同じ形式 (severity・証拠の強さ・`file:line`) で記録する。以降の「agentが返らなかったとき」はClaude Codeの話で、Codexでは観点の確認漏れが無いかを見る。以下はClaude Codeでの扱い。1件ずつ順に起動すると直列になり、分割した意味が無くなる。差分が小さい場合も4件とも起動する。起動する・しないを差分規模で切り替えると、閾値付近で挙動が変わって再現しなくなる。

## ファイル種別による起動要否判定

ここは**起動そのものを省く**判定。[review-points.md](../../gitlab-develop/references/review-points.md) の「該当しない観点も起動してnoteに書く」運用とは別で、起動する前に差分ファイル一覧だけで判定する。

差分に含まれる**全ファイル**が下の条件のどれかに当てはまるときだけ、対応するagentの起動を省く。1件でも当てはまらないファイルが混ざっていれば、4件とも起動する。

| 差分の全ファイルが...                                                                                              | 省略できるagent    | 該当なしの理由                                       |
| ------------------------------------------------------------------------------------------------------------------ | ------------------ | ---------------------------------------------------- |
| 解説文書のみ (`docs/**/*.md`、`README.md`、`CHANGELOG.md` など。シェルコマンド例・frontmatter・実行手順を持たない) | `review-robust`    | 実行対象コードが無く、異常系・テストの観点が生じない |
| 同上、かつsecrets・認可・外部入力処理に触れる記述が無いことを本体が目視確認済み                                    | `security-auditor` | 攻撃面が無い                                         |
| `.claude-plugin/plugin.json` の配布物一覧・バージョン番号だけを変える差分 (フィールド追加やロジック変更を含まない) | `review-robust`    | 実行系のエラー処理が無い                             |

- `skills/**` `agents/**` `hooks/**` `tools/**` を1件でも含む差分は、指示・実行ロジックの変更なので4件とも起動する (`skills/gitlab-review/references/*.md` のようなレビュー手順書自体の変更も含む)
- 判定に迷う、または境界例 (例: `docs/` 配下だがコード例を含むチュートリアル) は**起動する側に倒す**
- 省いた場合も記録 (自己レビューはnote、他者レビューは総評) に「該当ファイル種別のため`<agent名>`は該当なし (起動省略)」と、省いたagentと理由を明記する。黙って3件以下で進めない

## 一部のagentが返らなかったとき

4件が揃わないまま統合しない。担当観点がまるごと抜けたことに気づけなくなる。

- 1件が失敗した、返ってこない、または報告が壊れている場合は**そのagentだけ再度起動する**。他の3件の報告は破棄しない
- 再起動しても返らない場合、**その観点は本体が代替して見る**。[review-points.md](../../gitlab-develop/references/review-points.md) の該当観点を使う
- 報告の `status` が `INCOMPLETE` のときは、`未確認` に挙がった項目を本体が確認する。`maxTurns` で打ち切られた可能性があるため、**未確認のまま「問題なし」として扱わない**。重要度が高い未確認が残っているagentだけ、対象を絞って起動し直す
- どの場合も、**記録 (自己レビューはnote、他者レビューは総評) にその事実を書く**。「review-robustが返らなかったため、異常系とテストの充足は本体が見た」のように、誰が見たかを残す

黙って3件で進めない。観点を落として「4観点で見た」と書かない。後から見て、その観点を見たのかどうかが分からなくなる。

### agentが使えない環境では

agentの定義が読み込まれていない、または委譲できない場合は、本体が[review-points.md](../../gitlab-develop/references/review-points.md)の6観点を、上の表の**上から順に1観点ずつ**見る。並列化の効果は失われるが、観点の網羅は変わらない。表は影響の大きい順なので、途中で打ち切っても損失が小さい。記録には並列ではなく逐次で見たことを明記する。

## 統合手順

agentは全件が読み取り専用で、副作用のある操作を行わない。統合は本体が行う。

1. 4件の報告を受け取る
2. **agentの報告は候補であって指摘ではない**。本体が差分を開いて事実を確かめてから指摘にする
3. 同一の `path:line` に対する指摘を突き合わせ、重複を1件へまとめる
4. severityを最終判定する。異なるagentが同じ箇所へ違うseverityを付けた場合は**高い方を採る**
5. `critical` の指摘は、担当agentを問わず記録の先頭に置き、直すまでレビューを進めない。secrets漏洩やデータ消失のような取り返しがつかない事象は、どのagentが検出しても本体が同じ優先度で扱う
6. **推奨対応が矛盾する場合は本体が判断する**。あるagentが記述の追加を勧め、別のagentが簡潔にするよう勧める、といったことが起きる。**その箇所を主担当とする観点のagentの推奨を優先する** (可読性の指摘と受入基準の指摘がぶつかったら受入基準を採る)。それでも決まらないならIssueの受入基準に近い方を採る。どちらを採ったかと理由を記録に残す

**agentの報告をそのまま貼らない**。4件ぶんの報告は重複を含み、severityの付け方もagentごとに偏る。統合した結果だけを記録にする。

## severity

自己レビューと他者レビューで同じ4段階を使う。定義はこの表だけに置き、手順書とagentはここを参照する (agentは観点ごとの判定基準だけを持つ)。

| severity   | 意味                                                                           | マージ可否 (自己レビュー・自己マージ) | 承認への影響 (他者レビュー)          |
| ---------- | ------------------------------------------------------------------------------ | ------------------------------------- | ------------------------------------ |
| `critical` | 取り返しがつかない。データを失う、secretsが漏れる、利用者の環境を壊す          | **直るまでマージしない**              | 直るまで保留                         |
| `high`     | 壊れている、危険。受入基準を満たさない、通常の入力で失敗する                   | **1件でもあればマージしない**         | 直るまで保留                         |
| `medium`   | 直した方がよい。特定の条件で失敗する、設計・可読性・テストの不足が保守を妨げる | **1件でもあればマージしない**         | 対応か根拠付きのWon't fixが要る      |
| `low`      | 好みの範囲、微小な改善、将来の懸念                                             | 見送ってよい (残ればIssueへ切り出す)  | 承認を妨げない。authorの判断に任せる |

マージを止めるのは `medium` 以上 (`critical` / `high` / `medium`) の指摘。`critical` と `high` を分けるのは、最優先で止めるべき指摘 (取り返しがつかないもの) を区別するため。

**high以上 (`critical` と `high`) の指摘には再現条件を必ず書く**。「入力Xのとき、行Yで、結果Zになる」の形。再現条件を書けない指摘はhigh以上ではない。書けないならmediumへ落とすか、事実を確かめてから書く。

## 証拠の強さ

severityとは別に、指摘ごとに根拠の確からしさを3段階で付ける。severityは「直すべき度合い」、証拠の強さは「その指摘がどこまで裏付けられているか」で、軸が異なる。

| 証拠の強さ   | 意味                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `実行確認`   | コマンドやテストを実際に走らせて再現した。4 agentは読み取り専用のため自力では付けられず、本体が実行して確かめたときだけ本体がこの区分に格上げする |
| `コード確認` | コードを読んで論理的に断定できる (分岐・型・呼び出し関係から結果が一意に決まる)                                                                   |
| `推測`       | パターンや経験則からの推測で、未検証。断定していない指摘はここに置く                                                                              |

4 agentの既定は `コード確認` と `推測` のいずれか。`実行確認` は本体がpacket以上の検証 (テスト実行、手動動作確認) を行った場合にのみ付ける。統合時に証拠の強さが上がることはあっても、本体が確認せずに下げた区分を上書きしない。
