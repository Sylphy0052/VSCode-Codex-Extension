# 視認性の観点

[SKILL.md](../SKILL.md) から参照される。**UIを変更するMRでは視認性を1項目として必ず確認する**。動作が正しくても、読めない・押せない・気づけない画面はレビューを通さない。`review-style` の担当観点だが、判断がつかない項目は本体が見る。

対象は画面に出るものすべて。Webの画面、CLIの出力、ログのフォーマット、エラーメッセージも含む。

## 見る点

| 見る点 | 落ちているとどうなるか |
| --- | --- |
| 文字と背景のコントラスト | 明るい環境や低品質のディスプレイで読めない。本文は4.5:1、大きい文字とUI部品の境界は3:1を下限とする |
| 色だけで区別していないか | 色覚特性や白黒印刷で情報が消える。色に加えて形・文字・アイコンでも区別する |
| 文字サイズと行間 | 小さすぎる文字、詰まった行間は読み飛ばしを生む |
| 要素の重なりとはみ出し | 長い文字列、想定より多い件数、日本語の折り返しで崩れる |
| 狭い画面と拡大表示 | 幅の狭い画面やブラウザ拡大で押せない・読めない箇所が出る |
| 情報の優先順位 | 重要な数値やエラーが、装飾や余白に埋もれて気づかれない |
| 状態の可視性 | 読み込み中、エラー、空データが画面に出ているか。無言で何も起きないのが最悪 |
| フォーカスと操作対象の大きさ | キーボード操作でどこにいるか分かるか。押す領域が小さすぎないか |

## スクリーンショットが無いとき

**スクリーンショットが添付されていないUI変更のMRは、視認性を確認できない**。次のどちらかにする。

- MRへスクリーンショットの添付を求める指摘 (medium、コード修正なし) を出す
- 自分でチェックアウトして撮る ([gitlab-screenshot](../../gitlab-screenshot/SKILL.md))。チェックアウトは他人のコードを自分の環境へ持ってくる操作なので、ビルドやスクリプト実行を伴う場合は何が動くかを読んでから動かす

## 総評への書き方

**見ずに済ませたなら、そのことを総評noteへ書く**。「視認性: スクリーンショットが無いため未確認」と書けば、確認していないことが後から分かる。UI変更が無いMRでは「該当なし」と書く。
