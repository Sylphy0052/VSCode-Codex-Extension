# Agent Sessions (VSCode Extension)

CLIコーディングエージェント（Codex / Claude Code）のセッションを、VSCodeのファイルタブと同じ感覚でエディタタブとして扱う拡張機能。

- 1ボタンで新規セッションをエディタタブとして開く
- 過去セッションをサイドバーの履歴から選んで再開する（CodexとClaude Codeを1つの一覧で扱う）
- VSCode再起動後もタブが会話ごと戻る
- 会話の途中から分岐して、別のタブで続きをやり直す（Codex）
- 本流を汚さずに脇道の質問だけ聞く。跡を残さない使い捨てのタブで応答が返る（Codex、`/btw`）
- 同じ指示を条件が満たされるまで繰り返す
- 応答を止めずに、途中で指示を足す（Codex）
- スクリーンショットを貼り付けて、見せながら指示する
- エディタで選択した範囲を、右クリックから直近アクティブだったタブの入力欄へ挿入する（送信はしない）
- コンテキストの残りを見ながら、その場で会話を圧縮する
- 現在のセッションの推定コストを確認する（Claude Code）
- 現在のセッションの累計トークン数を確認する（Codex。金額を出す経路が無いための代替表示）
- 手を出させずに計画だけ立てさせる（Plan mode）
- コードレビューを起動する（Codexは対象を選んで実行、Claude Codeは `/code-review` を送るだけ）
- 進行中のタスクをTODO一覧で確認する（Claude Code）
- ツールやMCPサーバからの問い合わせに、その場で答える（Codex）
- hooksの一覧と信頼状態を確認する（Codexは信頼操作も可能）
- skillsの一覧とどこ由来かを確認する（Codexは有効無効の切替も可能）
- pluginの一覧・提供するものを確認し、インストール/アンインストールする（Claude Codeは有効無効の切替も可能）。Codexはappの一覧も確認できる
- Claude Codeの設定・skills・plugins・最近のセッションなどをCodexへ取り込む（Codex、`/import`相当）
- バックグラウンドで走っているプロセスを確認する（Claude Codeは個別に停止できる）
- サブエージェントの活動を会話の中で確認する（Codex。切替はできない）
- 実行したセッションを日報・週報システムへ流す
- 複数のタスクを依存関係つきのYAMLで定義し、並列のセッションで走らせる（[ワークフロー](#ワークフロー並列オーケストレーション)）

**状態: 動作するが実機での検証は途上。** 詳細は[開発状況](#開発状況)を参照。

## 必要環境

- VSCode 1.90以降
- Node.js 20以降
- [Codex CLI](https://developers.openai.com/codex/) または [Claude Code](https://code.claude.com/docs/en/quickstart) がPATH上にあること（両方でも片方でもよい）

WSL RemoteやDev Containerなどリモート環境で開発している場合、CLIもその環境側に必要になる。この拡張機能は `extensionKind: ["workspace"]` として動作するため、UI側（Windows等）のCLIは参照しない。

## インストール

Marketplaceには未公開のため、vsixを作ってインストールする。

```bash
git clone https://github.com/Sylphy0052/VSCode-Codex-Extension.git
cd VSCode-Codex-Extension
npm install
npm run package                                    # vscode-codex-extension-<version>.vsix を生成
code --install-extension vscode-codex-extension-0.0.1.vsix
```

VSCodeのUIからインストールする場合は、拡張機能ビューの右上「...」→「Install from VSIX...」で同じvsixを選ぶ。インストール後にウィンドウをリロードすると、アクティビティバーに Agents のアイコンが増える。

## クイックスタート

1. アクティビティバーの Agents アイコンを開く
2. 履歴ビューのタイトルバーのアイコンでセッションを始める（`+`: Codex / スパークル: Claude Code）
3. 会話するとサイドバーの履歴に積まれる。次からは履歴をクリックすれば再開できる
4. ウィンドウをリロードしても、開いていたタブは会話ごと戻る

セッションがまだ無いワークスペースでは、履歴ビューに新規セッションへの導線が表示される。

### スラッシュコマンド

入力欄で `/` を打つと候補が出る。**CodexとClaude Codeで中身が違う**。

|             | 候補に出るもの                                                   | CLIの組込コマンド              |
| ----------- | ---------------------------------------------------------------- | ------------------------------ |
| Codex       | カスタムプロンプト・スキル・この画面の機能（`/compact` `/init`） | 出ない（送っても効かないため） |
| Claude Code | CLIが返す全コマンド（組込・ユーザー定義・プラグイン由来）        | 出る。そのまま効く             |

**Codexの組込コマンド（`/status` `/review` `/diff` など）はチャット画面では使えない。** CLIのTUI層の機能であり、送ってもただの文章としてモデルへ渡るため候補に出していない。同じことは画面の操作でできる。

| TUIのコマンド                                           | この拡張機能での場所                                              |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| `/compact`                                              | 入力欄の「圧縮」ボタン、または候補の `/compact`                   |
| `/init`                                                 | 候補の `/init`（AGENTS.mdを生成。既存があれば確認してから上書き） |
| `/status` `/usage`                                      | 入力欄の下（コンテキスト残量とレート制限の消費率）                |
| `/model` `/effort`                                      | 画面下の設定行                                                    |
| `/skills`                                               | 候補そのもの                                                      |
| `/new` `/resume` `/fork` `/rename` `/archive` `/delete` | 履歴ツリーとコマンドパレット                                      |
| `/btw`                                                  | 候補の `/btw <質問>`（跡を残さない使い捨てのタブで応答）          |

Claude Codeは組込コマンドがそのまま効くため、候補もCLIから受け取ったものをそのまま出す。セッション中にスキルが増減しても追従する。

判定の根拠と全一覧は [docs/slash-commands.md](docs/slash-commands.md) にある。

### ファイルを指し示す

入力欄で `@` を打つとワークスペースのファイル候補が出る。操作はスラッシュコマンドと同じで、打ち進めて絞り込み、`↑` `↓` で選び、Tab か Enter で確定する。`Esc` で閉じる。

**確定すると `@` は消え、ワークスペース相対パスだけが入る**（`src/view/chatView.ts` の形）。`@` は候補を出す引き金で、CLIへはただのパス文字列として渡る。

- 候補から外れるもの: `node_modules` `dist` `.git` などの決め打ちの一覧と、ワークスペース直下の `.gitignore` に載っているもの
- `.gitignore` の解釈は簡易版。否定（`!`）や階層ごとの `.gitignore` は見ないため、除外し切れずに候補へ出るものがある
- 候補はエージェントが作ったファイルもすぐ拾えるよう、`@` を打つたびに集め直す（数秒は結果を使い回す）
- 直前が行頭か空白のときだけ候補を出す。メールアドレスを書いている途中では出ない

### シェルコマンド・メモリ追記（Claude Codeのみ）

入力欄の行頭が `!` ならシェルコマンド、`#` ならメモリ（CLAUDE.md）への追記として扱う（Claude Code TUIのbashモード・メモリモード相当。issue #5, #6）。行頭でない `!` / `#` や、複数行にまたがる発言は対象にしない。送信前に入力欄の下へ何が起きるか案内が出る。

**Claude CLIにこれに相当する制御要求（control_request）は無い。** `!ls` 相当の実行系14候補、`#` 相当の追記系12候補（`bash` `shell_command` `memory_save` `append_claude_md` など）を実測し、すべて `Unsupported control request subtype` で拒否されることを確認した（詳細は[docs/design.md](docs/design.md) §14.29）。そのため両方とも拡張機能側の機能として実装している。

- `!` シェルコマンド: 確認ダイアログの後、統合ターミナルへコマンドを入力する。**自動実行はしない**。CLIの承認設定（`claude.permissionMode`）が及ばない経路のため、実行するかはターミナル側でユーザーが自分でEnterを押して決める（`openLoginTerminal` と同じ流儀）。入力したことは会話にも1行残る
- `#` メモリ追記: 追記先（プロジェクトの `CLAUDE.md` / `.claude/CLAUDE.md`、またはユーザーの `~/.claude/CLAUDE.md`）を選び、内容と追記先を確認してから追記する。追記後、どこに書いたかが会話に残る

### 計画だけ立てさせる（Plan mode）

調べさせて計画を出させるところまでで止めたい場面のための機能。入力欄の横の「計画」ボタンで入り、もう一度押すと出る。入っている間はボタンの見た目と入力欄の下の表示で分かるようにしてあり、切り替えは会話にも残る。

**作り方がCLIごとに違う。**

|             | 仕組み                                                              | 抜けたとき                              |
| ----------- | ------------------------------------------------------------------- | --------------------------------------- |
| Codex       | 送信時の権限を読み取り専用にする（サンドボックス + 承認を求めない） | 入る前の権限へ戻す                      |
| Claude Code | CLIの承認方法を `plan` に切り替える                                 | 設定の承認方法へ（空なら `manual`）戻す |

Codexのapp-serverにはPlan modeそのものが無いため、**権限で作っている**。ファイルを書こうとすると権限で弾かれる。計画を促す指示を勝手に足すことはしないので、TUIの `/plan` とは別物で、保証するのは「書けないこと」だけになる。

- Codexは**入る前の権限を読めなかったセッションでは入れない**（読み取り専用から出られなくなるため）。その場合は理由が会話に出る
- 進行中の応答には効かない。次に送る指示から効く
- Codexが計画を出した場合は、進み具合が `[ ]` / `[~]` / `[x]` の一覧として会話に並ぶ

### コードレビューを実行する

入力欄の周りの「レビュー」ボタンで起動する。**CLIごとに作りが違う。**

|             | 仕組み                              | 対象・出し先の選び方                                     |
| ----------- | ----------------------------------- | -------------------------------------------------------- |
| Codex       | 専用メソッド `review/start`         | ボタンを押すとQuickPickで対象（4種）とdeliveryを選ばせる |
| Claude Code | `/code-review` を発言として送るだけ | QuickPickは出さない。CLIが対話で対象を聞いてくる         |

- Codexの対象は「未コミットの変更」「ベースブランチとの差分（ブランチ名を入力）」「指定コミット（SHAを入力）」「自由記述（指示文を入力）」の4種
- deliveryは「この会話の中」（既定）と「別のタブ」。別のタブを選ぶと新しいCodex画面が開き、元の会話には影響しない
- **レビュー中は割り込めない**。Codexのapp-serverはレビュー中のターンへの割り込みを受け付けないため、応答中に送った指示は待ち行列に積まれ、レビューが終わってから送られる。入力欄の下に「レビュー中は割り込めません」と出る
- `/code-review` はClaude Codeの実在コマンド（実測で確認済み）。CLIのコマンド一覧に無い場合はボタンごと出さない（`/review` は実在しないため候補にも出さない）
- 結果は専用の表示を作らず、通常の会話として流れる

### 会話を書き出す

入力欄の周りの「エクスポート」ボタンで、会話全体をMarkdownとして取り出す。CodexのTUIのCtrl+T（トランスクリプト表示）・`/raw`（生テキストモード）に相当する。issue #25・design.mdの§14.23。

押すとQuickPickで次の3つから選ぶ。

| 選択肢                 | 内容                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| クリップボードへコピー | 会話全体をMarkdownでコピーする                                                                             |
| ファイルへ保存         | 保存ダイアログを出し、Markdownファイルとして保存する（既定のファイル名は `transcript-<日時>.md`）          |
| 生テキストで開く       | 装飾（バブル・折りたたみ・画像）を持たない通常のエディタタブとして開く。コピー・検索・保存もそのままできる |

- 会話がまだ無い状態で押すと、その旨を伝えて何も起きない（黙って空のファイルを作らない）
- 3つとも同じMarkdown（発言・コマンド実行・ファイル差分・Web検索結果・画像の参照などを見出しごとに並べたもの）を使い回す。画面の折りたたみ（コマンド出力・思考の要約表示）は書き出しには影響せず、常に全文が入る
- **外部へ送る機能は作らない**。クリップボード・ローカルファイル・エディタタブの3つに留める。生テキストにはコマンド出力やファイル内容など機微な内容が含まれうるため
- 会話全体の組み立てはMarkdownの拡張機能ホスト側で行い、Webviewの描画は止めない。長い会話でも上限（500万文字）を超えた分は先頭を捨てて末尾を残す

### 応答のMarkdown描画

応答本文を見出し・箇条書き・強調・インラインコード・コードブロック・リンクとして描画する（issue #290・design.md §14.51）。**Codex / Claude Code両画面共通**で、外部ライブラリは使わず拡張機能内で組み立てている。

- コードブロックには右上に「コピー」「エディタへ挿入」「新規ファイルで開く」の3ボタンが付く。「エディタへ挿入」は開いているエディタの選択範囲へ差し込み、「新規ファイルで開く」はフェンスの言語表記（例: `ts`）に応じたシンタックスハイライト付きの新規タブとして開く
- リンクのクリックは[Web検索結果](#会話を書き出す)と同じ経路で既定のブラウザへ開く。Webview内では遷移しない
- 応答が生成中（ストリーミング中）でも、閉じていないコードフェンスや途中で切れた強調記号は表示が崩れず、閉じたときに描き直される
- コマンド実行・思考（reasoning）の表示は対象外で、従来どおり生テキストのまま
- `agent.chat.renderMarkdown`を`false`にすると、装飾を持たない従来の生テキスト表示へ戻る（[設定](#共通)参照）

### 差分からファイルとdiffを開く

会話中に表示されるファイル変更の差分（`<summary>`の見出し行）から、対象ファイルへ直接操作できる（issue #291・design.md §14.52）。**Codex / Claude Code両画面共通**。ボタンはワークスペース内のパスに解決できる差分にのみ表示され、この判定はWebview側の見た目上のヒントに加えてホスト側でも必ず行う（`..`を含むパス・ワークスペース外の絶対パス・シンボリックリンクでの脱出は操作対象にならない）。

- 「エディタで開く」: 対象ファイルをエディタで開く。可能であれば差分の最初のハンクの行へジャンプする
- 「差分を開く」: 変更前後をVSCode標準のdiffエディタで並べて表示する。変更前の内容は会話に含まれるunified diffのテキストから復元するため、ハンク見出し（`@@ ... @@`）が無い、あるいは文脈行が不足していて復元できない差分（Claude CodeのEditツール由来の差分など）ではボタン自体を出さない
- 「この変更を戻す」: 確認ダイアログ（モーダル）で同意した後、その差分の変更だけを元に戻す。**破壊的操作**で取り消せない。ファイルが既に無い、または差分を取った時点から内容が変わっている場合は何もせず理由を表示する。移動を伴う変更（`movePath`）は対象外
- 追加（add）・削除（delete）・更新（update）・移動（move）の種類ごとに出るボタンは異なる。削除された変更には「エディタで開く」は出ない、移動を伴う変更には「この変更を戻す」は出ない、など

### 送信キーの切り替え

入力欄の送信キーを選べる（issue #288・design.md §14.49）。**Codex / Claude Code両画面共通**。

- 既定（`ctrlEnter`）: `Ctrl+Enter` / `Cmd+Enter`で送信、`Enter`は改行のまま
- `enter`: `Enter`で送信、`Shift+Enter`で改行。`Ctrl+Enter` / `Cmd+Enter`でも送信できる（`ctrlEnter`に慣れた手のままでも送れる）
- 候補メニュー（`/` `@`）を開いている間は`Enter`が候補の確定として優先され、送信されない
- IME変換中の`Enter`（変換確定）は送信しない
- 入力欄のプレースホルダの案内文が設定に追随する
- `agent.chat.sendOn`で切り替える（[設定](#共通)参照）

### 入力欄アイコン列の整理

入力欄下のアイコン列（画像・ループ・圧縮・インポート・要約・計画・高速・レビュー・エクスポート・ワークフロー）は使用頻度の差が大きく、既定ではよく使う4つ（画像・ループ・圧縮・インポート）だけを表に残し、残りを「…」ボタンのメニューへ畳む（issue #296・design.md §14.58）。**Codex / Claude Code両画面共通**。

- 「…」を押すとメニューが開き、アイコンに文字ラベルを添えた項目が並ぶ。押すと元のボタンと同じ動作をし、メニューは閉じる
- メニューは`ArrowUp` / `ArrowDown`で項目間を移動し、`Tab` / `Shift+Tab`もメニューの中だけを巡る（外へフォーカスは逃げない）。`Escape`で閉じて「…」ボタンへフォーカスが戻る。メニュー外をクリックしても閉じる
- 「計画」「高速」はメニューに移っても押されている状態（トグルON）が見た目で分かる
- インポート・要約・レビュー・高速は、元々の表示条件（`showImport` / `showRecap` / コマンド一覧の有無 / Fast mode対応）を表・メニューのどちらにあっても同じまま引き継ぐ
- `agent.chat.composerButtons`（既定 `[attach, loopToggle, compact, claudeImport]`）で表に出すボタンとその並びを変えられる。指定しなかったボタンは必ず「…」メニューに現れ、どこからも到達できなくなることはない。未知のIDや重複を含む場合は既定へ丸め、警告を出力チャネル「Agent Sessions」へ記録する（[設定](#共通)参照）

### プリセットから新しい会話を開く

モデル・承認・サンドボックス・作業ディレクトリを毎回組み直さずに済むよう、名前付きプリセット（`agent.sessionPresets`）を選んで新しい会話を開ける（issue #295・design.md §14.56）。

- コマンドパレットの `Agent: プリセットから新しい会話を開く…`、または履歴ビューのタイトルバーのアイコンから使う
- `agent.sessionPresets`が空（既定）のときはどちらにもコマンドが出ない
- 選ぶと、そのプリセットの`model` / `effort` / `approvalMode`（Codexの承認方針、Claudeは`permissionMode`相当） / `sandbox`（Codexのみ）で新しい会話が開く
- **プリセットは拡張機能の設定より権限を緩める方向へは効かない。** `approvalMode` / `sandbox`が現在の設定より緩い場合は無視し、警告を出す（ワークフロー定義YAMLのクランプと同じ方針。[設定](#共通)参照）
- マルチルートワークスペースでは、プリセットに`workingDirectory`の指定が無い（または無効な）場合、開く前に作業ディレクトリをQuickPickで選べる。フォルダが1つのときはQuickPickを出さない
- `workingDirectory`はワークスペースフォルダ配下の絶対パスに限る。外を指す値は無視して警告を出す

### TODO一覧

Claude CodeのTUIの `/todos` に相当する表示。**Claude Code画面だけの機能**（issue #31のスコープがClaude側のみのため）。

Claude CodeがTodoWriteツールを使うと、入力欄の上（ステータス行とループパネルの間）にTODO一覧が出る。会話には積まず、更新のたびに**同じ場所が書き変わる**。項目ごとに `[ ]`（未着手）/ `[~]`（進行中）/ `[x]`（完了）が付き、進行中の項目は太字、完了した項目には取り消し線が付く。TodoWriteを使わないセッションでは表示自体が出ない。

- TodoWriteは呼ばれるたびに一覧をまるごと送ってくる（差分ではない）。実測で確認済み
- `--resume` で開き直したセッションでも、transcriptに残っている最後のTodoWriteの内容を初期表示にする
- Codex画面には出ない。Codexは計画（`turn/plan/updated`）を会話内の `plan` 項目として既に表示しており（[前述](#計画だけ立てさせるplan-mode)）、状態が分かる一覧という受入基準はそちらで満たしているため、今回は変更していない

### 問い合わせに答える

ツールやMCPサーバが「どちらにしますか」「この値を入れてください」と聞いてくることがある。TUIでは対話プロンプトとして出るもので、この拡張機能では**会話の中にカード**として出す。

**Codex画面だけの機能**。app-serverが `item/tool/requestUserInput` と `mcpServer/elicitation/request` を送ってくるのに対し、Claude Codeのstream-jsonには同じ要求を拡張機能へ渡す経路が無い（承認は別の仕組みで届く）。

- 選択肢がある場合はボタン、自由入力の場合は入力欄が出る。答えると会話に残る
- MCPサーバからのフォーム（elicitation）は**どのサーバからの要求か**を必ず添えて出す。外部のプログラムからの依頼なので、信用の判断材料を隠さない
- 入力欄の形が読み取れなかった場合は、欄を作らず拒否だけができる状態にする（作った欄で嘘の値を送らないため）
- 答えないままタブを閉じた場合は取り消しとして返す。放置するとCLIが待ち続けるため

### アカウント

サイドバーの設定パネルに、ログイン状態とlogin/logoutの操作を出す（Codex / Claude Codeのタブそれぞれ）。issue #29・design.mdの TP-53。表示するのはログイン済みかどうか・ログイン方式・メールアドレスなどの識別子・プランまでで、トークンやAPIキーの値は画面にもログにも出さない。

- **状態の取得**: Codexは `account/read`（app-server）、Claude Codeは `claude auth status --json`。どちらも会話を開いていない状態で問い合わせられる
- **ログアウト**: 確認ダイアログを挟んだうえで、CodexとClaude Codeどちらも対話端末を要さないCLIサブコマンド（`codex logout` / `claude auth logout`）をそのまま実行する
- **ログイン**: Codexは「APIキーでログイン」ボタンからVSCodeの入力欄（マスク表示）でキーを受け取り、`codex login --with-api-key` の標準入力へ渡す（引数やログには残さない）
- **ブラウザでのOAuthログイン**（Codexの既定のChatGPTアカウントログイン、Claude Codeの唯一のログイン手段）は、**拡張機能内では完結できない**。統合ターミナルを開いてコマンド（`codex login` / `claude auth login`）を入力するところまでで止め、実行はユーザーがEnterを押すまで行わない
- Claude Code側にはAPIキーでの非対話ログインの経路が見つからなかったため実装していない。「無い」という事実を画面の案内文に出している（詳細は design.md §14.16）

### MCPサーバー

サイドバーの設定パネル下部に、設定されているMCPサーバーの一覧を出す（Codex / Claude Codeのタブそれぞれ）。issue #27・design.mdの TP-50。

サーバーごとにチェックボックス（有効/無効）・名前・状態バッジ（接続済み / 無効 / 起動していません）・提供ツール数を出す。チェックボックスで有効/無効を切り替えられ、CLIの設定へ書き込まれるので次回以降も保たれる。

- Codexは `config/value/write` で `config.toml` の `mcp_servers.<name>.enabled` を書き換えてから `config/mcpServer/reload` で反映する。Claude Codeは `mcp_toggle` を送る。どちらも会話を開いていない状態から切り替えられる
- 起動に失敗しているサーバーは「起動していません」で分かる。**理由の出し方はCLIで違う**。Claude Codeの `mcp_status` はエラー文言をそのまま返すため理由まで表示できるが、Codexの `mcpServerStatus/list` には失敗理由を持つフィールドが無く、無効化されたサーバーと見分けが付かない（実測で確認した制約。詳細は設計書 §6・§14.14）
- 一覧を取得できない場合（CLIが古い、app-serverが起動しない、応答がない）はその旨を出し、パネル自体は壊さない。0件（未設定）とは表示を分ける

### hooks

サイドバーの設定パネル下部（MCPサーバーの下）に、登録されているhookの一覧を出す（Codex / Claude Codeのタブそれぞれ）。issue #28・design.mdの TP-52。

hooksは任意のコマンドを実行する仕組みで、特にプロジェクト側（リポジトリ内）で定義されたhookはcloneしただけで任意コマンドが動く経路になりうる。**中身を隠さず全部見せる**方針で、1件あたりイベント名・実行するコマンド・出どころ（user / project / plugin等）を表示する。

- **Codex**は信頼状態（信頼済み / 未信頼 / 変更あり / 管理者設定）も持つ。未信頼・変更ありのhookには「信頼する」ボタンが出る（`config/batchWrite`。実行ファイルの文字列調査が根拠で、実機での書き込み確認はしていない）。**取り消す操作は無い**（CLI側にそれに相当する経路が見つからなかったため）。信頼していないhookが実行をブロックされると、会話画面に一言注記が出る（`hook/completed` の `status: 'blocked'` が根拠。CLIのプロトコルには「信頼してください」という要求そのものが存在しない）
- **Claude Code**は一覧のみ。**信頼状態を返す経路がプロトコルに無い**（実測: プロジェクト側にhookを1件だけ置いた状態で起動したところ、承認を求められることなくそのまま実行された）ため、信頼操作のボタンは出さない。「無い」旨を注記に出す。また、plugin由来のhookは一覧に出てこないことがある（実測で確認した制約）
- 一覧を取得できない場合はその旨を出し、パネル自体は壊さない

### skills

サイドバーの設定パネル下部（hooksの下）に、使えるskillsの一覧を出す（Codex / Claude Codeのタブそれぞれ）。issue #35・design.mdの TP-56。

skillはモデルへ渡す指示（プロンプト）で、hooksと同じくプロジェクト側（リポジトリ内）で定義されたskillはcloneしただけで効く経路になりうる。1件あたり名前・説明・出どころ（ユーザー / プロジェクト / プラグイン / 同梱 / 管理者配布 / 不明）を表示する。

- **Codex**は`skills/list`（実測。cwdごとに`{name, description, path, scope, enabled}`が返る）から一覧を作り、`scope`（`user` `repo` `system` `admin`）をそのまま出どころへ対応させる。チェックボックスで有効/無効を切り替えられ、`skills/config/write`（スキーマ根拠。この環境のskill設定を書き換えない方針のため実際の書き込みは未検証）で反映する
- **Claude Code**は`reload_skills`（実測。専用の一覧取得要求は無く、これが唯一の経路）から一覧を作る。**有効/無効を返す・切り替える経路がどちらもプロトコルに無い**ため、常に「有効」として表示しチェックボックスは出さない。出どころは応答の`description`に付く注記（` (user)` ` (project)`、プラグインは`name`が`plugin:skill`の形になり`description`の先頭に`(plugin) `）からの**推測**であり、正式なAPIフィールドではない旨を注記する
- 一覧を取得できない場合はその旨を出し、パネル自体は壊さない

### plugins / apps

サイドバーの設定パネル下部（skillsの下）に、導入済みのpluginの一覧を出す（Codex / Claude Codeのタブそれぞれ）。Codexはさらにappの一覧も出す。issue #32・design.mdの §14.20。

pluginは任意のコード（hookやMCPサーバーなど）を持ち込む仕組みで、hooks・skillsと同じく**中身を隠さず全部見せる**方針にする。1件あたり名前・説明・出どころ・提供するもの（skills / agents / hooks / MCPサーバーの件数、分かる範囲）を表示する。**インストールは外部からコードを持ち込む操作**のため、実行前に確認ダイアログで「何をどこから入れるか」を必ず示す。

- **Codex**は`plugin/installed`（実測: 導入済みのpluginをマーケットプレイス単位で返す）から一覧を作り、`plugin/read`（1件ずつ。この環境では`plugin/read`の`installed`/`enabled`フィールドは信用できないことを実測で確認したため、提供するものの内訳だけを使う）で内訳を補う。**有効/無効を切り替える専用APIが無い**ため、インストール/アンインストールのみ操作できる（`plugin/install` / `plugin/uninstall`。スキーマ根拠。この環境のplugin設定を書き換えない方針のため実際の書き込みは未検証）。アンインストールは確認ダイアログ必須
- appも一覧する（`app/installed` + `app/read`）。**有効/無効・インストール/アンインストールの確定した書き込み経路が無い**ため閲覧のみ。「無い」旨を画面に注記する
- **Claude Code**は`claude plugin list --json` + `claude plugin details <id>`（実測。専用のJSON-RPC相当の経路は無く、CLIサブコマンド一式を使う。`reload_plugins`は`initialize`と同じ全コマンド一覧を返すだけでplugin専用の情報を持たないため使わない）から一覧を作る。有効/無効の切替（`claude plugin enable` / `disable`）・インストール（`claude plugin install`）・アンインストール（`claude plugin uninstall`）をすべて操作できる。切替以外はいずれも確認ダイアログ必須（**enable/install/uninstallは実測ではなく`--help`根拠のみ**。この環境のplugin設定を変える可能性がある操作を調査目的で実行しないこととしたため）
- 一覧を取得できない場合はその旨を出し、パネル自体は壊さない

### 他エージェントからの設定インポート

サイドバーの設定パネル下部（pluginsの下、Codexのタブのみ）に、Claude Codeなど他エージェントから取り込める設定の一覧を出す。CodexのTUIの `/import` に相当する。issue #36・design.mdの TP-57。

インポートは既存の設定を書き換えうる操作のため、**実行前に必ず確認ダイアログで何を・どこから・どこへ取り込むかを示す**。1件あたり種別（Instructions / 設定 / skills / plugins / MCPサーバー設定 / サブエージェント / hooks / スラッシュコマンド / メモリ / 最近のセッション）・CLIが返す説明文（何を・どこから・どこへ、が書かれている）・内訳（名前付きの項目は代表的な名前を出す。メモリの中身そのものは会話本文と同じ扱いで出さず件数のみ）を表示する。チェックボックスで取り込む対象を選び、「選択した項目をインポート」で実行する。

- `externalAgentConfig/detect`（`includeHome: true` を指定）で候補を検出する。**既定の呼び出し（`includeHome`省略）では常に空になる**ことを実測で確認したため、必ず指定する。この一覧はCodexにログイン中の会話を開いていなくても取得できる
- 検出した項目をそのまま`externalAgentConfig/import`へ再送して実行する。応答は`importId`のみを即座に返し、実際の結果は`externalAgentConfig/import/completed`通知で非同期に届く（Phase 0調査のUI文言「Import started. You can keep working while it finishes.」と整合）。拡張機能は単発起動のクライアントで完了通知を最大5分待ち、届かなければ「開始はできたが結果は履歴で確認してほしい」旨を表示する（黙って何も起きない状態にしない）
- `externalAgentConfig/import/readHistories`で過去の実行履歴（実行日時・成功/失敗の件数）も一覧に出す。実行前に「前回いつ何を取り込んだか」が分かる
- **migrationSourceはClaude Code固定**（指定を省略。実測でこれが既定のソースであることを確認した）。バイナリの文字列調査でCursor向けの実装（`source_cur.rs`）も存在することが分かったが、issueのスコープ（Claude Codeのみ）に合わせて選択UIは設けていない
- **実行系（`externalAgentConfig/import`）は開発中に一度も実行していない**（この環境の実際の設定を書き換えない方針のため）。検出（`detect`）と履歴読み取り（`readHistories`）は実際にこのリポジトリで`codex app-server`を起動して実測した

### バックグラウンドターミナル

チャット画面の入力欄の上（TODO一覧と同じ並び）に、バックグラウンドで走っているプロセスの一覧を出す。CodexのTUIの `/ps` に相当する。issue #33・design.mdの §14.23。

- **Codex**は会話内の `commandExecution` 項目のうち `status: inProgress`（まだ終わっていない）のものを一覧にする。**個別に停止する確定した経路が無い**（`command/exec/terminate` はクライアント自身が起動したプロセス専用で、エージェントが実行したコマンドのprocessIdを渡すと「no active command/exec for process id」で拒否されることを実測で確認した）ため、停止ボタンは出さず「この画面から停止する経路はありません」と表示する
- **Claude Code**はBashツールを`run_in_background:true`で呼んだときに届く `background_tasks_changed` 通知から一覧を作る。**`stop_task`で実際に停止できる**（実測で確認済み）ため、各行に停止ボタンを出す。破壊的操作のため実行前に確認ダイアログを必ず挟む
- 実行中のものが無い間は一覧の枠ごと表示しない

### サブエージェントの状況表示

Codexがサブエージェントを起動したとき、その活動を会話の中の項目として表示する（issue #34・design.mdの TP-55 / §14.26）。Codex TUIの「switch the active agent thread」に相当する機能を調べた結果、**アクティブなagent threadを切り替える経路は無い**（`codex app-server generate-json-schema` でClientRequestの95メソッドを全数確認したが、切替に相当するものが無かった）ため、切替ボタンは実装していない。

- サブエージェントの起動・入力・中断（`subAgentActivity`）は、どのエージェント（`agentPath`）が何をしているか（開始/応答/中断）が読める形で会話に出る
- サブエージェントを操作するツール呼び出し（`collabAgentToolCall`。起動・入力送信・再開・完了待ち・終了）は、指示・モデル・reasoning effort・対象エージェントごとの状態まで本文に読める形で出る
- 履歴ツリーでは、対象スレッドの親スレッドid（`parentThreadId`）が取れた場合だけtooltipに表示する。**ツリーを親子でネストする表示は実装していない**（`parentThreadId` が入ったスレッドを実機で再現できておらず、既存の履歴一覧はサブエージェント由来のスレッドを意図的に除外しているため。詳細は design.md §14.26）

### コスト

チャット画面のフッター（入力欄の下、レート制限の消費率・コンテキスト残量と同じ行）に、現在のセッションの推定コストを出す（Claude Codeのみ。issue #37・design.mdの TP-60）。TUIの `/cost` に相当する。

- `get_usage`（control protocol）から取り、ターンが終わるたびに読み直す。**レート制限の消費率・コンテキスト残量とは別の数字**なので、`コスト $0.2177` のように見出しを分けて並べる
- サブスクリプションのプランでも金額は0にならず、API料金換算の見積額が入る。ただし**実際の請求額ではない**ため、ホバーすると注記が出る
- Codexには該当する金額のAPIが無い（`account/usage/read` は確認したが、返るのはトークン数・連続日数の統計のみで金額を含まない）ため、Codex画面には出ない
- セッション分析（TUIの `/insights` 相当）は、入力欄で `/insights` と打つか候補から選ぶだけで動く。既存のスラッシュコマンド送信の仕組みをそのまま使うため専用のボタンは無い。CLIの合成応答として会話に表示される（処理に時間がかかることがある）

### セッション累計のトークン数

チャット画面のフッター（コストと同じ場所）に、Codexのセッションで**累計トークン数**を出す（Codexのみ。issue #294・design.mdの§14.53）。

- Codexには金額（コスト）を取得する経路が無い（上記「[コスト](#コスト)」のとおり）。その代わりとして、`thread/tokenUsage/updated` 通知の `total.totalTokens`（スレッド全体の累計トークン数）を `累計トークン 12k` のように出す
- コンテキスト残量（`コンテキスト N/M`。圧縮すると減る）とは別の数字。累計トークンは圧縮しても減らない
- **値がまだ届いていない間（会話を始める前など）は表示ごと出さない**。`0`や`-`を出すと「取れていない」のか「本当に0」なのか区別が付かなくなるため
- ホバーすると正確な値と、金額を出さない理由が注記として出る
- Claude Codeのセッションでは出ない（既存の「コスト」表示だけが今までどおり出る）

### 同じ指示を繰り返す（ループ）

「1話書く → 次へ → 次へ → …」のように、同じ指示を条件が満たされるまで送り続けたい場面のための機能。チャット画面の「ループ」ボタンでパネルを開き、次の4つを入力して「ループ開始」を押す。

| 入力     | 内容                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| 初回指示 | 1回目に送る指示。空なら継続指示から始まる（例: `第1話を執筆`）                   |
| 継続指示 | 2回目以降に繰り返す指示（例: `次へ`）                                            |
| 最大回数 | 送信回数の上限。1回目を含めて数える（上限200）                                   |
| 終了条件 | 満たされたら止める条件。空なら回数だけで終わる（例: `20話の執筆が完了している`） |

ループ中は入力欄の上に `ループ 3/20回目` と進行が出る。1ターンが終わるたびに次の指示が自動で送られ、次のいずれかで止まる。

- 終了条件が成立した（条件を入力した場合、指示に「満たしたら合図を出すように」という依頼が自動で添えられ、その合図を検出して止まる）
- 最大回数を送り終えた
- ターンが失敗した、またはCLIが落ちた
- 「ループ停止」を押した
- 手動で発言した、または中断した（割り込みとみなして止める）

承認カードが出ている間や、手で送った指示が待ち行列に残っている間は次の指示を送らず、それらが片付いてから続きへ進む。止まった理由は次のループを始めるまで画面に残る。

## ワークフロー（並列オーケストレーション）

複数のタスクを依存関係つきのYAMLで定義し、独立したタスクを並列のセッションで走らせる機能。`T1 → (T2 || T3) → T4` のように、T1が終わったらT2とT3を同時に始め、両方が終わってからT4を始める、という形が書ける。各タスクは通常のチャット画面（Codex / Claude Code）1枚として開き、独立したgit worktreeで走る。設計の詳細は[docs/design.md](docs/design.md) §16を参照。

**状態: 実装は完了している。実機確認は途上。** ワークフローの実行・並列化・worktree隔離・危険操作の検知・ワークフローView・成果の統合・PR/MR作成・ゴール→ロードマップ→YAMLの生成・タスク間メッセージングは、いずれも実行への配線を含めて実装済みで動く。ユニットテストとプロトコル上の実測までは済んでいるが、実VSCode上で通しで動かした確認はまだ無い（[既知の制約](#既知の制約)、[docs/manual-test.md](docs/manual-test.md) W群）。

タスクが終わるたびに拡張機能がrun専用の統合ブランチへマージし、worktreeを片付けて次のタスクへ進む。全タスクが `done` になると、統合ブランチからmainへのPR/MRを作る（設定で無人マージまで進めるか、PR/MR止まりにするかを選べる。[後述](#無人実行についての注意)）。PR/MRは「タスクブランチ→統合ブランチ」「統合ブランチ→main」の2層で作られ（`agent.workflows.pullRequest`）、ホストはGitHub（`gh`）とGitLab（`glab`）の両方に対応する（`agent.workflows.forge`）。ゴールの文からロードマップ（Markdown）を経てYAMLへ落とす2段階生成も使える（[後述](#ゴール文からyamlを生成する)）。

### 開き方

サイドバー（Agents）の履歴のタイトル行にあるワークフローのアイコン、またはチャット画面のアイコン列にあるワークフローのアイコン（既定では「…」メニューの中。[後述](#入力欄アイコン列の整理)）を押すと、次の操作を選べる。

- ワークフローを実行…（YAMLの定義を選んで開始する）
- ワークフローViewを開く（実行中のものがあれば先頭に出て、件数が添えられる）
- ゴール文からワークフローを生成…
- ロードマップを生成…
- ワークフローを停止…（実行中のものがあるときだけ出る）

同じ操作はコマンドパレット（`Ctrl+Shift+P`）の `Agent:` からも実行できる。

### 無人実行についての注意

**`autoApprove: true` を書いたタスクは、承認要求を拡張機能が自動で許可しながら走る。読み飛ばさずに次を理解してから使うこと。**

- **危険と判定した操作だけは自動で通さず、そのタスクを止めて人へ回す。** 判定はパターン照合による補助でしかなく、一次防御ではない（後述）
- **一次防御はサンドボックスであり、既定で有効。** `sandbox`（Codex）/ `approvalMode` / `permissionMode` はYAMLから拡張機能の設定より**緩める方向へは動かせない**。緩める指定は無視され警告が出る
- **Claude Codeの `bypassPermissions` はワークフローでは使われない**（`agent.workflows.allowClaudeBypassPermissions` で明示的に許可した場合を除く）**。** この設定では承認要求そのものが発行されず、上の危険判定が丸ごと働かない。`claude.permissionMode` を `bypassPermissions` にしている場合、ワークフローのタスクは `acceptEdits` へ読み替えて実行し、その旨を警告に出す（チャットの設定はそのまま。ワークフロー実行時だけの読み替え）。**確認を挟まずに走らせたい場合は、`bypassPermissions` ではなく `autoApprove` を使う**（[後述](#確認を挟まずに走らせたい場合)）
- **タスクの `allow` を書くと、そのタスクに関する限り危険判定そのものが効かなくなる。** `allow` は「既定の停止条件から外すパターン」を追加するフィールドで、書いた分だけそのタスクは自動承認の対象が広がる（`.git` 配下への書き込みなど一部は `allow` でも解除できない）。使っているワークフローは実行前に確認が出て、ワークフローViewの警告欄に常時表示される
- **`autoApprove: true` はYAMLに書くだけでは効かない。** machineスコープの設定 `agent.workflows.allowAutoApprove`（既定 `false`）が有効なときだけ意味を持つ。無効のままなら、YAMLに何と書かれていても全ての承認要求を人へ回して走る（設定は[後述](#設定)）
- **`agent.workflows.finalMerge` の既定は `auto`。** 全タスクが `done` になると、統合ブランチからmainへのPR/MRを作ったうえで、そのままmainへマージする（`gh pr merge` / `glab mr merge`）。**人の目を通さずmainが進む。** MRの自己マージを禁じる運用規約がある場合は、machineスコープの設定で `agent.workflows.finalMerge` を `pr-only` にする。PR/MRを作って止め、mainへの書き込みは人が行う

### 最小のYAML

ワークフロー定義は`.agents/workflows/`（既定。設定 `agent.workflows.dir` で変更可）配下の `.yaml` / `.yml` ファイルに置く。

```yaml
version: 1
name: 認証機能の追加

defaults:
  provider: codex # codex | claude
  maxParallel: 3

tasks:
  - id: T1
    prompt: 認証方式を検討し、docs/auth-design.md に設計を書く
    done: docs/auth-design.md を書き終えている

  - id: T2
    dependsOn: [T1]
    prompt: |
      docs/auth-design.md に従いAPI側を実装する。
      設計時の要約:
      {{T1.result}}
    done: API側の実装が終わり、全テストが通っている

  - id: T3
    dependsOn: [T1]
    prompt: docs/auth-design.md に従いUI側を実装する
    done: UI側の実装が終わり、全テストが通っている

  - id: T4
    dependsOn: [T2, T3]
    prompt: API側とUI側の結合部分に齟齬がないか確かめ、あれば直す
    done: 結合部分の確認が終わり、全テストが通っている
```

`id` は英数字・`_`・`-`のみ（先頭ハイフン不可、`^[A-Za-z0-9_][A-Za-z0-9_-]{0,49}$`）。`dependsOn` は先に完了していなければならないタスクidの配列で、同じ段（同時に走れる集合）は依存の深さから決まる。`done` は終了条件で全タスクに書く（宣言だけでなく、拡張機能がコミットの有無なども確認する）。`{{T1.result}}` のように書くと依存タスクの最後の応答を差し込める（依存に挙げたタスクのみ参照可）。フィールドの全一覧と検証ルールはdesign.md §16.2。

### 実行の手順

1. コマンドパレットから `Agent: ワークフローを実行…`（`agent.workflows.run`）。`agent.workflows.dir` 配下のYAMLをQuickPickで選ぶ
2. `allow` を使っているタスクがあれば、実行前に確認ダイアログが出る
3. ワークフローViewが開き、進行を確認できる。開き直すには `Agent: ワークフローViewを開く`（`agent.workflows.view`）
4. 止めるには `Agent: ワークフローを停止…`（`agent.workflows.stop`）で実行中のrunを選ぶ

### Viewの見方

専用のWebviewパネルで、**この画面だけ見ていれば全体の状況が分かる**ことを狙っている。

- **全体の進捗**: 状態ごとの件数（完了・実行中・承認待ちなど）と経過時間、全体のパーセンテージ
- **依存グラフ**: タスクをノード、`dependsOn` をエッジとした有向グラフ。依存の深さで段が決まるので、`T1 → (T2 || T3) → T4` はそのまま縦3段になる。ノードは色と記号の両方で状態を示し（色だけに頼らない）、ライト/ダーク双方のVSCodeテーマ色で読める。外部ライブラリは使わずWebview内で組み立てている
- **タスク一覧**: グラフの下の表。id・状態・provider・作業ディレクトリ（worktreeのブランチ）・経過・送信回数・直近の応答が並ぶ
- **操作**（一覧の行に置く）:
  - `中断`: 進行中のターンだけ止める。タスクは止まらず、次の指示から続く
  - `タスク停止`: そのタスクのループを止め、失敗として扱う（他のタスクは走り続ける）
  - `再実行`: 失敗・スキップされたタスクを、依存が満たされていればもう一度走らせる（新しいスレッド・新しいworktreeでやり直す）
  - `続ける`: 送信回数の上限に達して止まったタスクを、**同じ会話・同じworktreeのまま**続きから走らせる。押すたびに上限（`maxIterations`）の分だけ予算が足される。あと少しで終わりそうなのに回数だけが尽きた、という場合に最初からやり直さずに済む。セッションが生きている間だけ出るボタンで、ウィンドウをリロードした後は「再実行」になる
  - `承認`: 承認待ちのタスクへ、要求の内容を見て許可・拒否を返す
  - `再マージ`: マージが衝突して `blocked` になったタスクを、人が手元で衝突を解いたあとにもう一度マージする
- **画面全体の操作**: 実行・全体の停止・定義ファイルを開く・統合ブランチのPR/MRを開く・「統合ブランチと残ったworktreeをまとめて片付ける」（人が明示的に押したときだけ撤去する。runが実行中の間は撤去できない）
  - `全体の停止`: まだ始まっていないタスクをスキップし、走っているタスクのループも止める（止まったタスクは「手動停止」として失敗扱いになる）。**進行中のターンには割り込まない**ので、そのターンが終わってから次の指示を送らずに止まる。worktreeとブランチは残るため、途中まで進んだ内容は後から確認できる
- **統合の状況**: 統合ブランチ名、取り込み済みのタスク数、タスクごとと統合ブランチのPR/MRへのリンク
- ノードまたは一覧の行を押すと、そのタスクのチャットタブが開く（初回は背面で開く）。**タブを閉じてもタスクは止まらない**。ノードを押せば同じセッションが開き直り、会話が復元される（これが効くのはウィンドウが生きている間だけで、リロード後は「再実行」になる）
- 警告欄に、gitでないフォルダへのフォールバック・`allow` によるチェック解除・回数切れ・PR/MR作成の前提不足（remote / CLI / 認証）などが常時出る
- 画面に出す動的な文字列（応答の要約・タスクid・ブランチ名など）はテキストノードとして挿入する。エージェントの出力やYAMLに由来する内容を信用しないための対策

### ゴール文からYAMLを生成する

タスクを1つずつ書く代わりに、達成したいことを文章で渡してYAMLの下書きを作らせられる。規模の大きいゴールは、間にロードマップ（Markdown）を挟む2段階の経路（[後述](#ロードマップを生成する)）も使える。

1. コマンドパレットから `Agent: ゴール文からワークフローを生成…`（`agent.workflows.plan`）
2. 「ゴール文から生成」「ロードマップから生成」のどちらかをQuickPickで選ぶ（続けて、生成に使うエージェントを選ぶ。[後述](#生成に使うエージェント)）
   - **ゴール文から生成**: ゴールを入力する（例: `認証機能を追加してテストとレビューまで終える`）。分解用のセッションが1つ作られ、YAMLだけを返すよう指示してスキーマとワークスペースの情報を渡す。妥当性の検証を通らなければ、エラーを添えて1度だけ再生成する
   - **ロードマップから生成**: `agent.workflows.roadmapDir`（既定 `docs/roadmap`）配下のロードマップから対象ファイルとフェーズをQuickPickで選び、選んだフェーズをYAML化する。**フェーズは複数選べる**（先頭の「全フェーズ」でロードマップ全体を一度に選べる）。選んだ分は1本のYAMLにまとまり、1つのrunで通しで走る。ただし**選べるのはフェーズ単位**で、フェーズをまたいだ部分選択（フェーズ1の後半とフェーズ2の前半だけ、など）はできない
   - ロードマップにIssue番号が無い項目へIssue番号が書かれるなど、生成されたYAMLの `issue` がロードマップと食い違っていた場合は、**ロードマップの値へ直してから保存する**（誤った番号のままだとPR/MRのマージで無関係のIssueが閉じるため）。直した件数は警告で知らせる
   - 合計の項目数がタスク数の上限（50件）を超える選択では、**フェーズ単位で複数のYAMLへ分けて生成する**。分けた分は別々のrunになるため、**前のrunが終わってから次を実行すること**。分けたYAMLをまたぐ依存はYAML上で表現できないため落とし、落とした件数を警告で知らせる（実行順序は人が守る）
3. 保存先のファイル名を確認する。ゴール文から作った名前が既定値として入っているので、そのままでよければEnterを押す（取り消すと保存しない）
4. `agent.workflows.dir` へ保存され、エディタとワークフローViewが開く。**生成したまま自動実行はしない**。依存関係の図を見ながら人が直してから「実行」を選ぶ

生成されたYAMLに、`dependsOn` に挙げていないタスクを参照するテンプレート変数（`{{R3.cwd}}` など）が含まれていた場合は、保存前にその参照だけを機械的に落とす。検証を通らず生成そのものが失敗してしまうのを避けるため。落とした件数は警告で知らせるので、参照が消えて文意が通らなくなったタスクがないか確認すること（`dependsOn` は増やさない。ロードマップに書かれた依存と食い違わせないため）。

ファイル名の既定値は、ゴール文から記号と空白を `-` へ畳んで作る（日本語はそのまま残す。40文字で切り詰め）。ゴール文にファイルパスが混じっている場合は、その部分をファイル名（拡張子なし）へ縮めてから繋ぐので、`docs/plan/x.md を読んで` は `x-を読んで` になる。「認証 機能/を追加」のように区切り文字を別の意味で使っている場合は縮約せず、従来どおり `-` へ畳む。

分解用のセッションは読み取り専用相当で起動し、承認要求は全て拒否する（ワークスペースの中身を読むため、リポジトリに仕込まれた文を指示として実行させないための対策。拡張機能の設定より緩めない、という通常のクランプとは別に、常に固定の値で起動する）。承認モードはCodexが `never`、Claude Codeが `manual` で、どちらも「ワークスペースの読み取りだけができる」状態になる。生成されたYAMLが `autoApprove: true` や非空の `allow`、`sandbox` / `approvalMode` の緩和指定を含んでいれば、保存時に強調して知らせる。

### 生成に使うエージェント

ワークフローとロードマップの生成は、Codex / Claude Codeのどちらでも走らせられる。

- **チャット画面のアイコンから起動したとき**: その画面と同じエージェントを使う（Claude Codeの画面から押せばClaude Codeが、Codexの画面から押せばCodexが開く）
- **サイドバーのアイコン・コマンドパレットから起動したとき**: 起動元が決まらないため、生成に使うエージェントをQuickPickで選ぶ

設定項目は無い。片方のCLIしか入っていない場合でも選択肢は両方出るので、入っているほうを選ぶこと。

### ロードマップを生成する

ゴールが複数のrunにまたがる規模のときは、先にロードマップ（Markdown）を作って人がレビューし、そこからYAMLへ落とす。1段で直接YAMLを作ると、規模の大きいゴールではタスク数が膨らみ、分解の誤りをYAMLの上で読み取ることになるため。

1. コマンドパレットから `Agent: ロードマップを生成…`（`agent.workflows.roadmap`）
2. ゴールの文を入力する（サイドバー・コマンドパレットから起動した場合は、続けて生成に使うエージェントを選ぶ）
3. 保存先のファイル名を確認する。ゴール文から作った名前が既定値として入っているので、そのままでよければEnterを押す（取り消すと生成しない）
4. 生成セッションが、ワークスペースの構成・`AGENTS.md` / `CLAUDE.md`・既存のIssue（`gh issue list` / `glab issue list` が使えれば取得。既存Issueとの重複を避け、項目にIssue番号を紐づけるため）を参照してロードマップを作る。生成セッションはゴール文からのYAML生成と同じ制限（読み取り専用相当、承認要求は全て拒否）で走り、使うエージェントの決まり方も同じ（[前述](#生成に使うエージェント)）
5. `agent.workflows.roadmapDir`（既定 `docs/roadmap`）へMarkdownとして保存される。フェーズごとのチェックリストに、項目間の依存と対応するIssue番号（分かれば）が入る
6. 人がレビューして直す（分解の誤りを一番安く直せる段）。直したら「ゴール文からYAMLを生成する」の「ロードマップから生成」でYAML化する（1フェーズだけでも、複数フェーズまとめてでも、全フェーズ一度にでもよい）

runが終わると、そのrunで `done` になったタスクに対応するロードマップの項目にチェックが入る（人が書いた文は書き換えない）。

### 確認を挟まずに走らせたい場合

既定では `bypassPermissions` のまま走らせることはできない（上記のとおり読み替えられる）。承認要求そのものが発行されない設定では、危険なコマンドを止める仕組みが一切残らないため。人が席を外していても進むようにしたいなら、まず**危険判定を残したまま自動承認する** `autoApprove` を使う。

1. User settings（`settings.json`）へ `"agent.workflows.allowAutoApprove": true` を書く。machineスコープなので、リポジトリ側の `.vscode/settings.json` からは有効にできない（cloneしただけのリポジトリが無人実行を勝手に有効化する経路を残さないため）
2. ワークフローYAMLの `defaults` へ `autoApprove: true` を書く（タスクごとに書かなくてよい）

なお、1を有効にしている環境では**生成（`agent.workflows.plan`）の時点で** `defaults.autoApprove: true` と各タスクの `allow: [shell-metacharacters]` を書いたYAMLを作る。無効な環境では従来どおり、どちらも書かないYAMLを作る。

```yaml
version: 1
name: 例
defaults:
  autoApprove: true
tasks:
  - id: T1
    prompt: ...
```

この状態での挙動:

- ファイルの編集は承認要求自体が出ない（`acceptEdits`）ので、そのまま進む
- 通常のコマンドは承認要求が出るが、自動で許可される
- **危険と判定したものだけ、そのタスクを止めて人へ回す**（ワークフローViewの「承認」で決める）

止まるのは次の場合（既定の停止条件。括弧内は `allow` で解除するときのid）。

- 作業ディレクトリ・worktreeの境界の外を触る（`outside-working-directory`）
- シェルメタ文字を含む、または複数のコマンドが連結されている（`shell-metacharacters`）
- 再帰的な強制削除、`rm -rf` 相当（`recursive-force-delete`）
- 追跡外ファイルの一括削除、`git clean` の強制実行（`untracked-clean`）
- 作業ツリーの強制巻き戻し（`worktree-reset`）
- ブランチまたはタグの削除（`branch-tag-delete`）
- `DROP TABLE` / `TRUNCATE`（`db-drop-truncate`）
- `find` の `-delete` / `-exec`（`find-delete-exec`）
- リモートへの強制push（`force-push`）
- デプロイまたはパッケージの公開（`deploy-publish`）
- 外部へ到達しうるコマンド、`curl` / `wget` / `nc` 系（`external-egress`）
- `base64` / `xxd` によるデコード（`decode`）

**`&&` や `|` を含むコマンドは `shell-metacharacters` に当たるため止まる。** ここも自動で通したいなら、そのタスクの `allow` に上のidを書いて個別に解除する。ただし `allow` を書いた分だけそのタスクの危険判定は働かなくなるので、タスクを分けてコマンドを単純にするほうが安全である（`.git` 配下への書き込みなど、`allow` でも解除できないものもある）。

#### 承認要求そのものを出さずに走らせる（非推奨）

`autoApprove` でも承認カードが出るのが困る場合の最後の手段として、`bypassPermissions` の読み替えを止める設定がある。User settings へ `"agent.workflows.allowClaudeBypassPermissions": true` を書き、`claude.permissionMode` を `bypassPermissions` にすると、ワークフローのClaudeタスクもその設定のまま走る。

**この設定を有効にすると、上に挙げた12の停止条件は全て無効になる。** Claude Code CLIがツール実行の可否を一切問い合わせなくなるため、この拡張機能側に判定の機会が無い。`rm -rf` 相当・force push・外部への送信・作業ディレクトリ外への操作を含め、ワークフローが生成したコマンドは内容にかかわらず実行される。使う場合は、失っても構わない環境（使い捨てのコンテナやVM）に限ること。

`agent.workflows.allowAutoApprove` と同じくmachineスコープで、リポジトリ側の設定からは有効にできない。

[並列オーケストレーション](#ワークフロー並列オーケストレーション)で使う設定。

| --------------------------------------- | ------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `agent.workflows.dir`                   | `.agents/workflows`             | resource            | ワークフロー定義ファイル（`.yaml` / `.yml`）を探すディレクトリ                                                                       |
| `agent.workflows.allowAutoApprove`      | `false`                         | machine             | YAMLの `autoApprove: true` を有効化できるようにする。**これが `false` のままだと、YAMLに何と書かれていても全ての承認要求を人へ回す** |

### machineスコープについて

実行するバイナリと権限に影響する設定は `machine` スコープに固定しており、リポジトリの `.vscode/settings.json` からは変更できない。これがないと、リポジトリをクローンして開いただけで任意のバイナリが起動され、CLIのサンドボックスも無効化されうる。

## 日報・週報連携

この拡張機能から実行したセッションを、**セッションごとに1行**だけ日報の追記バッファへ書き出す。

- 出力先: `~/workspace/dairy/.buffer/<YYYY-MM-DD>.jsonl`
- 形式: `{"ts","source","cwd","text","ref"}`（`source` は `codex` / `claude-code`、`ref` は `vscode`）
- 本文は1行要約200文字まで。会話本文そのものは書き出さない
- `agent.activityLog.enabled` を `false` にすれば一切書かない

`~/.claude/scripts/daily/collect.py` がこのバッファを読み、日報・週報の作業ログに載る。拡張機能経由のClaude Codeセッションは transcript 走査とも重複しうるため、収集側で1件に畳んでいる（設計書 §15.4）。

## トラブルシューティング

**「`codex` コマンドが見つかりません」と出る**
PATH上にCLIが無い。通知の「インストール手順」から導入するか、「設定を開く」で `codex.executablePath` / `claude.executablePath` に絶対パスを入れる。WSL Remoteの場合、Windows側にインストールしたCLIは見えない点に注意。

**リモート環境でCLIを入れてあるのに見つからない**
VSCodeが読むPATHはシェルの対話設定（`.bashrc` 等）を経ないことがある。`which codex` で得た絶対パスを設定に入れるのが確実。

**Claude Code画面で「ツール実行の承認を受け取れませんでした」と出る**
承認のやり取りに使うプロトコルが利用できない構成。会話自体は続き、以後は `claude.permissionMode` の設定に従う。確認なしで実行させたくない場合は `manual` を指定する。

**タブが復元されない**
チャット画面はVSCodeのWebview復元に任せているため、VSCodeがタブを復元しない設定になっていると戻らない。Codex画面とClaude Code画面のどちらも復元対象だが、Claude Codeのforkで作ったセッションだけは、CLIが振る新しいidを追えないため対象外になる。

**履歴に過去のセッションが出ない**
既定では現在のワークスペースのセッションだけを表示する。履歴ビューのタイトルバーで「全ワークスペースを表示」に切り替える。件数は `codex.history.maxEntries` で頭打ちになる。タイトルバーの絞り込みが有効なままだと該当セッションだけに絞られるので、「絞り込み中」の表示が出ていないか確認する（解除アイコンで戻せる）。

**履歴がグループ分けされて見づらい**
`codex.history.groupBy` を `none` にすると、以前と同じフラットな1リストに戻る。

**それでも原因が分からない**
コマンドパレットの `Agent: ログを表示`（出力チャネル `Agent Sessions`）に、起動した引数や失敗理由が出る。不具合報告にはこのログを添えてほしい。

## 既知の制約

- **チャット画面が依存するapp-serverはexperimental**: 将来のCLI更新で挙動が変わりうる。未知の通知とitem種別を素通しする設計で、変更時に機能が落ちても壊れないようにしている
- **中断した応答は復元されない**: 復元は会話履歴からの読み直しで、Codexは中断したターンに自分の発言しか残さない。リロードやresumeの後は、途中まで表示されていた応答が消える（app-serverへ直接問い合わせて確認）
- **中断してもコマンドの子プロセスは止まらない**: `turn/interrupt` はターンを終わらせるが、実行中だったコマンドはCLI側で走り続ける（実測。詳細は設計書 §9.6）。画面はそのコマンドに `中断後も継続中の可能性` の印を付け、会話へ注記を1行残す。実際に止めるにはターミナルでそのプロセスを終わらせる。中断の要求そのものが失敗したときは、応答中の見た目を解いたうえで「中断できませんでした」の注記を出す（ターンは続いている可能性がある）
- **復元したCodex画面の作業ディレクトリ**: 復元されたタブはcwdを持たないため、Codex側はワークスペース直下を充てる（Claude Code側はtranscriptから元のディレクトリを引く）
- **effortの反映は確かめられない**: Claude Codeにはeffort専用の制御要求が無く、唯一の経路が結果を返さない。送りはするが「変わった」とは言えないため、画面にもそう出している
- **Codexの一覧ではMCPサーバーの起動失敗理由が分からない**: 無効化されたサーバーと起動に失敗したサーバーが、`mcpServerStatus/list` の応答上は区別できない（実測。詳細は設計書 §14.14）。Claude Codeは `mcp_status` が理由をそのまま返す
- **Codexにはセッションの課金額を出す経路が無い**: `account/usage/read` は実在し呼べることを確認したが、返るのはトークン数・連続日数の統計のみで金額を含まない（実測。詳細は設計書 §14.17）。コスト表示はClaude Codeのみで、Codexは代わりに[セッション累計のトークン数](#セッション累計のトークン数)を出す（issue #294・設計書 §14.53）
- **ブラウザでのOAuthログインは拡張機能内で完結しない**: `codex login` / `claude auth login` はどちらも対話的なコマンドで、統合ターミナルへコマンドを入力するところまでしか案内できない（詳細は設計書 §14.16）。Claude Code側にはAPIキーでの非対話ログインの経路も無い
- **マルチルートワークスペース**: 既存の「新しい会話」（サイドバーの `+` / スパークル、`codex.newChat` / `claude.newChat`）はフォルダを1つだけ選ぶ（アクティブエディタが属するフォルダ、なければ先頭）。狙ったフォルダを毎回選びたい場合は[プリセットから新しい会話を開く](#プリセットから新しい会話を開く)を使う。プリセットに`workingDirectory`が無ければ開く前にQuickPickでフォルダを選べる（issue #295・design.md §14.56）
- **ウィンドウを跨いだ排他はしない**: 同一ウィンドウ内の二重オープンは防ぐが、別ウィンドウで同じセッションを開くことは止めない
- **CLIから直接archive/deleteした場合**: 履歴は追従するが、開いているタブは残る
- **ワークフローは実装・配線ともに完了しているが実機確認は途上**: 統合ブランチからのPR/MR自動作成、`agent.workflows.roadmap` によるゴール→ロードマップ→YAMLの2段階生成、`blocked` タスクのワークフローViewからの「再マージ」、タスク間メッセージング（MCPツール `list_tasks` / `send_message`）、gitリポジトリでないフォルダでの複製による隔離（疑似worktree）は、いずれも実行層（`runner.ts`）への配線を含めて実装済みで動く。ユニットテストとプロトコル上の実測までは済んでいるが、実VSCode上で通しで確認した記録はまだ無い。詳細は[docs/design.md](docs/design.md) §16.13を参照
- **Codexの履歴取得はthread/list優先**: app-serverに繋がっていれば `thread/list` を使い、繋がらない・応答が空のときはファイル読みへ退避する。退避したときは出力チャネル（`Agent: ログを表示`）に理由が残る（詳細は設計書 §4.0）
- **agent threadを切り替える経路が無い**: Codex app-serverのClientRequest 95メソッドを全数確認したが、「アクティブなagent threadを切り替える」に相当するものが無い（実測。詳細は設計書 §14.26）。サブエージェントの状況は会話内の項目として見えるが、そこへ「切り替える」操作は無い
- **検索（Ctrl+F）は折り畳んだ部分を拾わない**: コマンド出力・思考の要約の折りたたみ、`<details>` の中はDOM上非表示のため検索対象にならない。畳んでいる箇所を検索したい場合は開いてから検索する（詳細は設計書 §14.48）
