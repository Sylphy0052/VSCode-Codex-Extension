# 並列PRのマージ後は、main先頭のCIを確かめるまで完了と言わない

## 何が起きたか

#2055/#2056/#2057をsubagent 3本で並列に実装し、マージして「完了」と報告した。ユーザーに3回、「本当にこれで良いか」と指摘された。確かめ直すと次のことが分かった。

- main先頭のCIが `failure` だった。原因はTypecheckの2件 (`webGptDiscussionCommand.ts`)
- Typecheckで止まるため、Test以降が走らず、#2057が壊した既存テスト1件 (`claudeChatViewCoverage.test.ts`) が隠れていた
- 3本のsubagentは「tscの2件は既存エラー」と報告し、私は検証せずに繰り返した。実際に既存だったが、変更前のコミットのCIログで裏付けたのは指摘の後だった
- レビューagentの指摘には、存在しない行番号 (34行のファイルの `:217`) が混ざっていた
- 自己レビューは、各agentの差分の読み直しと、私が1ファイルを読んだだけで済ませ、規約が求める巡 (review系agentによる確認) を飛ばしてマージした

## なぜ

- 各subagentは自分のPR単体のテストしか回さない。同じファイルを触った別PRとの統合後の全テストは、誰も回さなかった
- CIが赤のまま続いていたため、「tscの失敗は既存」という報告を疑う理由が無いように見えた。赤が続くことは、新しい失敗が混ざっていない証拠にならない
- subagentの数値や行番号は、読んだ範囲の記憶から書かれる。実ファイルと突き合わせていない

## どうするか

- 並列PRをマージした後、「完了」と報告する前に `gh run list --branch main --workflow CI` でmain先頭のCI結論を見る。赤なら、失敗したstepのログを読む。Typecheckで止まっているときは、後続のstepが隠れていると考える
- 全ユニットテストは、統合後 (最後のPRをmainへ取り込んだ状態) で1回回す。個別のPRのテストだけで済ませない
- 2026-11-20からCIのworkflowは無効なので、上のCI結論の確認はできない。代わりに統合後のmainで`npm run typecheck`・`npm run lint`・`npm run format:check`と全テスト (`npx vitest run --maxWorkers=2`) を手元で回す。オーケストレータのrunで並列にmergeした後の後片付けでも同じ (2026-11-26のrunの18本では、後片付けの時点で回しておらず、翌日の最終チェックで回した)
- subagentが「既存」「無関係」と報告した失敗は、変更前のコミットのCIログか、変更前のcheckoutで再現してから採る
- レビューagentの指摘は、`file:line` を実ファイルで確かめてから直す。行が存在しなければ、その指摘は根拠を取り直す
- マージ前に、規約が求める自己レビューの巡を済ませる。省いたまま、マージ済みの後から埋めない
