# 引き継ぎの申し送りに書かれたIssueの状態は、ghで確かめてから使う

## 何が起きたか

2026-11-26のrunの後片付けを、コンテキスト残量の都合で新しいセッションへ引き継いだ。申し送りには「完了したIssue（#2171〜#2180、#2192〜#2195、#1998、#2187、#2188）がロードマップに残っているので外す」と書かれていた。

`gh issue list`で状態を取り直すと、#1998はOPENのままだった。PR #2182は待ち時間を据え置く理由をコメントに残しただけで`Closes`が無く、#1998は#2187のログが溜まるのを待つ状態だった。申し送りどおりに外していたら、OPENのIssueがロードマップから消えていた。

## なぜ

- 申し送りの「次にやること」は、引き継ぎ元のアシスタントが書いた要約で、事実を機械的に取ったものではない。ロードマップのチェック（`[x]`）を見て「完了」と判断した可能性がある（推測）。チェックの状態はIssueの状態と連動しない
- runは、タスクのPRがmergeされるとロードマップのチェックリストの行を`[x]`にする（`src/orchestrator/taskRunRoadmapFollower.ts`の`handleTaskMerged`）。一方、Issueを閉じるのはPRの`Closes`だけ。#1998のタスクは`Closes`の無いPR #2182でmergeされたため、行は`[x]`になったがIssueはOPENのまま残った

## どうするか

- 申し送りに書かれたIssueやPRの状態は、着手前に`gh issue list --state all --json number,state`などで取り直す。申し送りと食い違ったら、取り直した値を採る
- ロードマップから外すIssueは、チェックの有無ではなく、Issueの`state`が`CLOSED`かどうかで決める
- 申し送りの誤りに気づいたら、完了報告に「申し送りと違った点」として書く
