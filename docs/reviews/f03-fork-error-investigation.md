# F03追加調査:途中からの分岐エラー

調査日:2026-09-09。対象commit:`efd5cd67eb6a9b0a957538c9b5f981e2969875b6`。

利用者から「分岐は途中でやるとエラーになる」と報告された。プロバイダ、操作画面、エラー文は未取得のため、報告された事象の原因は未確定。コードとローカルCLIのAPI定義から、エラーにつながる条件と周辺の不具合3件を追加で記録した。いずれもP2、未修正・実行による再現未確認。

[F03の初回レビュー](f03-session-lifecycle.md)の6件とは別の指摘。F03は合計9件（P1:3件、P2:6件）。[機能別レビュー台帳へ戻る](../feature-inventory.md#f03)。

## 調査で分かった範囲

| 確認                   | 結果                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Codexの分岐要求        | チャット・会話閲覧とも`thread/fork`へ`threadId`と`lastTurnId`を送る                                                                           |
| 手元のCLI              | `codex --version`は`codex-cli 0.153.4`                                                                                                        |
| 現在のAPI定義          | `lastTurnId`は任意項目として存在する。指定ターンを含めて引き継ぐが、そのターンは実行中にできない。`beforeTurnId`も存在する                    |
| 保存済みターンIDの形式 | ローカルの直近30ファイルから読んだ444件の`turn_context.payload.turn_id`はすべてUUID形式。この標本ではIDの形式違反を確認できなかった           |
| エラーログ             | 利用可能なVSCode Serverのログを分岐エラー・要求名で検索したが、報告された操作と対応する記録は見つからなかった。ログが残っていない可能性はある |
| 再現操作               | 未実施。既存会話への送信・分岐・巻戻しは行っていない                                                                                          |

型定義は`codex app-server generate-ts --experimental --out .worktree/review-schema-20260909`で生成した。参照した`v2/ThreadForkParams.ts`の`lastTurnId`説明には`The referenced turn cannot be in progress.`とある。生成物はworktree内の無視対象に置いた。会話本文や生ログはこの文書へ転記していない。

CodeGraphで分岐の呼出関係を探索し、返却範囲にないUI・状態変換・制御処理は直接読んだ。ソースに記された過去のCLI実測と、今回確認した事実は区別している。

## 追加指摘

### F03-07[P2]:同じ進行中ターン内の追加指示を分岐点にすると拒否される

**条件:**Codexの応答中に待機中の指示を「今すぐ送る」などで割り込み送信し、同じターンに属する後続のユーザー発言で「ここから分岐」を押す。

[ChatSession.steer:372](../../src/appserver/chatSession.ts#L372)は現在の`turnId`を`expectedTurnId`として送る。[通知の取込](../../src/appserver/chatState.ts#L1328)もユーザー発言へ通知の`turnId`を付ける。一方、[chatScript.ts:1409](../../src/view/chatScript.ts#L1409)は「直前のユーザー発言」のIDを分岐点として使い、同じターン内か、完了済みかを区別しない。

その結果、同一ターン内の後続発言では、実行中のターン自身が`lastTurnId`になる。[forkFrom:2076](../../src/view/chatView.ts#L2076)はそのまま要求するため、CLIの「実行中ターンは指定できない」という条件に抵触する。これは報告されたエラーを説明できる候補だが、利用者がこの操作順だったことは未確認。

また、同じターンの完了後に要求が通っても、`lastTurnId`はターン全体を含める指定であり、表示上の「押した指示の手前」とは一致しない。通常の別ターン同士では、直前ターンの指定が誤りというわけではない。

F05の継続調査では、[sendQueued:444](../../src/appserver/chatSession.ts#L444)が通常応答中の予約を`steer()`へ渡す経路を確認した。「送る」「今すぐ送る」から上記条件へ進めることの補足であり、報告されたエラーの再現や原因確定ではない。[F05レビュー](f05-input-send-queue-interrupt.md)に送信・中断との競合を別途記録した。

**修正方針:**ユーザー発言単位とCLIターン単位を分けて扱う。完了済みの有効な境界だけを選び、同一ターン内の発言単位へ戻せない場合はその制約を表示する。`beforeTurnId`の採用も、対応CLIと必要な境界を確認して判断する。

**修正後の確認条件:**通常の複数ターン、進行中ターンへの割り込み、同一ターンに複数のユーザー発言がある場合を分ける。要求の境界と分岐先に含まれる会話を照合する。

### F03-08[P2]:再開したCodex会話でターンIDを落とし、途中分岐が表示されない

[readInitialItems:827](../../src/appserver/chatSession.ts#L827)は`thread.turns`を読むが、外側の`turn.id`を各項目へ付けない。[normalizeItem:771](../../src/appserver/chatState.ts#L771)は`turnId:undefined`で項目を作る。

これにより、再開応答から読み込んだ過去のユーザー発言にはターンIDがなく、[分岐点の計算](../../src/view/chatScript.ts#L1409)でも`previousTurnId`が埋まらない。[ボタン表示](../../src/view/chatScript.ts#L1351)は分岐点がなければ非表示になる。初回レビューではこの変換漏れを見落としていた。

この経路は「ボタンを押してエラー」とは別の事象であり、報告されたエラーそのものの原因とは扱わない。編集再送も同じ境界を利用するため、修正時はF09の動作を併せて確認する。

**修正方針:**再開応答の外側のターンIDを項目へ保持し、ライブ通知で作られた項目と同じ境界情報を渡す。

**修正後の確認条件:**複数ターンの会話を閉じて再開し、各発言のボタンと要求のIDを確認する。分岐先の再開、項目のないターン、IDの欠損も確認する。

### F03-09[P2]:分岐失敗後に同じボタンで再試行できない

[チャットのクリック処理](../../src/view/chatScript.ts#L399)は`fork.disabled=true`にする。状態の更新では分岐先と表示有無を更新するだけで、`disabled`を戻さない。[会話閲覧画面](../../src/view/conversationView.ts#L220)もクリック時に無効化し、ボタンの文言を「分岐しています…」に変えたまま、結果を受け取って復帰する処理がない。

CLIの一時エラー、Claudeの巻戻し失敗、開始失敗などを通知しても、元の画面の同じ分岐ボタンで再試行できない。再描画で同じDOMを使うチャットでも解消しない。エラーの初発原因とは別だが、失敗後の復旧を妨げる。

**修正方針:**分岐要求へ識別子を付けて完了・失敗をWebviewへ返し、失敗時には操作可能な状態へ戻す。処理中の重複実行の防止は維持する。

**修正後の確認条件:**CLI要求を一度失敗させ、その後に同じ発言から分岐できることを両プロバイダのチャットとCodex会話閲覧で確認する。

## Claudeの場合に追加で照合する点

ClaudeはCodexとは別の経路で、forkした新規プロセスへ`rewind_conversation`を最新発言から順に送る。[forkFromTurn.ts](../../src/claude/forkFromTurn.ts)では`rewound`を判定し、最初の失敗で停止する。単純に過去のUUIDを一度だけ送る実装ではない。

エラー文が「会話がその後に進んでいる」なら`stale target`、「分岐元の発言が見つからない」なら`target not found`に対応する。元会話から採ったUUID列と、新しくforkしたプロセスが読み込んだ履歴が一致しているかを調べる必要がある。[openForkFromTurn:973](../../src/view/claudeChatView.ts#L973)はプロセスを開始して巻戻し要求を送るが、CLI側の履歴読込時点と元会話の追加発言との整合は、この静的調査だけでは確定できない。

先頭発言の直前にアシスタント発言がない場合やCLI更新によるプロトコル差も、[既存設計書](../design.md#1461-会話の途中のターンから分岐claude-codeissue-333)に未確認点として残っている。過去のCLI2.1.235での記録を、現在の環境で再現済みとは扱わない。

## 原因確定に必要な情報

プロバイダ、チャットか会話閲覧か、エラー文、クリック時に応答中だったかを照合する。Codexなら分岐要求が失敗したのか、分岐成功後の`thread/resume`が失敗したのかも切り分ける。後者は[F03-02](f03-session-lifecycle.md#f03-02p1codexの復元分岐で元のcwdを保持しない)のcwd継承問題など、分岐要求以降の経路を追う。

今回の調査では実CLIによる会話の再現、テスト・型チェック・lintは行っていない。指摘の修正も未実施。
