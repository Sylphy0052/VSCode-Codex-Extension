# 設定の読取りと正規化

対象:`src/config.ts`、`test/unit/config.test.ts`。両ファイルの全文を読み、既定値、型の判定、範囲、設定保存先、警告の重複除け、各テストの入力と期待値を確認した。テスト未実行。

## 新規指摘

### EX-CONFIG-01・P1:権限設定が真偽値以外でも有効扱いになる

`src/config.ts:848`と849は`get<boolean>() ?? false`だけで、実行時の型を検証しない。設定読取りが文字列`"false"`を返すと、その文字列を保持する。`src/orchestrator/workflow.ts:1889`の`!allowAutoApprove`がfalseになり、YAMLの`autoApprove: true`を抑止しない。Claudeでも`src/orchestrator/taskConfig.ts:130`が真になり、継承した`bypassPermissions`を安全なモードへ変更しない。runner側の同じ真偽判定も防御にならない。

不正な型の設定値が返ることが発生条件。正常なbooleanのfalseでは起きない。machineスコープのため、これだけでリポジトリ側から設定を書き換えられるという指摘ではない。権限を有効にする値は`=== true`で限定すべき。VSCode実機で不正値の取込みは未検証。

`config.test.ts`は自動承認の既定値だけを検証する。draftPullRequestのテストには、JSON Schemaが型を担保するという前提を置いて不正型を試さない旨のコメントがある。数値設定では直接編集で不正値が入ることを前提に正規化しており、権限設定だけ防御が弱い。

## 関数・分岐

- 基本設定:文字列は型を確認し、数値は有限値まで確認する。履歴上限などの下限・整数化は一律には行わない。追加引数と書込み先は文字列要素を抽出する。既定provider、グループ方式、送信キー、composer、候補・要約はそれぞれの正規化へ渡す。
- 真偽値:通知、要約、ループ、自動再開などにも型引数とnull合体だけの経路がある。loopAdvisorの明示true判定などとは扱いが異なる。
- 補助AI:providerの既知値判定、モデル、空白指示の既定化、第二意見の10秒〜60分・advisor待機の1分〜4時間の丸めを確認。goal evaluator、goal draft、一部advisorの数値は有限値だけ、または下限だけで、workflowタイマーほど厳密な上限検証はない。実際の停止への影響は呼出先の丸めにも依存する。
- 設定更新:Globalへ保存する。workspace値が優先される場合に見かけ上戻る点は既存F04。連続更新の失敗はPromise経由で呼出元へ返る。
- workflowの保存先:空白だけ、絶対パス、両区切りの`..`セグメントを拒否する。シンボリックリンクを解決する境界検証ではなく、利用側の実体検証も必要。
- 疑似worktree除外:undefined/nullは無警告の既定。非配列、空配列、非文字列、空文字、gitセグメント、区切り、`.`/`..`は設定全体を既定へ戻す。trim後の値を格納する。警告は同文を抑止し、正常値で抑止状態を解除する。通知自体の失敗処理はない。
- workflow数値:秒数は有限・範囲内を確認して切捨て。回数とpoll間隔は整数を要求し、0を認める項目と認めない項目を区別する。各上限と既定値への復帰を確認。タイマーは2147483秒以下に制限する。
- workspace:アクティブ文書の所属が取れればそれを使い、取れない場合だけ先頭へ戻す。一覧は全フォルダーのfsPathを返す。

## テスト内容と不足

テストは保存先の通常値・絶対・親参照、除外設定の全体復帰・大文字git・区切り・空値・trim・警告重複・テスト間リセット、各workflow数値の既定・有効値・一部境界・範囲外・非整数、2種類の承認待ち設定の独立性を確認する。チャット設定では送信キー、composerの順序と未知値、要約・ループの保存往復、空の指示、evaluatorのprovider・数値差替え、通知の既定とboolean変更を確認する。

不足は真偽値設定の不正型、NaN/Infinityを含む全正規化の両境界、警告が正常値で解除された後の再警告、設定更新のreject・workspace上書き、基本Codex設定の全キー、workspace選択の各分岐。既定値とモジュール定数を比較するテストは外部仕様の値まで独立に保証するものではない。
