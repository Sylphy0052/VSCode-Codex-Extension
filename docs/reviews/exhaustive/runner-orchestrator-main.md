## 関数・分岐と契約

- MCP elicitationはサーバ名と末尾のtool名を照合し、限定集合を自動承認する。通常の危険操作の承認とは別経路。実行契約とタスク一覧はuntrusted区切りへ入れるが、導入文のrun名と復元質問はそのまま連結する。
- 警告履歴は追加・削除50件、差替えと依存変更はtaskIdごとの最新1件へ丸める。その他の警告まで全体上限を課す処理ではない。
- run終了、failureRecovery、レビューコメント待ち、最終マージ確定、人の停止を分ける。stopは停止方向なので人の停止中も許し、merge判断はorchestratorモードと理由・長さを要求、holdは停止中でも許す。program操作はprogramControlへ委譲し、このrun用ガードを通らない。
- retryのallow確認、continue、単件accept/decline、継続指示更新、pending契約更新、タスク追加・削除・依存変更を確認。変更は候補全体をvalidateWorkflowへ通した後に反映する。削除は後続のdependsOnも除き、残るテンプレート参照が不正なら全体を拒否する。updatePendingTaskの未知フィールドは単独なら変更なし、認めたフィールドとの混在では無視する。
- 継続指示更新はLiveTaskの存在だけを見るため、終了後もLiveTaskが残る場合の対象制限は状態では保証しない。定義変更の非永続性は警告に出す。削除失敗の案内はupdate_task_promptの制限を説明するが、現在はupdate_taskでpending本文を修正する道もある。
- ask_userはセッション、既存質問、空本文、本文長、選択肢数、回数上限を確認する。選択肢個別の型・長さはMCP入口へ依存。回答は整数添字と二重回答を防ぎ、busyなら保持してidleで送る。配送では質問・イベントを先に消すため、send失敗を検知・再送する契約は無い。
- setupはProviderと読取専用設定、接続URL、承認ハンドラ、画面open、状態購読、導入通知を組む。openTaskSessionのawait後に破棄を再確認せず、open後に状態購読する。途中例外のcatchは警告だけで、得たセッションのdisposeを行わない。runner側の寿命試験と合わせて残る出口を照合する。
- 応答要約の変化で未読数を増やし、busyの立下りで回答または蓄積イベントを送る。未読数は完了ターン数ではなく要約が変わった回数。旧セッションの通知をセッションIDで識別する処理は無い。
- イベント上限は受付時に数え、質問中・busy中はキューに溜める。上限到達後は終了・再開・人の停止通知も同じ入口で落ち得る。手入力は上限外で、保留イベントとまとめて送る。
- 状態差分からdone、失敗理由別、承認待ち、blockedを通知し、他状態は省く。blocked文言は衝突と表現するが、占有待ち停止等もこの状態になる。終了・再開・停止の説明と、再開後の旧MCP接続が復元されない仕様を確認した。

get_run_statusは本文フィールドを写さないが、警告には変更したprompt等の全文が含まれる場合がある。「本文を一切渡さない」と一般化はできない。既存のログ・プロンプト露出指摘と重複計上しない。
