### F11-01[P1]:Codexの失敗した完了通知を失敗なしと扱い、自動再開を予約しない

**条件:**上限到達で失敗したターンが、`turn/completed`の`turn.status:'failed'`として届く。制限通知側ではlimitedがtrueになっている。

[applyEvent](../../src/appserver/chatState.ts#L1282)はturn.statusとturn.errorを読まず、すべてのturn/completedで`turnFailed:false`へ戻す。[自動再開の予約](../../src/view/chatView.ts#L1057)はturnFailedを必須とするため、失敗した会話が対象から外れる。自動再試行の結果でも同じ完了通知なら、[再試行判定](../../src/view/chatView.ts#L1044)が予約を解除する。

前の調査でローカル生成したCodex CLI 0.153.4の`TurnCompletedNotification.ts`・`Turn.ts`・`TurnStatus.ts`では、完了通知がfailedを含む状態を運ぶ。`ServerNotification.ts`にturn/failedはない。実装は別のturn/failedだけを失敗へ変換し、[既存テスト](../../test/unit/chatState.test.ts#L347)もその形を固定している。接続層・画面側に完了通知をturn/failedへ読み替える処理は見つからない。

**修正方針:**完了通知のstatusとerrorからターン結果を確定する。上限による失敗、その他の失敗、手動中断を区別し、上限による停止だけを再開対象にする。

**修正後の確認条件:**同じturn/completedでcompleted・failed・interruptedを与え、上限失敗だけで予約が作られることを確認する。上限が続く再試行でも予約が解除されないことを確認する。実CLIの上限到達時の通知順序は未実測。

### F11-02[P1]:手動中断で消した再開予約が状態更新で復活する

**条件:**自動再開が有効でlimitedがtrueのClaude会話を、プロセスが生きている間に手動中断する。CodexでもturnFailedとlimitedが残った状態で予約を取り消した後、別の状態更新が来る場合が対象。

Claudeの[中断ハンドラー](../../src/view/claudeChatView.ts#L1986)はタイマーを消してからsession.interruptを呼ぶ。[interrupt](../../src/claude/streamSession.ts#L1004)はusageを残したままbusyをfalseへ更新するため、[onSessionChange](../../src/view/claudeChatView.ts#L1587)から再び予約判定へ入り、同じ操作中に予約が復活する。取消処理が保持するのはタイマーと待機フラグだけで、人が中断した事実を保持しない。

Codexの[取消](../../src/view/chatView.ts#L1022)にも中断済みの記録はない。両条件が残れば後続の使用量通知などで再予約される。タイマー発火時のガードも手動中断を確認しないため、時間が来ると継続指示を送れる。[設定の説明](../../package.json#L791)にある「手動で中断した場合は送信しない」と一致しない。

**修正方針:**停止対象のターンや再開待ちに対して、手動取消の状態を保持する。通常の通知では解除せず、次の明示送信や再開操作で解除する。

**修正後の確認条件:**上限待ちで中断し、その直後の状態更新・使用量更新・費用更新を挟んでも予約と自動送信が復活しないことを確認する。タイマーを消した直後だけの確認では不十分。

### F11-03[P2]:Claudeは失敗していない会話も制限フラグだけで自動続行する

**条件:**Claudeのlimitedがtrueのまま、ターンが成功する。または自動続行が成功して予約を解除した後、費用やコンテキストの応答が届く。途中でallowed通知が来ない場合に限る。

[scheduleLimitAutoResume](../../src/view/claudeChatView.ts#L1637)は通常の予約判定でturnFailedを見ない。[結果の反映](../../src/claude/streamJson.ts#L367)もusageは保持する。そのため完了済みの会話に再開予約を作れる。

自動続行の成功直後は一度取消へ進むが、その後の[get_usage応答](../../src/claude/streamSession.ts#L1217)などが再度onSessionChangeを呼ぶと、残ったlimitedから再予約する。成功した作業へ不要な継続指示を送る問題であり、手動中断の記録不足であるF11-02とは分けて修正する必要がある。

**修正方針:**上限で停止した未完了ターンを明示的に保持し、その再開だけを予約する。成功・手動中断・別目的の送信で再開対象を消し、古い使用量情報だけでは復活させない。

**修正後の確認条件:**limited=trueの後にsuccess、さらに費用・コンテキスト応答を与えても自動送信しないことを確認する。上限による失敗は引き続き再試行する。

### F11-04[P2]:Codexのsecondaryや別の制限枠を表示・再開判定に使わない

**条件:**primaryには余裕があるがsecondaryが100%に達する。または現在使うモデルの制限が別のlimitIdで管理される。

[APIからの読取り](../../src/codex/usage.ts#L28)と[ログからの読取り](../../src/codex/usage.ts#L74)はprimaryだけを採る。[チャットへの通知反映](../../src/appserver/chatState.ts#L1405)もprimaryの割合だけでlimitedを決める。primaryが20%、secondaryが100%なら画面は20%となり、チャットは上限未到達として扱う。F11-01を修正しても、この形では自動再開を予約できない。

CLI 0.153.4の生成済み型はprimary・secondaryに加え、取得応答のrateLimitsByLimitIdを持つ。実装は複数の制限枠の識別子を保持せず、通知は[全会話へ配る](../../src/view/chatView.ts#L2301)ため、モデルと制限枠の対応も判断できない。[既存テスト](../../test/unit/rateLimitsRead.test.ts#L4)ではsecondaryがnull。

**修正方針:**制限枠ごとの割合・リセット時刻・識別子を保持し、会話に適用される枠のどれかが上限なら検出する。再開時刻も、実際に阻害している枠を基準に決める。

**修正後の確認条件:**primaryのみ、secondaryのみ、両方の上限と、異なるlimitIdの通知を区別して確認する。枠の名前だけで週次・短時間を決め打ちしない。

### F11-05[P2]:共通の自動再開設定を変えても、他タブの予約を更新しない

**条件:**自動再開が無効の間に2つの会話が上限で止まり、片方のメニューから有効へ切り替える。その後、もう片方に新しい通知が来ない。

設定は[Globalへ書く共通値](../../src/config.ts#L377)だが、[Codex](../../src/view/chatView.ts#L1530)・[Claude](../../src/view/claudeChatView.ts#L2264)のハンドラーは操作したentryだけを予約・取消する。[設定変更の監視](../../src/extension.ts#L941)にもこの設定を全会話へ反映する処理がない。もう片方は有効になっても予約されず、次の状態通知まで止まったままになる。

無効への切替では他タブのタイマーと表示が直ちには消えない。ただし発火時には実効設定を読むため、無効のままなら送信は止まる。無効時にも送信すると断定するものではない。

**修正方針:**共通設定の変更を両マネージャーの全会話へ適用し、予約とメニュー表示を更新する。ワークスペースによる上書きも含め、書いた値ではなく実効値で判断する。

**修正後の確認条件:**Codex・Claudeをまたぐ2タブで切り替え、他方に通知を追加しなくても予約・取消が反映されることを確認する。[既存の切替テスト](../../test/unit/chatView.test.ts#L551)は生成HTMLのボタンとaria-pressedを確認している。

### F11-06[P2]:Claudeの割合取得が制限到達・リセット時刻の表示を上書きする

**条件:**rate_limit_eventで上限到達とリセット時刻を表示した後、別プロセスの/usage読取りに成功する。

[parseUsageReport](../../src/claude/usageText.ts#L40)は割合とラベルだけを返し、limitedとresetsAtはundefinedにする。[refreshUsage](../../src/view/claudeChatView.ts#L446)は既存情報へ統合せず、そのままステータスバーへ渡す。[updateClaude](../../src/view/usageStatusBar.ts#L42)が全文と背景を置き換えるため、到達の警告とリセット時刻が消える。

さらにセッションの行を優先するため、週次上限の通知後に「セッション16%」だけが残る場合がある。その後の会話更新ではstate.usageが再び渡り、割合表示のほうが消える。チャット内のusageと自動再開判定には/usageの結果を入れておらず、今回の指摘はステータスバーの情報喪失に限る。

**修正方針:**取得元ごとの情報を制限枠と時刻に対応付けて保持し、割合だけの取得で到達状態を消さない。異なる枠の数値とリセット時刻を混ぜない。

**修正後の確認条件:**週次のrejected通知とセッション割合の取得結果を両順序で与え、上限情報が失われず、取得順序だけで表示内容が欠落しないことを確認する。

### F11-07[P2]:Claudeのステータスバーの残り時間が通知停止中に進まない

**条件:**Claudeの制限通知で「2時間後」と表示された後、チャットを使わず2時間以上待つ。

[updateClaude](../../src/view/usageStatusBar.ts#L42)は呼ばれた時点の時刻で残り時間を文字列へ変換する。[定期描画](../../src/extension.ts#L882)はCodexのupdateだけを呼び、Claudeのスナップショットを再描画しない。新しい通知が来るまで「2時間後」のまま残る。

**修正方針:**Claudeの最新スナップショットも保持し、共通の定期描画で残り時間を更新する。時刻が過ぎたことと、実際に上限が解除されたことは分けて表示する。

**修正後の確認条件:**通知を追加せず時刻だけ進め、残り時間の表示が変わることを確認する。単体の[時刻整形テスト](../../test/unit/claudeUsageText.test.ts#L7)だけでは更新の呼出有無を検証できない。

### F11-08[P2]:最新ログに使用量がないと、他のログにある使用量も表示できない

**条件:**app-serverから使用量を取得できずログへフォールバックする。更新時刻が一番新しいログにはtoken_countがなく、別のログには有効な使用量がある。最新ログの末尾64KiBからイベントが押し出された場合も含む。

[UsageReader.read](../../src/session/usageReader.ts#L22)はmtimeが最大のファイルを1件だけ選ぶ。そこから使用量が読めなくても他の候補を試さずundefinedを返す。[呼出元](../../src/extension.ts#L875)はその結果で表示を更新するため、新しい会話を作っただけでも取得済みの使用量が「未取得」へ変わりうる。

ファイルの最終更新が最新でも、その中の使用量イベントが最新とは限らない。古い会話へ使用量以外の追記があった場合は、古い使用量を選ぶ経路も残る。

**修正方針:**読めない最新ファイルだけで探索を止めず、上限を設けて候補をたどる。有効な使用量イベントの取得時刻を比較し、古い値にはその時刻を明示する。

**修正後の確認条件:**最新ファイルはsession_metaのみ、2番目に有効な使用量という組合せで取得できることを確認する。[既存テスト](../../test/unit/usageReader.test.ts#L93)はtoken_countがないファイル1件の場合だけを扱う。

## 確認できた境界と残る確認

- CodexはAPI取得を優先し、失敗時にログへフォールバックする。ゲージ表示は設定で省略でき、75%以上で警告、90%以上で強調する。未取得と0%は区別する。リセット残り時間を再描画しても、使用率そのものを再取得したことにはならない。
- Codexのセッション累計はtokenUsage.total.totalTokens、コンテキスト量はlast.totalTokensを使う。圧縮でlastが減っても累計は別に保持する。Codexの金額を推定して表示する処理はない。
- Claudeの費用はget_usageのsession.total_cost_usdを使い、未取得を0へ置き換えない。サブスクリプションの場合はAPI料金換算の見積りと表示する。追加クレジットは同じ応答から読み、decimal_placesで金額の単位を変換する。フッターは有効状態・使用割合・無効理由を表示し、上限時の追加要求は確認ダイアログを経る。実際の請求・管理者通知・クレジット購入は操作していない。
- get_usageは同時に1件まで保留する。応答が来ない場合は次の取得を見送るため、接続が続いたまま応答だけ失われる条件での表示回復は未検証。古い値を残す場合の取得時刻は費用のツールチップで確認できる。
- 再開予定は通常リセット時刻の30秒後、時刻不明なら30分後。再開しても失敗と上限が残ると1分後へ再予約する。待機はメモリ内のタイマーであり、リロードをまたぐ復元機能ではない。ワークフロー自身の自動再開は別機能として後続レビューで扱う。
- タイマー発火時に破棄済み・パネルなし・設定無効・busy・承認待ち・質問待ちなら送信を見送る。teardownでもタイマーを取消する。承認待ちを解除した後は、その状態更新から再度予約判定へ入る。手動中断の抑止にはF11-02が残る。
- Codexの再開送信がRPCエラーになる場合にも[F05-01](f05-input-send-queue-interrupt.md)のbusy残留が及ぶ。再試行タイマーを作ってもbusyのガードで見送るため、既存指摘の修正対象へ含める。
- 上限判定とターン結果が別の通知で届くため、順序・古い通知・別モデルの通知との照合が必要。特にCodexは一般の接続失敗とアカウントの上限状態だけでも条件がそろいうる。F11-01の修正時に失敗理由を保持し、上限で止まった事実を判定する必要がある。
