### F06-01[P2]:相対パスのリンクを会話のcwdから開けない

**条件:**会話のcwdが`/work/project`で、応答中の`src/app.ts`などの相対リンクを押す。

[openChatFileLink:433](../../src/view/chatShared.ts#L433)は最初に`vscode.Uri.parse(url)`を呼び、`scheme==='file'`なら`fsPath`をそのまま使う。cwdを結合するのは`scheme===''`の分岐だけ。

VSCodeのURI実装は、非strictの解析でスキームが空なら`file`を補い、パスの先頭へ`/`を補う。このため上記の例は`/src/app.ts`を開く経路に入り、`/work/project/src/app.ts`にはならない。両プロバイダが同じヘルパーを使う。[公式URI実装](https://github.com/microsoft/vscode/blob/f09d623b525040809adb8abf4dcc70b228be07ba/src/vs/base/common/uri.ts#L55)と[APIへの公開箇所](https://github.com/microsoft/vscode/blob/f09d623b525040809adb8abf4dcc70b228be07ba/src/vs/workbench/api/common/extHost.api.impl.ts#L2155)を`gh api`で読んで照合した。

[公式API資料](https://code.visualstudio.com/api/references/vscode-api#Uri)も、非strictではスキームのない入力を互換性のため受け付けると説明する。上記の具体的な補完結果は公式ソースに基づく静的判断で、利用中のVSCodeでリンクを押して確認した結果ではない。

**修正方針:**生のリンク文字列から絶対URI・絶対パス・相対パスを区別し、相対パスをcwdへ結合してから`Uri.file()`へ渡す。フラグメントと末尾の行番号は分離して保持する。

**修正後の確認条件:**`src/app.ts`、`./src/app.ts#L12`、`../other.ts`、絶対パス、`file:`、HTTP(S)を両プロバイダで確認する。[既存テスト](../../test/unit/chatFileLinks.test.ts#L25)は`Uri.parse`を常に`file`を返すモックへ置き換えた絶対URIの1ケースで、相対パスの実挙動を確認していない。

### F06-02[P2]:画像読込中の送信で、画像が次の入力へ残る

**条件:**本文を書いた状態で画像を選択・貼付・ドロップし、FileReaderの読込完了前に送信する。

[offerFile:2303](../../src/view/chatScript.ts#L2303)は非同期で画像を読み、完了時に独立した`attach`要求を送る。読込中の件数や下書きとの対応を持たず、[send:3009](../../src/view/chatScript.ts#L3009)も読込完了を待たない。

先に`send`を受け取ると、ホストはその時点で登録済みの添付だけを送る。遅れて届いた画像は[Codex](../../src/view/chatView.ts#L1238)・[Claude](../../src/view/claudeChatView.ts#L1972)とも現在の添付欄へ追加する。この順序では画像なしの本文を送り、画像だけが次の入力へ残る。

**修正方針:**読込中の添付を下書きに関連付け、完了または明示的な取消までその下書きの送信を待つ。次の下書きへ遅れて追加しない。

**修正後の確認条件:**FileReaderの完了を遅延させて先に送信操作を行い、本文と画像が同じ送信に含まれることを確認する。複数画像の完了順が逆の場合、読込失敗、画像だけの送信も確認する。

### F06-03[P2]:画像の読込失敗が利用者へ通知されない

**条件:**選択・ドロップした画像の読込がFileReaderで失敗する。

[offerFile:2305](../../src/view/chatScript.ts#L2305)が設定するのは`onload`だけで、`onerror`・`onabort`の処理がない。[offerDropped:2325](../../src/view/chatScript.ts#L2325)も画像の読込を開始した時点で受取済みと判断して返る。その後に読み取れなくても`attach`も`dropRejected`も届かず、サムネイルも理由の通知も出ない。

ホスト側の[addAttachment](../../src/view/chatShared.ts#L77)はデータURLを受け取った後の検証結果だけを通知するため、読込失敗を補えない。

**修正方針:**FileReaderの失敗を固定の理由コードでホストへ伝え、読込中表示を解除する。取消を操作として設ける場合は、その取消と読込エラーを区別する。

**修正後の確認条件:**読込失敗イベントを発生させ、1回の通知と状態復帰を確認する。複数画像のうち1枚だけが失敗しても、成功した画像は保持する。

### F06-04[P2]:Codexの送信失敗時に戻した添付が枚数・合計サイズの上限を超える

**条件:**上限内の画像を付けてCodexへ送信し、要求の応答待ちに別の画像を追加する。その後、先の送信要求が失敗する。

[送信ハンドラー:1152](../../src/view/chatView.ts#L1152)は`take()`で添付欄を空にしてから要求を待つ。その間の画像追加は空いた欄に対して許可される。失敗時に呼ぶ[restore:207](../../src/provider/attachments.ts#L207)は、戻す画像と現在の画像を検証せず連結する。

例えば5枚を取り出した後に1枚を追加すれば、失敗後には6枚になる。合計10MiBの制約も同様に超えられる。`checkRoom()`は追加時だけの検証で、`take()`や送信データの組立てでは再判定しない。[既存テスト](../../test/unit/attachments.test.ts#L160)は取出しと復元の間に追加がないケースだけ。

**修正方針:**失敗分と編集中の添付を混ぜず回収するか、上限超過を明示して送信前に解消させる。画像を黙って捨てない。復元後の表示も更新する。

**修正後の確認条件:**応答を保留し、追加後に送信を失敗させる。枚数・合計サイズそれぞれの境界で、画像保持と再送時の上限を確認する。Claudeの通常送信は同期処理のため、同じ待機時間を前提とした不具合とは扱わない。

### F06-05[P2]:同じパスの画像更新や読込失敗からの回復を表示へ反映できない

**条件:**同じ会話で画像ファイルを同じパスへ上書きして再度表示する。または、最初の画像読込失敗後にそのパスの画像が読めるようになる。

[imageDataとimageAsked](../../src/view/chatScript.ts#L1002)はパスだけをキーにし、一度要求したパスを再要求しない。新しい会話項目でも、[createImage:1013](../../src/view/chatScript.ts#L1013)は同じパスのキャッシュを使う。成功した古い画像も、失敗理由も、Webviewが存続する間は更新・再試行する経路がない。

[CodexのimageView・imageGeneration](../../src/appserver/chatState.ts#L869)はファイルパスからこの経路へ入る。例えば`shot.png`を撮り直しても、新しい項目に前のスクリーンショットが出る。直接データURLを持つ画像はこの指摘の対象外。

**修正方針:**会話項目や画像の世代を区別してキャッシュし、失敗時の再試行を設ける。過去の表示を保持する場合も、新しい項目の読込を古いキャッシュで省略しない。

**修正後の確認条件:**同じパスへ内容の異なる画像を保存して別項目で表示し、新しい内容になることを確認する。失敗後の再試行と、異なるパスのキャッシュ利用も確認する。

### F06-06[P2]:ルート限定のディレクトリ除外が下位の同名ディレクトリにも適用される

**条件:**ルートの`.gitignore`に`/reports/`を書き、除外対象外の`src/reports/view.ts`も存在する。

[parseGitignore:112](../../src/provider/fileMentions.ts#L112)は先頭`/`を認識するが、単純なディレクトリ名なら[118行目以降](../../src/provider/fileMentions.ts#L118)で`rooted`を使わず`dirNames`へ入れる。[走査](../../src/session/nodeFileScan.ts#L31)は名前だけで全階層を除外するため、`src/reports/`にも入らず候補から消す。

否定パターンや階層ごとの`.gitignore`を扱わないという既存の制約とは別に、単純なルート限定指定の範囲を広げてしまう。ファイルに対するルート限定は既存テストにあるが、ディレクトリの適用範囲は確認されていない。

**修正方針:**ルート限定指定をパスの条件として保持する。名前だけで走査を止める最適化を使う場合も、対象階層を確認する。

**修正後の確認条件:**`/reports/`と`reports/`を分け、ルートと下位の同名ディレクトリで候補と走査対象を照合する。

### F06-07[P2]:ファイル候補の初回・期限切れ走査を入力ごとに重複実行する

**条件:**ファイル走査が終わる前に`@`の検索語を続けて入力する。初回、または5秒のキャッシュ期限切れ後に起こる。

[入力イベント](../../src/view/chatScript.ts#L3385)は語が変わるごとに`requestFiles`を送る。[FileMentionCatalog.list:213](../../src/provider/fileMentions.ts#L213)は完了済みのキャッシュだけを確認し、実行中のPromiseを共有しない。最初の走査が終わるまでの要求はそれぞれ`.gitignore`の読込と再帰走査へ進む。

1走査には20,000件の上限があるが、同時走査の本数は制限されない。大きい・遅いディレクトリで文字数に応じて同じ読込を重ね、候補表示をさらに遅らせる要因になる。遅延時間や資源使用量は未計測。[既存テスト](../../test/unit/fileMentions.test.ts#L174)は前回の完了後に次を呼ぶため、この競合を確認していない。

**修正方針:**同じcwdの走査中Promiseを共有し、完了後に各要求の語で絞り込む。失敗後の再試行と異なるcwdの独立性を保つ。

**修正後の確認条件:**走査を保留した状態で同じcwdへ複数要求し、走査が1回で各検索語の結果が返ることを確認する。異なるcwd、失敗後、期限切れ後も確認する。

## 確認した制約と保護

- 添付は1枚5MiB、合計10MiB、最大5枚。画像のデータURLまたはbase64ブロックとしてCLIへ渡す。ファイル選択・貼付・ドロップは共通の受信処理を使う。形式判定は宣言されたMIMEを基準とし、画像の実データを復号して形式を照合する実装ではない。
- ローカル画像の読込要求は会話の画像パスと一致するものだけを通し、拡張子を確認する。Node側は通常ファイルかと読込前の10MiB上限を確認する。読込前後にファイルが変化する場合の上限保持は未確認。
- `@`走査はシンボリックリンクを辿らない。否定・下位の`.gitignore`等の非対応、走査20,000件・表示50件の打切りは既存の制約として扱う。パターンによる除外は走査件数の上限適用後なので、巨大な除外対象が候補枠を消費する場合もある。
- ファイル候補の応答は現在の検索語と一致する場合だけ表示する。IMEと補完キーの競合は[F05-07](f05-input-send-queue-interrupt.md)を参照する。
- 外部リンクは[HTTP(S)だけ](../../src/appserver/chatState.ts#L973)を`openExternal`へ渡す。`command:`等をその経路で開く実装はない。ローカルファイルのエディタ表示はワークスペース外も許可する既存仕様で、画像データをWebviewへ返す経路とは別。
