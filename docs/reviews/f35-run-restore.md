## 指摘

### F35-01[P1]:返信待ちのタスクがリロード後に再開対象から外れる

[リロード時の補正](../../src/orchestrator/runStore.ts#L116)はrunningとwaitingApprovalをreloadInterruptedへ変えるが、waitingReplyを残す。一方、[復元する実行中タスクのMap](../../src/orchestrator/runnerRestore.ts#L406)は空で、返信を受け取るセッションやメッセージングをその状態から復元しない。[自動再開対象](../../src/orchestrator/runState.ts#L1085)はreloadInterruptedのfailedタスクである。

返信待ちの最中にリロードすると、保存状態だけが待機中に残り、受信・再開経路が失われる。返信待ちも中断状態へ正規化するか、待機先と受信処理を復元する必要がある。

確認例:waitingReplyだけが残るrunをリロードし、受信または再試行で先へ進めることを確認する。未実行。

### F35-02[P2]:完了した依存タスクの成果が復元されず、後続の入力が空になる

[保存対象](../../src/orchestrator/runner.ts#L4877)にはタスク状態やセッションIDなどが入るが、TaskResultは入らない。[復元](../../src/orchestrator/runnerRestore.ts#L406)でも完了タスクの結果を再構成しない。[依存成果の取得](../../src/orchestrator/runner.ts#L3795)は実行中Mapのresultを参照し、[テンプレート展開](../../src/orchestrator/workflow.ts#L1847)では結果がない参照を空文字へ変える。

先行タスク完了後にリロードすると、後続を再開できても成果・変更ファイル等の参照が欠落する。後続が必要とする結果を永続化するか、成果の再取得を再開条件にする必要がある。

確認例:A完了・B実行中でリロードし、B再試行時のAの成果参照がリロード前と一致することを確認する。未実行。
