### F07-01[P2]:Codexで無効化したスキルがファイル走査から候補へ戻る

**条件:**`<codexHome>/skills/example/SKILL.md`など走査対象のスキルがあり、`skills/list`がそのスキルを`enabled:false`として返す。

[readSkillsList](../../src/codex/skillsList.ts#L29)は無効なスキルを配列から除く。一方、[CommandCatalog](../../src/provider/commandCatalog.ts#L34)は設定上の有効・無効を読まず、同じファイルを候補に含める。[loadCommands](../../src/view/chatView.ts#L2266)から呼ぶ[mergeCommands](../../src/view/chatView.ts#L2453)はファイル由来の候補を土台にAPIの候補を追加・置換するだけで、無効な名前を削除しない。このためAPIが取得できても、無効なスキルが候補に残る。

**修正方針:**APIから得た有効・無効とスキルの識別情報を統合時まで保持する。取得成功時は無効なスキルを除き、APIが扱わないカスタムプロンプト等の候補とは区別する。

**修正後の確認条件:**同じスキルをファイルとAPIの両方に置き、無効化時に候補から消えることを確認する。API失敗時の代替候補も確認する。[既存テスト](../../test/unit/skillsList.test.ts#L31)はAPI応答の解析単体で、ファイル由来との再統合を確認していない。

### F07-02[P2]:Codexのスキル一覧要求が`cwds`ではなく`cwd`を送る

**条件:**会話の作業場所に固有のスキルがあり、その場所を指定して一覧を取得したい。

[loadCommands:2270](../../src/view/chatView.ts#L2270)は`skills/list`へ`{cwd:...}`を送る。しかし、[分岐調査](f03-fork-error-investigation.md)で手元のCodex CLI 0.153.4から生成した`v2/SkillsListParams.ts`の定義は次のとおり。

```ts
export type SkillsListParams = {
  cwds?: Array<string>;
  forceReload?: boolean;
};
```

`cwds`が空の場合は既定の作業場所を使うと型定義に記載されている。要求は公開された引数名と一致せず、意図した場所を指定できていない。未知の`cwd`が無視されるか要求が拒否されるかは、今回実CLIで確認していない。拒否時はファイル候補へ退避するため、接続自体の障害とも区別しにくい。

さらに、このメソッドは会話の`entry.cwd`を受け取らず、[候補キャッシュ](../../src/view/chatView.ts#L2232)もマネージャー全体で共有する。引数名だけを直しても、作業場所が異なる会話の候補を分離できない。

**修正方針:**会話のcwdを`cwds:[cwd]`として渡し、候補とキャッシュをcwdに対応付ける。ファイル走査側もその会話で使える範囲と合わせる。

**修正後の確認条件:**異なる2つのcwdで要求内容と候補を確認する。片方にだけあるスキル、ワークスペース外の会話、一覧取得失敗時も対象とする。型定義の生成物は無視対象の`.worktree/review-schema-20260909/`にあり、配布文書のリンク先にはしていない。

### F07-03[P2]:コロンを含むコマンド名を入力すると補完候補が閉じる

**条件:**Claudeで`genshijin:genshijin`のようなプラグイン由来のコマンドを、名前を途中まで打って絞り込む。

[CLI候補の解析](../../src/claude/control.ts#L134)はコロンを含む名前を受け付け、[既存テスト](../../test/unit/claudeControl.test.ts#L370)もその形式を使う。しかし、Webviewの[commandQuery](../../src/view/chatScript.ts#L2836)は`/^\/([\w-]*)$/`で判定するため、`/genshijin:`まで入力すると候補取得の対象外になる。

コロンを打つ前に候補を選ぶ操作や、完全な名前を手入力して送信する操作は可能。問題は名前空間以降を打って候補を絞り込めないこと。

**修正方針:**CLIの候補に存在する名前形式を補完の判定でも扱う。空白・行境界による補完の終了条件は保持する。

**修正後の確認条件:**`/genshijin`、`/genshijin:`、`/genshijin:g`の各段階で同じ候補を選択できること、確定後の引数ヒントも表示されることを確認する。純粋関数の絞込だけでなくWebviewの入力判定を対象にする。

### F07-04[P2]:ClaudeのCLI由来候補が遅れて完了したファイル走査で上書きされる

**条件:**画面準備時にCLI候補が未着でファイル走査が始まり、走査の完了より先に`initialize`の候補が届く。

[postCommands](../../src/view/claudeChatView.ts#L485)は呼出時の`entry.session.commands`を読み、空ならファイル走査を待つ。その間にCLIから候補が届くと、[setCommands](../../src/claude/streamSession.ts#L1335)と[通知コールバック](../../src/view/claudeChatView.ts#L1384)が別の`postCommands`を呼び、正規の候補を先に送る。

古い呼出しは待機後にCLI候補を読み直さず、ファイル由来の候補を送る。Webviewは[最後に届いた配列で置換](../../src/view/chatScript.ts#L3529)するため、組込・プラグインの候補が消え、次の通知等まで戻らない。

関連して、CLIから正常に空配列が届いた場合も`length>0`の判定でファイル候補へ退避する。[解析処理](../../src/claude/control.ts#L134)が区別している「未取得」と「取得済みの空一覧」を表示側で失っている。

**修正方針:**CLI候補の取得済み状態と世代を保持し、走査完了時に再判定する。取得済みの空一覧も正規の結果として扱い、古い代替候補を送らない。

**修正後の確認条件:**ファイル走査を保留し、その間にCLIの候補通知を先に完了させても候補が戻らないことを確認する。空一覧への更新と、走査中に画面を閉じた場合も確認する。

### F07-05[P2]:特殊入力の確認を取り消しても、消去済みの本文が戻らない

**条件:**Claudeで`# 長いメモ`を送り、追記先選択または追記確認を取り消す。`!`の確認、Codexの`/compact`や既存ファイルに対する`/init`の確認でも同じ経路になる。

Webviewの[send](../../src/view/chatScript.ts#L3009)はホストの受付前に入力欄と下書き履歴を空にする。[追記先選択・確認](../../src/view/claudeChatView.ts#L2534)、[シェル入力確認](../../src/view/claudeChatView.ts#L2511)、[圧縮確認](../../src/view/chatView.ts#L1614)、[生成確認](../../src/view/chatView.ts#L1784)は取消時に戻るだけで、元の入力を返さない。CLIにも通常の発言として送らないため、会話の発言履歴からも回収できない。

**修正方針:**特殊入力の受付・完了・取消を下書きに対応付ける。取消時は元の本文を回収できるようにし、待機中に書いた新しい本文を上書きしない。

**修正後の確認条件:**各確認段階で取り消し、元の本文と新しい下書きが保持されることを確認する。[F05-01/F05-06](f05-input-send-queue-interrupt.md)の通常送信失敗・キュー復元とは別の、確認取消の経路として扱う。

### F07-06[P2]:シェル入力用ターミナルの再利用で別会話の作業場所・未実行入力を引き継ぐ

**条件:**cwdが`/work/a`の会話で`!pwd`をターミナルへ入力した後、cwdが`/work/b`の別会話からシェル入力を行う。

[openShellCommandTerminal](../../src/view/claudeChatView.ts#L273)は固定名の既存ターミナルを探す。`cwd`を使うのは新規作成時だけで、再利用時に場所を合わせる処理はない。そのため別会話の入力も、先のターミナルの作業場所へ送られる。利用者がターミナルで移動した場合も同じ。

また、`sendText(command,false)`は改行なしで入力する。先のコマンドを未実行のまま再度入力すれば、入力を消す・置換する処理がなく、同じ入力行へ追加される。例えば`pwd`の後に`ls`を入力すると、シェルの通常の入力状態では`pwdls`になりうる。実際のターミナルでの再現は未確認。

**修正方針:**会話のcwdで新しい入力用ターミナルを開くなど、作業場所と空の入力状態を確保する。再利用する設計なら、現在の状態を利用者が確認できる導線を設ける。

**修正後の確認条件:**異なるcwd、利用者による`cd`後、前回の入力が未実行の状態で確認する。入力時に自動実行せず、利用者のEnterを待つ挙動を維持する。

### F07-07[P2]:メモリ追記の読込・全体書込の間に入った更新を失う

**条件:**`#`による追記処理が既存のCLAUDE.mdを読んだ後、書き込む前に別の追記やエディタ保存が同じファイルを更新する。

[runMemoryInputMode:2568](../../src/view/claudeChatView.ts#L2568)は`readStrict()`で全体を読み、`appendMemoryLine()`で文字列を作り、`workspace.fs.writeFile()`で全体を書き直す。ファイル単位の直列化や内容の世代確認はない。

例えば2つの追記が同じ本文を読み、順に「本文+A」「本文+B」を書くと、最後の結果からAが消える。両方の書込が成功すれば成功通知も両方に残る。書込前のシンボリックリンク確認は参照先の変化を確認するもので、通常ファイルの内容更新を検出しない。

**修正方針:**全体の読込・上書きに依存しない追記方法を検討する。拡張機能内の同じ実体ファイルへの操作を直列化し、外部編集との競合時にも既存の更新を消さない仕組みを選ぶ。

**修正後の確認条件:**2つの読込が同じ内容を得る順序を作り、追記が両方残ることを確認する。読込後の外部保存、同じ実体への別パス、新規ファイルへの同時追記も対象にする。[既存のファイルシステムテスト](../../test/unit/nodeMemoryFileSystem.test.ts#L32)は読込エラーとリンク解決を扱い、追記全体の競合は確認していない。

### F07-08[P2]:Codex API由来候補の統合でファイルの引数ヒントが消える

**条件:**SKILL.mdに`argument-hint`があり、同じ名前のスキルがCodexのAPI一覧にも含まれる。

[parseCommandFile](../../src/provider/slashCommands.ts#L54)はファイルの引数ヒントを保持するが、[readSkillsList](../../src/codex/skillsList.ts#L34)は常に`argumentHint:''`の候補を作る。[mergeCommands](../../src/view/chatView.ts#L2455)は説明だけでなく候補オブジェクト全体をAPI側で置換する。このため正常にAPI一覧を取得できた場合だけ、ファイルから読めていた引数ヒントが失われる。

**修正方針:**APIが返す説明等を優先しつつ、提供されない引数ヒントは対応するファイル由来の値を保持する。同名の別スキルを混ぜないよう、パス・スコープも確認する。

**修正後の確認条件:**ファイルに`argument-hint:<対象>`を持つスキルをAPI候補と統合し、候補一覧と確定後の両方でヒントが残ることを確認する。現在の[引数ヒントのテスト](../../test/unit/argumentHint.test.ts#L15)は統合後の候補生成を扱っていない。

## 確認できた境界と残る確認

- 擬似コマンドは同名のCLI・ファイル候補より優先する。前後の空白を除いた後に本文が複数行なら、擬似コマンドや`!`・`#`の特殊処理へ振り分けない。
- Codexの`/init`は既存AGENTS.mdを読めた場合に更新確認を挟み、モデルへ固定の指示文を送る。拡張機能が直接AGENTS.mdを書き換える機能ではなく、モデルによる既存内容の保持は今回確認していない。共有の`readTextFile()`は読込失敗を`undefined`へまとめるため、読めない既存ファイルではこの確認に入らない制約も残る。
- Claudeの`!`は確認後にターミナルへ入力するだけで、Enterを付けない。`#`は列挙した追記先から選び、確認後に読む。ENOENT以外の読込失敗は中止し、確認前後でリンク判別結果が変わった場合も中止する。
- `#`のプロジェクト候補は各ワークスペースルートと会話のcwd。ルート直下のCLAUDE.mdを優先し、`.claude/CLAUDE.md`だけがある場合はそちらを使う。ユーザーのCLAUDE.mdも候補に加え、前回選択先を先頭へ移す。
- 要約指示を有効にすると、擬似コマンド・特殊入力以外の本文末尾へ指示を足す。CLIへ送る通常のスラッシュコマンドも対象で、CLIによる引数解釈への影響は未確認。候補キャッシュの動的更新はF17でも確認する。

## 検証の限界

CodeGraphは有効で、候補統合・メモリ追記・シェル入力・AGENTS.md生成指示の呼出関係とソースを取得した。返却範囲外のWebviewやCLI応答処理は直接読んだ。`commandCatalog`・`slashCommands`・`pseudoCommands`・`inputModes`・`argumentHint`・`skillsList`・`claudeControl`・`nodeMemoryFileSystem`の関連テストを参照した。

テスト・型チェック・lint、実VSCodeでの候補選択・確認取消・ターミナル入力・メモリ追記、実CLIへのコマンド送信は未実施。API引数の照合には以前生成した手元のCLI型定義を使用し、外部サービスを操作していない。途中分岐エラーの原因を確定する新たな証拠も得ていない。

変更はレビュー文書と台帳のみ。次の対象はF08（チャット描画・操作性・状態同期）。
