# オーケストレーション実行の精度

H1〜H7。
[review-and-feature-consolidation.md](review-and-feature-consolidation.md)
の **WF-H（第4波）** が担当する。

## きっかけ

2026-08-21〜23に、7つのワークフローを**人手の並列オーケストレーションで回した**
（WF-A / WF-A2 / WF-B / WF-C / WF-D / WF-F の完了と、WF-E 第1波の着地まで）。
構造は次のとおりで、拡張機能のワークフロー実行と同じ形をしている。

- ユーザー → 全体オーケストレーター → 各ワークフローの担当 → 実装セッション（並列）
- 判断は上へ、作業は下へ。担当は自分で手を動かさず、実装は別セッションへ委譲する
- 成果はワークフローごとの統合ブランチへ集め、mainへのマージだけ人が判断する

この実運用で観測した壊れ方のうち、**W1〜W12 のどれにも道具が無い、または道具はあるが
起動条件が定義されていない**ものを集めたのが本ドキュメントである。

W1〜W12は「ワークフローに何ができるか」を埋める項目群であり、ほぼ埋まる見込みが立っている。
本ドキュメントが扱うのは**「実行の結果が正しいことを機械で確かめる層」**で、この層は現状まるごと無い。
人手で回したときは、その役目を全体オーケストレーター（人間側のセッション）が
検算・数え直し・実測で担っていた。拡張機能のオーケストレーターは**受け取った報告をそのまま次へ渡す**。

## 方針

1. **タスクの自己申告を完了条件にしない。** 報告の文面ではなく、オーケストレーターが
   実行して得た観測値で判定する
2. **静的に決まるものは事前配布し、動的に決まるものは事前宣言しない。** 識別子（節番号・
   ケース記号・ブランチ名）の事前配布は実運用で4項目とも衝突ゼロで機能した。一方、
   触るファイルの事前宣言は3回連続で外れた
3. **衝突のコストを実行後ではなく実行中に払う。** 交差は統合の段で初めて表面化するのではなく、
   走っている最中に測って並列度を下げる
4. **人手で回したときにオーケストレーターが担っていた仕事を、機能として置く。**
   本ドキュメントの項目はすべてこの形で選んである

## H1 タスクの完了報告を検算する

- 依存: なし
- Issue: 未起票（着手時に起票する）
- 現状: タスクの完了は、タスク自身が返す文面で判定される。オーケストレーターは
  **何を実行しての完了なのかを知らない**
- やること
  - タスクの定義に**検証コマンドを持たせ、オーケストレーターが実行して終了コードと出力を
    記録する**。完了判定はこの観測値で行い、文面では行わない
  - タスクが「テストを追加した」と報告した場合、**変更前のコードへ核となる一箇所だけを戻して
    落ちること**を確かめる段を置く。戻す範囲はタスク自身に指定させる
  - 「変化した」という主張（性能が上がった・違反が増えた・件数が減った）を含む報告は、
    **ベース側の測定値を添えることを必須にする**
- 根拠となった実測
  - **「全pass」の意味が実行コマンドで変わる。** W11（Issue #560）の担当が「全pass」と
    報告した状態で統合テストが2件落ちていた（78 passing / 2 failing、ベースは
    80 passing / 0 failing）。`npm test` は vitest のユニットのみで統合テストを含まない。
    **担当は嘘をついておらず、報告の意味が実行したコマンドによって変わる**
  - **テストが何も検証していない事例が3件。** (a) Issue #484 の対策に付いていたテスト3件は、
    差し替えの位置が事後確認の呼び出し直後にあったため、循環した旧実装へ戻しても通った。
    (b) Issue #443 の「呼び出し順序に意味がある」テストは、本番コードの2行を逆転させても
    1件も落ちなかった（テストコード側で明示的にその順に呼んでいた）。
    (c) W11の停止の回帰テストは、入口ガードと `isCancelled` の**2重の防御に守られて
    何も検知しない**状態だった
  - **レビューの指摘自体が仮説でしかない。** W1に対して「prettier違反を7ファイルへ入れた」
    という指摘が出たが、ベース `ab819844` を測ると10ファイルとも元から非準拠だった。
    変化の主張はベース側を測らないと成立しない
- 影響の見込み: タスク定義（検証コマンド）・runner の完了判定・ワークフローViewの完了表示

## H2 実行中のファイル交差を実測し、並列度を下げる

- 依存: なし（H4と同じ監視ループに載る）
- Issue: 未起票（着手時に起票する）
- 現状: 並列に走らせるかどうかは、ワークフロー生成時に宣言されたファイル集合で決まる。
  **走り始めた後に交差が分かっても、並列度を下げる経路が無い**
- やること
  - 各タスクの作業ツリーを定期的に `git diff --name-only` / `git status --porcelain` で測り、
    **実際に触っているファイルの集合を持つ**
  - 交差が出た時点で、後発のタスクを待機させる（または先発の完了を待ってから再開する）
  - 宣言されたファイル集合は**初期の並べ替えにだけ使い、交差の判定には使わない**
- 根拠となった実測
  - **事前宣言は3回連続で外れた。** (a) W3（Issue #337 / PR #548）は影響欄の
    `workflowView.ts` を1行も触らず、真の交差は `runner.ts` と `extension.ts` だった。
    (b) W2（Issue #336 / PR #573）は影響欄5ファイルに対し実際は22ファイルで、交差した
    `orchestratorSession.ts` は欄に無い。W2とW7の交差は、着手直後の実測では2ファイル
    だったが、着地時には5ファイルへ増えていた（`docs/design.md` / `docs/manual-test.md` /
    `test/unit/runner.test.ts` が後から加わった）。**交差は一度測れば済むものではない。**(c) W9とW11はどちらも
    `test/integration/helpers/workflow.ts` を触り、統合ブランチ上で衝突した
  - **一方、識別子の事前配布は機能した。** 節番号・ケース記号・ブランチ名は第1波の4項目とも
    衝突ゼロで、着手時の実測でも表の修正が不要だった。**静的に決まるものと動的に決まるものを
    同じ「定義」として扱っているのが誤り**である
  - **衝突のコストを実行後に払っている。** 交差は統合ブランチへ入れる段で初めて表面化した。
    走行中に分かっていれば片方を待たせるだけで済んだ
- 影響の見込み: scheduler・runner・ワークフローViewの並列表示

## H3 指示への応答に「解消されなかった残り」を持たせる

- 依存: W7（タスクからオーケストレーターへ判断を仰ぐ経路）・W8（ユーザーへ確認する経路）
- Issue: 未起票（着手時に起票する）
- 現状: オーケストレーターからタスクへの指示に対する応答は自由文であり、
  **指示に従った結果しか返ってこない**
- やること
  - 指示への応答に「**この指示で解消されなかった残り**」の欄を持たせ、
    無いなら「無い」と明示させる
  - 報告に含める数の単位を定義側で固定する（何を1件と数えるか）
- 根拠となった実測
  - **従った側は「解決した」形の報告を返しやすい。** WF-E の担当は、並列3→2の指示を受けた
    時点で `workflowView.ts` の交差が残ることを認識していながら報告に書かなかった（自己申告）。
    **指示を出した側は、自分の指示の穴を知る機会を失う**
  - **指示を出した側も同じ穴を踏んでいた。** 全体オーケストレーターは `runner.ts` の交差だけを
    見てW9を外し、W1×W3 の `workflowView.ts` を見落としていた。**上位が正しい前提は
    成立しない**
  - **数え方が報告者ごとに違う。** 同じ「N組」という語が、W-Pでは操作9・期待9、
    W-Nでは操作5・確認3・期待6を指していた。集計側が数え直すまで食い違いが出ない
- 影響の見込み: `send_message` の応答スキーマ・W7/W8の要求スキーマ・ワークフローViewの表示

## H4 タスク粒度を実行中に測り、再分割の起動条件を定義する

- 依存: W4（オーケストレーターがタスクを追加・削除・依存変更できるようにする）
- Issue: 未起票（着手時に起票する）
- 現状: 分解はワークフロー生成時に1回だけ行われる。W4が**分け直す道具**を用意するが、
  **誰が何を見て分けると判断するのか**が定義されていない
- やること
  - 実行中のタスクの規模（変更ファイル数・差分行数・往復回数）を観測値として持つ
  - **再分割を起動する条件を定義する。** 定義した条件に当たったとき、オーケストレーターへ
    「このタスクは分けたほうがよい」と提示する（自動で分けるかは提示のうえで判断させる）
- 根拠となった実測
  - **同じ「1タスク」の実体が大きく違う。** 着地時の規模は W2（PR #573）が22ファイル・
    +729/-33、W7（PR #574）が9ファイル・+584/-13。W3は1巡で完了した一方、W1とW9は
    それぞれ4巡かかった。W2は実質、停滞検知の純粋関数・View表示・設定追加の3つを含んでいる
  - **往復回数が粒度の指標になる。** 4巡かかった2件（W1・W9）はいずれも、
    指摘への対応が新しい指摘を生む形だった
- 影響の見込み: runner の観測値・W4の制御ツール・ワークフローViewのタスク表示

## H5 オーケストレーター自身の生存確認と引き継ぎ

- 依存: W10（中断からの自動再開）・W12（runをまたぐ統括）
- Issue: 未起票（着手時に起票する）
- 現状: オーケストレーターは単一障害点かつ直列化点である。**止まると全体が止まり、
  止まったこと自体を検知する仕組みが無い**
- やること
  - タスク側からオーケストレーターの生存を確認できる経路を置く
  - オーケストレーターが失われたときに、**走っているタスクを回収して引き継ぐ**手順を定義する
  - 未コミットの作業を捨てない。再開時は**作業ツリーの実測から始める**
- 根拠となった実測
  - **委譲先が完了記録を残さず消えた（2026-08-23、2件同時）。** プロセスの入れ替わりに
    巻き込まれ、W2とW7の実装セッションが停止した。**作業は未コミットで両worktreeに
    残っており**、`git status` を見るまで存在が分からない。「報告が無い」を「作業が無い」と
    読むと全部捨てる
  - **オーケストレーター自身も見失われかけた。** 同じ入れ替わりでセッション名が変わり、
    全体オーケストレーターが担当セッションを一時特定できなくなった。身元確認の往復1回で
    復帰したが、**生存確認の仕組みは無かった**
  - **無応答と正常な待ちが画面上で同じ。** 過去にはCI待ちで無報告停止した例もある。
    どちらも「動いていない」としか見えない
- 影響の見込み: runnerRestore・runStore・orchestratorSession・ワークフローViewの状態表示
- **W2との関係**: W2（ループ・停滞の検知）は、W11が実装したCI待ちの状態を知っている必要がある。
  知らないとCI待ちを停滞と誤判定して止める。**この依存はW1〜W12の割当表に書かれていない**

## H6 runをまたいで教訓を蓄積する

- 依存: W12（runをまたぐ統括）
- Issue: 未起票（着手時に起票する）
- 現状: runが終わると、そのrunで分かったことは失われる。**同じワークフローを2回目に流しても、
  1回目に踏んだ穴を踏み直す**
- やること
  - runの中で観測した失敗（無効なテスト・外れた事前宣言・迂回された既存ガード）を、
    **次のrunが読める形で残す**
  - 残す先を1か所に決める。runごとの記録が散らばると、次の担当が読む場所が無い
- 根拠となった実測
  - **人手で回したときは、これを毎回ドキュメントPRで補っていた。** 2026-08-23の1日だけで
    docs PRが6本（#565 / #567 / #568 / #570 / #572 と関連分）、うち5本は全体
    オーケストレーターが書いている。内容はすべて「セッションが終わると失われる教訓の書き戻し」
  - **書き戻しても、置き場所を間違えると残らない。** WF-A の申し送りが `.claude/handoff/` へ
    書かれ、`.gitignore` が `.claude/` をまるごと無視しているためリポジトリに入っていなかった。
    同一マシン上の別セッションからは読めるため、**書いた側が「残した」と錯覚しやすい**
- 影響の見込み: runStore・W12の統括・docs

## H7 runが生んだ残件の行き先を一元化する

- 依存: W12（runをまたぐ統括）
- Issue: 未起票（着手時に起票する）
- 現状: runが生んだ残件（追いIssue・未処理の警告・次のrunへ送るもの）の行き先が複数あり、
  **片方だけ更新されて漏れる**
- やること
  - 残件の行き先を1か所に定め、**登録と一覧への反映を同じ操作にする**
  - 一覧を更新した後に増えた残件が取り残されないよう、登録の側から一覧へ入る動線にする
- 根拠となった実測
  - **人手の運用で棚が4か所に分散し、2回漏れた。** Issue #502 はWF-Gへ送ったつもりで
    ロードマップに無く（`grep -c '502'` が0）、Issue #541 は棚を更新した後に起票されたため
    載っていなかった。**一覧を更新した後に新しく起票したものは、一覧へ戻る動線が無い**
  - **クローズコメントは棚ではない。** epic Issue のクローズコメントに残件を並べても、
    次の担当が読むのは棚のほうである
  - **機械的な検査は作れる。** `grep -n '未起票' docs/roadmap/workflow-autonomy.md` の結果に
    実際に未起票の項目だけが並ぶ、という形にすると漏れが数えられる
- 影響の見込み: runStore・W12の統括・ワークフローViewの残件表示

## 着手の順序

H1 → H2 → H3 の順に効き目が大きい。

1. **H1**（完了報告の検算）が最初。これが無い限り、他の全項目が自己申告の上に乗る
2. **H2**（実行中の交差の実測）。3回連続で外れた事前宣言に依存した設計を、実測へ置き換える
3. **H3**（応答フォーマット）。H1・H2で得た観測値を、指示の往復に載せる
4. **H4**（粒度の再判定）。W4の完了が前提
5. **H5**（生存確認と引き継ぎ）。W10・W12の完了が前提
6. **H6 / H7**（教訓と残件）。W12の完了が前提。この2つは同じ保存先を共有するため同時に行う

H1〜H3は W1〜W12 に道具が無く、独立して着手できる。
H4〜H7は道具（W4・W10・W12）の上に起動条件を載せる形になるため、**第2波・第3波の完了が前提**。

## この文書の位置づけ

本ドキュメントの全項目は、**拡張機能のワークフロー機能を実際に使って得た観測ではない**。
2026-08-21〜23に人手で同じ構造を回した実運用からの写像である。

[review-and-feature-consolidation.md](review-and-feature-consolidation.md) の方針2にあるとおり、
拡張のワークフロー機能によるドッグフーディングは全実装の完了後に別途行う。
**そこで得た観測は本ドキュメントの項目を裏づけるか、あるいは否定する**。
着手時には、その時点でドッグフーディングが済んでいるかを確かめ、済んでいれば
実測を優先して項目を見直す。
