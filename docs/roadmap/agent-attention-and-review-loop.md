# Agent Attentionとローカルレビューの計画

## 結論

次の実装候補は`C0:Global Attention Index`と`A0:Active Local Review`である。両者に技術的な依存はない。先行対象は、利用頻度、見逃しによる作業停止の影響、実装規模を基準に選ぶ。

`A1`は`A0`の実利用で必要性が確認できた時だけ扱う。`G:Completion Evidence`は、検証結果の来歴を保存する基盤ができるまで扱わない。

|依存|機能|目的|今回の状態|
|---|---|---|---|
|独立|C0:Global Attention Index|人の入力が必要な既存項目を一箇所で見つける|実装済み・ローカル検証済み|
|独立|A0:Active Local Review|保存済み差分の指摘を、指定した実行中セッションへ送る|実装済み・ローカル検証済み|
|A0の後|A1:レビューライフサイクル|下書き・送信・失敗などを追跡する|利用結果を受けて判断|
|Gの前|検証結果の来歴|完了判断に使えるコマンド実行結果を記録する|基盤候補|
|検証結果の来歴の後|G:Completion Evidence|完了・未確認・失敗の根拠を表示する|基盤完成後に判断|

本書は2026-09-15時点の計画と実装判断を記録する。受入条件はC0をIssue#1236、A0をIssue#1234で管理する。型検査、lint、テストは実施済みである。PR#1237のCI結果はPR上で確認する。

## 現状から確認できること

会話には`idle`、`running`、`approvalPending`があり、承認待ちは実行中より優先して表示される。[src/view/sessionActivity.ts](../../src/view/sessionActivity.ts)

ワークフローのタスクには`waitingApproval`と`waitingReply`があり、人の承認や返信を待つ状態を実行状態から区別している。[src/orchestrator/runState.ts](../../src/orchestrator/runState.ts)

会話用のSession Kanbanとワークフロー用のKanbanは既にある。全セッションの状態を再分類して並べる「Global Control Center」は重複する。現在のDiff表示は会話画面から開けるが、行コメントをエージェントへ返す共通の文脈や配送契約はない。[src/view/chatView.ts](../../src/view/chatView.ts)

## C0:Global Attention Index

### 目的と境界

承認待ちや明示的な返信待ちが複数の既存画面に分かれると、利用者は画面を巡回しなければならない。C0は、要入力の項目だけを集約し、元の画面へ移動する入口を提供する。

C0は既存状態の読取り専用の横断投影である。状態、優先度、既読、解決、表示順を自分で保持せず、元の状態を変更しない。表示に必要な発生源の識別子、表示文字列、遷移先だけを一時的に持つ。別のKanbanや作業場所にはしない。

### 範囲

- 会話セッションの`approvalPending`を表示する。
- ワークフロータスクの明示的な`waitingApproval`を表示する。
- `waitingReply`は、人への返信待ちと確定できる場合だけ表示する。
- 各項目に発生源、短い理由、対象名、既存画面へ戻る操作を表示する。
- 項目ごとの承認、返信、再試行、停止、マージは既存UIで行う。

### 表示規則

- 会話は`session.activity === approvalPending`だけを対象にする。
- ワークフローは`task.state === waitingApproval`だけを対象にする。`waitingReply`は人への返信待ちと確定できた時だけ追加する。
- 二つの発生源が同じ依頼を表すと確定できる識別子がなければ、推測して統合しない。発生源ごとに表示する。
- 同じ依頼に見える項目が二つ並ぶことは許容する。誤った統合を避けるためであり、後から推測に基づく重複排除は追加しない。
- 表示順は発生源種別と安定した識別子による決定的な順序にする。既存状態に発生時刻が無いため、初期版は時刻順にしない。新しい優先度は作らない。
- 項目を開く直前に元の状態を再確認する。解消済みなら操作せず、次の描画で除去する。

### 導線

- 拡張機能の既存サイドバーに、折りたたみ可能な「要対応」一覧を常設する。件数がある時だけバッジで知らせる。
- 項目を選ぶと、対象の会話またはワークフローの既存UIを開く。承認や返信は遷移先で行う。
- コマンドパレットを入口にしない。キーボードショートカットは、利用実態が確認できるまで追加しない。

### 範囲外

- Session KanbanやWorkflow Kanbanの置き換え。
- `running`、`idle`、完了済み、端末実行中、サブエージェント実行中の集約。
- `blocked`を「人の入力が必要」と推測して表示すること。
- 既読、却下、スヌーズ、独自の永続状態。
- 外部PR/MRレビューコメントの集約。未解決状態を正確に取得・追跡する基盤がまだない。

### 完了条件

1. 対象状態だけが一覧に出る。
2. 表示理由は元の状態を言い換えるだけで、新しい状態や優先度を作らない。
3. 項目を開くと対象の会話またはワークフローの既存UIへ移動できる。
4. 元の状態が解消されると、操作時は実行せず、次の描画で項目を除去する。
5. 会話とワークフローの少なくとも二つの既存画面にある要対応項目を、画面巡回なしで発見できる。
6. 単一の既存画面だけを使う利用者に、C0を経由する操作を要求しない。

### Issueで確定すること

- 会話とワークフローを同じ更新周期で読むか、各Viewの更新通知を購読するか。
- `waitingReply`の人への返信待ちを確実に識別できるか。識別不能なら初期版から除外する。
- 各発生源から既存UIを開く安定した識別子と深いリンクをどこに置くか。

## A0:Active Local Review

### 目的

差分を読んだ利用者が、現在作業中のエージェントへ具体的な修正依頼を返す経路がない。A0は、保存済みの変更箇所と十分な文脈を1つの通常メッセージとして指定セッションへ送る。

### 最小契約

- コメント対象は、拡張機能が開いたDiff editorの変更後側だけにする。ベース側、削除済み行、通常エディタは対象外にする。
- 対象は保存済みの`file:`文書だけにする。未保存、Untitled、dirty bufferは送らない。
- Diffを開く時点で`provider`、`sessionId`、`worktreeKey`、リポジトリ識別子を含む`ReviewContext`を渡す。開いているファイル名から送り先を推測しない。
- 指摘はUI上の範囲に加え、worktree、リポジトリ相対パス、内容ハッシュ、選択箇所、周辺文脈を保持する。
- 送信直前に内容と周辺文脈が完全一致することを検査する。1件でも古ければ全件を送らず、行番号のずれを推測して再配置しない。
- 指定セッションが同じprovider、同じsessionId、同じworktreeで生存し、送信可能な状態であることを確認する。別セッションへの振替、再開、別worktreeへの配送はしない。
- `A0 Foundation`として、送り先検証、provider非依存の送信契約、成功・失敗・取消・利用不能の結果をA0の範囲に含める。コメントUIからprovider固有の送信処理を直接呼ばない。

### 導線

- 会話下の三点リーダに「この会話の変更をレビュー」を置く。これは現在の会話に結び付いた変更一覧またはDiffを開く入口である。
- Diffの変更後側でコメントを作り、コメントスレッドまたはDiffの操作から「エージェントへ送る」を選ぶ。
- 送信は、対象Diffと送り先会話が明示できる時だけ有効にする。会話下の三点リーダから、対象が曖昧なまま直接送信しない。
- コマンドパレットを入口にしない。

### 送信内容と安全境界

- 送信先は既存セッションのproviderだけに限り、そのproviderの通常送信経路とWorkspace Trustを迂回しない。
- 対象は現在のworkspace内で、Diffを開いた会話と同じ正規化済み作業ディレクトリに属するファイルだけにする。worktree境界を曖昧にする候補は送信しない。
- 送信前に、依頼文、引用範囲、追加する周辺文脈を利用者が確認できる。確認画面に表示する内容と、実際に送信するpayloadを一致させる。
- 検査、確認、実送信の間に対象が変われば送信を拒否する。送信時に最新内容へ読み替えず、確認済みでない内容を送らない。
- `.gitignore`の扱い、秘密情報の自動検出、providerごとのデータ保持方針をA0が新たに推測・保証することはしない。既存providerの安全境界を越えない。

### 範囲外

- ベース側へのコメント。
- 古いコメントの自動復旧、曖昧な再配置、スナップショットへの降格。
- 完了済みセッションの再開、候補探索、自動振替。
- コメントの解決状態、永続保存、履歴一覧。
- 複数provider共通の長期キュー。

### 完了条件

1. 拡張機能から開いた保存済みDiffの変更後側でだけ指摘を作れる。
2. コメント作成後に、選択範囲または保持した周辺文脈のバイト列が変われば送信しない。
3. 利用者が指定した実行中セッション以外には送られない。
4. 送信前に利用者が確認した対象ファイル、範囲、引用箇所、周辺文脈、依頼文だけを送る。
5. セッション終了、provider切断、worktree不一致、ファイル変更、周辺文脈変更、送信失敗を区別して表示し、現在のDiffを見直すか指摘を破棄するかを選べる。
6. 送信に失敗しても、別セッションへの送信や自動再開は起こらない。
7. 選択外の変更、rename、HEAD変更、同内容でrevisionだけが変わる場合の扱いは、実装IssueのSpecで固定する。

### Issueで確定すること

- Diffを開く全経路に`ReviewContext`を渡せるか。
- VS Code Comments APIのスレッド情報と、送信用DTOをどこで分離するか。
- providerごとの送信可能状態を共通契約でどう表すか。

## 後続候補

### A1:レビューのライフサイクル

A0の実利用で必要になった場合だけ、下書き、送信済み、古い、失敗、再試行、解決状態を永続化する。送信契約そのものはA0に含める。C0へ送るのは、利用者の入力が必要な失敗だけとし、通常の下書きや送信済みを通知一覧へ流さない。

### 検証結果の来歴とG:Completion Evidence

完了画面に根拠を表示するには、検証コマンドの結果をタスクと改訂に結び付ける必要がある。少なくともリポジトリ識別子、worktree識別子、HEAD、dirty-state識別子、コマンド、cwd、exit code、開始・終了時刻、実行者、取得方法を構造化して保存する。HEADだけを「検証したソース」と見なさず、同じHEADでもdirty-stateが異なれば別の検証対象として扱う。

この基盤なしにGを作ると、「未確認」が多いだけの表示になり、完了の信頼性を上げられない。証拠は拡張機能が直接観測したもの、agentが報告したもの、外部から取り込んだものを区別する。既存のタスク出力、端末出力、PR/MRコメントは、検証済みの完了根拠としては扱わない。

### Cross Provider Takeover

ClaudeとCodexの間で実行の所有者を移す機能は保留する。会話要約を渡して新しい会話を始めるだけでは、既存のTeam、Advisor、Second Opinion、handoffと重なる。本当に引き継ぐには、元セッションの扱い、承認・質問の移管、タスク割当、worktree、責任表示を一貫して定義する必要がある。

### 常駐Runtime

CLIプロセスだけを拡張機能の外へ残しても、拡張機能再読込後に会話プロトコルへ再接続できない。実現するなら、プロセス、stdin/stdout、JSON-RPC状態、承認、送信キューを持つプロトコル所有者を外部化する必要がある。小さな機能追加としては扱わない。

## Issue化の順序

1. `C0`と`A0`を別々のIssueにする。先行順は、利用頻度、見逃しによる作業停止、実装規模で決める。
2. `C0`のIssueでは、状態の取得元、深いリンク、重複、表示順、消滅競合をSpecで固定する。
3. `A0`のIssueでは、`ReviewContext`、内容一致検査、送信可能状態表、送信内容確認、配送失敗時の表示をSpecで固定する。
4. `A0`の実利用が永続的な下書き・履歴・再試行・解決状態を必要とした場合だけ`A1`を設計する。
5. `G`は検証結果の来歴と証拠の信頼区分を保存できることを確認してから別Issueに分ける。

各Issueでは既存のViewや状態遷移を再利用し、状態の二重管理を作らない。実装時の自動テスト、型検査、lintは、そのIssueで求める検証として別途決める。

実利用の評価では、C0は表示件数、遷移成功・失敗、古い項目、重複を、A0は作成件数、送信成功、古さによる拒否、セッション利用不能、送信失敗を確認する。製品テレメトリーの追加を、この計画だけで決定するものではない。

## 独立レビューで確定した判断

別のGPT会話で本書全文を独立にレビューし、次を計画へ反映した。

- C0を読取り専用の横断投影として明文化し、独自の状態・優先度・解決管理を持たせない。
- C0とA0は技術的に独立とし、先行順を固定しない。
- provider非依存の最小配送契約をA0へ含め、A1から分離する。
- A0の送信内容確認、workspace/worktree境界、失敗理由と手動復旧を明文化する。
- Gの前提にdirty-stateと証拠の信頼区分を加える。
- 改訂版の再確認ではP0なしと判定され、検査・確認・送信の競合、意図的な重複表示、dirty-stateの同一性を各IssueのSpecに残すことにした。

## 議論で退けた案

|案|退けた理由|再検討の条件|
|---|---|---|
|Global Control Center|既存の二つのKanbanと機能が重なる|一覧を要対応だけに限定できる|
|Completion Evidenceを先行|検証結果の構造化された来歴がない|来歴の保存基盤ができる|
|Cross Provider Takeoverを先行|所有権と待機状態を正しく移せない|移管契約をSpecで定義できる|
|プロセスだけを常駐化|再読込後の会話再接続を保証できない|プロトコル所有者を外部化できる|
