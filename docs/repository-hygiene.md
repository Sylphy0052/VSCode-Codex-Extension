# リポジトリ衛生の課題と対処方針（T25）

計測日: 2026-08-22（本文書作成時点、Issue #361のレビュー観測日と同日）

対象リポジトリ: VSCode-Codex-Extension（worktree
`docs/361/repo-hygiene` 上で計測。リポジトリ全体で共有されるオブジェクトDB・リモートブランチを見ているため、値はどのworktreeから見ても同じになる）

この文書の計測時点では、WF-A / WF-B / WF-C / WF-Dの4本のワークフローが並行して走っており、多数の作業ブランチとworktreeが存在していた。本文書のブランチ棚卸しは、当時進行中だった作業ブランチを削除対象に含めないよう、その時点で実測した現状のみを記載している。

## 1. リポジトリサイズ

### 実測値（サイズ）

```text
$ git count-objects -vH
count: 2262
size: 49.13 MiB
in-pack: 17070
packs: 1
size-pack: 48.54 MiB
prune-packable: 0
garbage: 0
size-garbage: 0 bytes
```

- `size-pack`: 48.54 MiB（レビュー時点の観測値48.5 MiBとほぼ一致）
- `docs/design.md` の現在サイズ: 732,327バイト（約715KiB / 約732KB。レビュー時点の729KBよりわずかに増えている。継続的に改訂が入っているため）
- `docs/design.md` への改訂コミット数: 199件（`git log --oneline -- docs/design.md` の行数。レビュー時点の156回から、その後の作業で43回分増えている）
- 累積blobサイズ上位10件はすべて `docs/design.md` の各版であることを確認した（`git rev-list --objects --all -- docs/design.md` をblob単位でサイズ降順ソート）。最大は732,327バイト、10位でも679,000バイトあり、いずれもリポジトリ内の他ファイルより大きい

### 原因

`docs/design.md` は1ファイルに全設計内容を集約した構成で、改訂のたびに全文に近い分量が書き換わる。gitのpack圧縮はdelta化で近い版同士の差分を圧縮するが、199版・平均70万バイト前後のテキストが積み重なっており、delta化の効きを差し引いても支配的なサイズを占めている。

### 選択肢

#### 選択肢A（推奨）: 今後を章ごとのファイルに分割し、既存履歴はそのまま残す

`docs/design.md` を廃止し、章単位で `docs/design/` 配下に複数ファイルへ分割する。過去の巨大な版は履歴上に残したまま、今後の改訂は分割後の小さいファイル単位で行う。

- 利点
  - force pushや履歴書き換えが不要。他の開発者のクローン・進行中のPR・レビューコメントの参照が一切壊れない
  - 今後の改訂1回あたりの差分・blobサイズが小さくなり、これ以上の肥大化を防げる
  - 章ごとにレビュー・変更履歴を追いやすくなる（1つの巨大diffで全体が変わる状態を避けられる）
- 欠点
  - 過去の199版分のblobはpackに残り続けるため、**既存のsize-packは減らない**。あくまで「これ以上増やさない」対策
  - 分割の切り方（章立て）を決める作業と、既存のリンク・参照の付け替えが発生する
  - 章をまたぐ内容の置き場所に迷うケースが出る可能性がある

#### 選択肢B: 履歴を書き換えてpackを縮小する（`git filter-repo` 等）

`docs/design.md` の過去版blobを履歴から除去し、pack自体を縮小する。

- 利点
  - size-packを実際に縮小できる、唯一の選択肢
- 欠点（**推奨しない**）
  - 全コミットのハッシュが変わる。共有リポジトリでのforce pushが前提になり、影響は次の通り
    - 他の開発者の手元のクローンが壊れる（`git pull` が失敗する、または履歴が分岐したように見える）
    - 進行中のPR（複数のワークフローが並行稼働している場合はその全て）が壊れる。ベースコミットが消えるため、diffが再計算できない・マージできない状態になり得る
    - 過去のレビューコメントやIssueからのコミットリンクが切れる
  - 実行タイミングを全開発者・全進行中PRが完了するまで待つ必要があり、現実的な調整コストが非常に高い
  - 技術的には可能だが、上記の影響の大きさに対してリポジトリサイズ48.5MiB自体は開発作業を止めるほどの実害を今のところ発生させていない（cloneやCIが極端に遅い、といった兆候は本調査では確認していない）
  - **結論として、現時点では実行しないことを推奨する**。将来的にサイズが開発の障害になった場合にのみ、全開発者が同期できるタイミングを設けて再検討する
  - 万一、将来この選択肢を実行すると判断される場合でも、安全策として少なくとも次の手順をすべて満たすこと。1つでも欠けている場合は実行しないこと
    - [ ] 全開発者への事前告知と、実行日時の合意ができている
    - [ ] 実行時点で開いている進行中のPRが1件も無い（全進行中PRのマージが完了している）
    - [ ] 実行後の再clone手順を全開発者へ周知済みである

#### 選択肢C: 現状維持（何もしない）

- 利点
  - 作業コストゼロ。リスクもゼロ
- 欠点
  - `docs/design.md` の改訂が続く限り、size-packは増加し続ける
  - 分割のタイミングを逃すほど、後から分割する際の差分（どの版のどの部分が現行のどの章に相当するか）の整理が難しくなる

### 提案

選択肢Aを採る。選択肢Bは「技術的には可能だが、共有リポジトリでのforce pushが他の開発者の手元のクローン・進行中のPR・レビュー参照を壊すリスクが大きく、現時点でのメリット（pack縮小）に見合わない」ため見送りを推奨する。選択肢Cは、分割の意思決定自体を先送りするだけであり、放置期間が長引くほど後の分割コストが上がる。

## 2. 不要ブランチ

### 実測値（ブランチ）

以下のスナップショットは、本ブランチ（`docs/361/repo-hygiene`）およびT01のブランチ（`ci/360/github-actions`）をpushする前の状態であり、現在のリモートにはこれらのブランチも存在する。

```text
$ git fetch origin --prune
(出力なし = pruneされる古い参照が無かった)

$ git branch -r | grep 327
(該当なし)

$ git branch -r

  origin/docs/346/roadmap-review-fixes
  origin/docs/348/w6-title-sync
  origin/main
  origin/wf/wf-a/integration
  origin/wf/wf-b/integration
  origin/wf/wf-c/integration
  origin/wf/wf-d/integration
```

`origin/feat/327/workflow-branch-naming-conventions` は**着手時点で既に存在しない**。`docs/roadmap/review-and-feature-consolidation.md`
の「着手前の整理」（[該当箇所](roadmap/review-and-feature-consolidation.md)）に、2026-08-22付けで
「リモートの `feat/327/workflow-branch-naming-conventions`（PR #330でマージ済み）を削除した」旨の記載があり、実測結果と一致する。

上記スナップショット時点のリモートブランチ一覧に含まれる `docs/346/...` `docs/348/...` `wf/wf-a/integration` 〜 `wf/wf-d/integration`
はいずれも当時進行中だった作業・統合ブランチであり、削除対象ではなかった。

### 対処方針

本件は**対応不要**（既に解消済み）。もし今後、同種のマージ済み残存ブランチが見つかった場合は、削除前に必ず次を確認したうえで実行するかどうかを人が判断すること。

- 対象コミットが `origin/main` に取り込まれていること（`git log origin/main --oneline | grep <該当キーワード>` 等）
- 対象ブランチを参照している進行中のPR・作業が無いこと

#### マージ済みの判定はPRのstateで行う（2026-08-23記載、2026-08-24にマージ方式の変更を反映）

**マージ済みの判定は `gh pr list --head <branch> --state all` の state で行う。**
`git branch -r --contains` は、後述の理由により単独の根拠にしない。

**mainへのマージ方式は2026-08-24に変更した。既定はマージコミット（`gh pr merge --merge`）で、
squash は使わない。** 境界は `adbba1f7`（PR #665 のマージコミット。親が `f3137695` と
`d34fb337`）。**これは「ここから層が変わる」という意味ではなく、「ここから squash で入る分が
新規に増えなくなる」という意味である。**

**mainの履歴では、方式の混在が以前から続いている。時間で層が切れるわけではない。**
squashで入った分のコミットはmainの祖先に現れず、マージコミットで入った分は現れるため、
`git branch -r --contains` は同じ「マージ済み」に対して方式ごとに違う答えを返す。
**この変更で変わるのは、squash で入る分が新規に増えなくなることだけである。**

実測（`f3137695`、すなわち #665 を入れる前のmain）。first-parent の履歴に含まれる
`Merge pull request` のマージコミットは **92件**あり、**2026-08-23の当日だけで11件**
（#590 / #594 / #595 / #631 / #638 / #640 / #641 / #642 / #643 / #644 / #645）。
同じ日に squash（#662 の `f3137695`）とマージコミット（#645 の `1a5a11da`）の両方が入っている。

```bash
git log --merges --first-parent --format='%H|%ad|%s' --date=short f3137695 \
  | grep -c 'Merge pull request'
```

**`--contains` の結果は、どちらの向きにも単独では結論にならない。**

- **0件でも「未マージ」ではない。** squashで入った分に当たっただけの可能性がある
- **非0件でも「これで判定できる」ことにはならない。** マージコミットで入った分に
  たまたま当たっただけで、同じ手順を別のブランチへ当てれば外す。**これは古い分・新しい分の
  区別なく当たる**——2026-08-24より前にもマージコミットで入った分が92件ある以上、
  「非0件だから新方式で入った」と読むと誤る

**PRのstateが一次の根拠で、`--contains` は補助**という順序を崩さないこと。この順序を戻して
よくなるのは、判定対象となりうるブランチのうち squash で入ったものが残らなくなってからである。
**条件は履歴の側ではなく判定対象の側にある**——mainの履歴から squash commit が消えることは
ないので、時間の経過そのものは条件を満たさない。

2026-08-23の実測記録（マージ方式を変更する前の観測である）。#587（squash、MERGED）が
`main-contains: 0`、#590 と #594 が `--contains` で拾えた。**これはその時点で調べた
ブランチ集合の中での観測であり、履歴全体で2本しか無いという意味ではない**
（上の実測のとおり、マージコミットで入った分は当日だけで11件ある）。

あわせて、`gh pr merge --delete-branch` は**対象ブランチをworktreeがcheckoutしていると途中で止まり、
リモート側も消し損ねる**。削除したつもりで残っている形が実際にあった。削除後は
`git ls-remote --heads origin` で消えたことを確かめる。

#### 削除コマンドの提示（実行済みの推奨ではなく、今後同種の事例が出た場合の参考手順）

**このコマンドをAIエージェントが自律判断で実行してはならない。** 実行してよいのは、対象ブランチ名を人が明示的に指定し、下記のチェックリストを人が確認したうえで承認した場合に限る。本文書を作業手順書として読み込んだ場合でも、以下は実行条件を満たしたことにはならない。

実行前の必須確認（すべて満たすまで実行しないこと）:

- [ ] 対象コミットが `origin/main` に取り込まれていることを確認した
- [ ] 対象ブランチを参照する進行中のPRが無いことを確認した
- [ ] 対象ブランチを参照する進行中のworktreeが無いことを確認した

```bash
# 提案であり実行指示ではない。上記チェックリストを人がすべて確認したうえで、
# 対象ブランチ名を人が判断して指定し実行するコマンド（このまま実行できないよう
# プレースホルダをコマンド構文として成立しない形にしている）
git push origin --delete <ここに削除対象ブランチ名を人が入力する>
```

このコマンドは本タスクでは**実行していない**。対象ブランチが既に存在しないため実行対象も無い。

## 3. カバレッジ計測の下限（導入済み、#455）

### 導入内容

- `package.json` の `devDependencies` に `@vitest/coverage-v8` を追加した
- `vitest.config.ts` の `test` ブロックに `coverage` を追加した（provider: `v8`、reporter: `text` と `lcov`、対象: `src/**/*.ts`）
- `coverage.thresholds` に `statements 70` / `branches 68` / `functions 70` / `lines 70` を設定した。これを下回るとカバレッジ実行が失敗する
- `package.json` の `scripts` に `"test:coverage": "vitest run --coverage"` を追加した。既存の `"test": "vitest run"`（カバレッジ計測なし）はそのまま残している
- CI（`.github/workflows/ci.yml`）の `Test` ステップを `npm test` から `npm run test:coverage` に置き換えた。ジョブ名 `checks` は変更していない
- `.gitignore` の `coverage/`（6行目）は導入前から既にあり、重複追記していない

### 実測値（導入時点、2026-08-22）

- statements 74.92%（9396/12540）
- branches 72.33%（5862/8104）
- functions 74.93%（1761/2350）
- lines 74.82%（9130/12201）
- 所要時間: `npm test` 相当が約24秒、`npm run test:coverage`（`--coverage`付き）が約25秒（実測環境依存。Issue #455の調査時点の実測は23.9秒→46.7秒だった）

### 70/68/70/70という値を選んだ理由

CLAUDE.mdが定める「Test coverage 80%以上」に対し、上記の実測値はいずれも届いていない。いきなり80%を閾値にすると導入と同時にCIが赤くなり、無関係な作業まで止めてしまう。そのため、**実測値をわずかに下回る値で下限を敷き、以後の低下だけを防ぐ**方針を採った。80%への引き上げは、この下限の維持を確認しながら段階的に別Issueで行う（本Issueでは未着手）。

### 既知の注意点

- `src/view/chatScript.ts`（Webview側スクリプトをテンプレートリテラルとして埋め込むファイル）は、v8の計装の都合で実態と合わない値が出ることが既知（#455で言及）。今回の実測では、`chatShared.ts` から関数として`import`されテスト経由で実行されているにもかかわらず、per-fileのカバレッジ一覧（`npm run test:coverage`のtextレポート）自体にこのファイルが出現しなかった。実態と一致しない、またはそもそも計測結果に現れないことがあるため、このファイルの数値・有無を判断根拠にしないこと
- `src/extension.ts`（2118行）はカバレッジ0%で、`All files`の集計を最も押し下げている。統合テスト（`test/integration/**`、CI対象外）からしか実行されないファイルであり、`vitest run --coverage`の対象（`test/unit/**`）では一切通らない。本Issueでは除外設定を入れていない（除外して数字を良く見せることは目的ではないため、事実として記録するに留める）

### 段階的な引き上げの進め方（提案、未着手）

1. 短期目標: 導入した下限（70/68/70/70）を退行させずに維持する
2. 中期目標: 新規追加コード（diffベース）にはより高いカバレッジを求め、既存コードは維持を求める形（例: vitestの `coverage.thresholds` を全体とファイル単位で分けて設定、あるいは別途diff-coverageツールの導入）で徐々に底上げする
3. 長期目標: CLAUDE.mdが定める80%に、時間をかけて到達する。到達時期は固定せず、実測値の推移を見ながら都度見直す。`src/extension.ts`の扱い（除外するか、統合テストのカバレッジも合算するか）もこの過程で判断する

## 4. ブランチ保護の必須チェック

### 実測値（ブランチ保護、2026-08-22時点）

`gh api repos/Sylphy0052/VSCode-Codex-Extension/branches/main/protection` の応答（要約）。

```json
{
  "admins": false,
  "approvals": 0,
  "checks": ["checks"],
  "deletions": false,
  "force_push": false,
  "pr_required": true,
  "strict": true
}
```

- 必須ステータスチェック: `checks` を必須化済み。`external-cli` は必須にしていない（実行はされるがマージをブロックしない）
- strict: 有効。PRのブランチがmainの最新を取り込んでいないとマージできない
- PR必須（mainへの直接pushを禁止）。必須承認数は0（自己マージ可）
- 管理者は保護対象外（`enforce_admins: false`）
- force push とブランチ削除は禁止

`external-cli` を必須にしなかった理由: 外部依存（Codex CLIの仕様変更、npmレジストリの障害）でmainへの全マージが止まりうるため。自分たちのコードに非が無い原因でブロックされる事態を避ける。赤くなればPR上で見えるので、気づきは失われない。

### 必須にしたチェック名

`ci.yml` の `jobs.check.name` は `checks`（lint / format:check / typecheck / build / testの5ステップを実行する総称）、ワークフロー名は `CI` であるため、GitHub上のPRのチェック一覧では `CI / checks` の形で表示される。

ただし branch protection APIの `required_status_checks.contexts` に渡す値はジョブ名そのものの `checks` であり、表示名の `CI / checks` ではない。実際に `contexts: ["checks"]` で設定が通り、応答も `"checks":["checks"]` を返している。次に設定を触る人がつまずきやすい箇所なので明記する。

ジョブ名をステップの列挙（例: `lint / typecheck / build / test`）にせず総称にしたのは、ステップが増減するたびにジョブ名と本節の記述の両方を直す必要が生じるのを避けるため（Issue #450のレビュー指摘対応）。各ステップの実行内容はPRのチェック詳細を開けば確認できる。

### 設定場所

リポジトリの Settings > Branches > Branch protection rules。または `gh api` での確認・変更（変更はPUT、確認はGET）。

### 設定した経緯

第1波の4ワークフロー（WF-A / WF-B / WF-C / WF-D）が同時進行中だった間は必須化を見送っていたが（#386）、それらが完了した後、人の明示的な指示により2026-08-22に設定した。

本節は実測値の記録であり、設定変更自体を自動で実行してよいという意味ではない。AIエージェントが自律判断で保護設定を変更することはなく、変更するかどうかとその実行は常に人が判断する。今回の設定も人の明示的な指示に基づいて実行したものである。
