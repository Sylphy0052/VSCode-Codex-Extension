実VSCodeでしか確認できない範囲のチェックリスト。ロジック層はユニットテスト（`npm test`）が担うため、ここでは**実際のCLIプロセス・Webview・タブ復元**が絡む挙動だけを対象にする。

対象CLI: Codex CLI 0.147.0 / Claude Code 2.1.227（確認時の版を各回の記録に残す）。`codex --version` / `claude --version` で確かめる。

履歴一覧は当初、実CLIを呼ばせないために`executablePath`を存在しないパスへ固定する制約と
`ProviderRegistry.available()`の仕様（実行ファイルを解決できないプロバイダを一覧からまるごと
除外する）が噛み合わず、5件とも「一覧が空」で失敗していた（issue #164）。一覧の構築は
ファイル読みだけで完結しCLIプロセスを要さないため、実行ファイルの解決可否で一覧を絞るのを
やめる形で実装側を直した。CLIをPATHから外しただけで過去の履歴が消えなくなったことは
H-09の狙いそのものでもある。

画面上の見え方（アイコンの図柄・並びの見た目・右クリックメニューの実際の表示）は
TreeItemの値までしか確かめられないため、各ケースの手順は手動の確認としても残す。

`npm run check`（commit前チェック）には含めていない。実VSCodeのダウンロードと起動が
毎回走るため手元・CIとも重く、既定の高速フィードバックループを崩すと判断したため。
必要なときに明示的に呼ぶ運用とする。

## C群・L群の仕分け（Issue #186）

チャット画面についても、W群と同じ「**CLIとの境界だけをフェイクへ差し替え、それ以外は実物を
通す**」方式が取れることを確かめた（`chatHarness.test.ts`）。境界はCodexが `app-server` との
接続（`AppServerConnectionPort`）、Claude Codeがプロセスの起動（`ClaudeSpawnPort`）にある。

そのうえで、C群44件・L群40件を次の3つに仕分けた。移送は #187（Codex）/ #188（Claude Code）で
進め、済んだケースはこの文書から落とす。

| 分類         | 意味                                                                                   |
| ------------ | -------------------------------------------------------------------------------------- |
| **機械**     | プロトコル上のやり取り・状態遷移・配線だけで主張が閉じる。そのまま統合テストへ落とせる |
| **一部機械** | 送受信するデータは機械で確かめられるが、見え方（色・折りたたみの操作感）は実機に残る   |
| **実機**     | 画面の操作感・モデルの出力・外部認証など、機械では確かめようがない                     |

## 準備

```bash
npm run check     # 全緑であること
npm run build     # dist/extension.js を更新
```

- VSCodeで `F5`（Run Extension）。拡張機能ホストの新しいウィンドウが開く
- 開発ホスト側で確認用の作業フォルダを1つ開く。**ファイルを壊してよい捨てフォルダ**にする（承認の確認でコマンドを実際に実行させるため）
- コマンドパレット → `Agent: ログを表示`（`codex.showLog`）でOutputChannelを常時開いておく。以下「ログ」と書いたらこれを指す
- WSL Remoteの場合、拡張機能は `extensionKind: ["workspace"]` でリモート側に載る。CLIがリモート側のPATHにあることを `which codex` `which claude` で確認する

### 設定

承認カードを確実に出すため、確認中は次にする（`settings.json` またはサイドバーの設定パネル）。

| キー                        | 値                 | 理由                                 |
| --------------------------- | ------------------ | ------------------------------------ |
| `codex.sandbox`             | `read-only`        | 書き込みのたびに承認要求を発生させる |
| `codex.approvalMode`        | `on-request`       | 承認カードの経路を通す               |
| `claude.permissionMode`     | 空 または `manual` | control protocolの承認を通す         |
| `agent.activityLog.enabled` | `true`             | A群で使う                            |

`codex.approvalMode` が `never` だと承認要求そのものが発生せず、サンドボックスで弾かれた操作がそのまま失敗する。`danger-full-access` + `never` の組み合わせ、および `claude.permissionMode` の `bypassPermissions` も承認カードが出なくなるため、C群・L群の承認ケースでは使わない。`workspace-write` では作業フォルダ内の書き込みが承認なしで通るため、承認カードの確認には向かない。

**前提**: サンドボックスの実行には `bubblewrap` が要る。無いと `Codex could not find bubblewrap on PATH` が出てサンドボックス実行が失敗し、承認要求の内容が「サンドボックス無しで再試行するか」という異常系に変わる。

```bash
sudo apt install bubblewrap
```

### 準備

# .agents/workflows/sample.yaml
version: 1
name: サンプル

tasks:
  - id: T1
    prompt: docs/note.md に「T1」と書いて保存して
    done: docs/note.md に T1 と書いてある

    done: docs/note-summary.md が書けている

### W-A 通し実行と画面の見え方

準備のYAMLを1回実行し、その間に画面を見る。W-Bはこの実行の続きで行う。

- 操作: コマンドパレット `Agent: ワークフローを実行…`（`agent.workflows.run`）→ 準備のYAMLを選ぶ
- 期待: 依存グラフがT1（1段目）、T2とT3が横に並ぶ2段目、T4（3段目）の縦3段で描かれる
- 期待: ノードの色と記号が状態（`pending` 灰色枠のみ→ `running` 強調色＋アニメーション→ `done` 塗りつぶし＋チェック）に合わせて変わる。`running` のノードには送信回数（`n回目`）が添えられる
- 期待: ノードに直近の応答の1行要約が出て、内容が進むたびに書き換わる
- 操作: カラーテーマをライトとダークそれぞれに切り替える
- 期待: どちらのテーマでも、状態ごとの色（`pending` / `running` / `waitingApproval` / `done` / `failed` / `merging` / `blocked` / `skipped`）と記号の両方で状態が判別できる。色だけに頼った表示になっていない
- 操作: 実行中のタスク（例: T2）のノードを押し、開いたチャットタブを閉じる。しばらくしてから同じノードをもう一度押す
- 期待: タブを閉じても進行は止まらず、開き直すと同じセッションのタブに閉じる前までの会話が復元されている
- 操作: 実行中のタスクの行で「中断」を押す
- 期待: 現在のターンだけが止まり、次の指示（`continuePrompt`、既定は「続けてください」）が自動で送られて続く
- 操作: 実行中にウィンドウをリロードする（`Developer: Reload Window`）→ `Agent: ワークフローViewを開く` で開き直す
- 期待: 実行していたrunが一覧から選べ、進行状況が復元表示される。走行中だったタスクは中断扱い（`failed`、理由: 中断）になっている
- 操作: 中断扱いになったタスクを「再実行」する
- 期待: 新しいworktree・新しいブランチ（`wf/<runId>/<taskId>-retry<n>`）・新しいセッションが実際に作られ、最初からやり直される（`git worktree list` で確認できる）

### W-B 危険操作の承認と `allow` の常時表示

- 前提: 対象タスクのYAMLに `autoApprove: true` を足す
- 操作: そのタスクへ、安全な書き込み指示と危険と判定される操作（例:「作業ディレクトリ配下の一時ファイルを `rm -rf` で再帰的に削除して」）の両方を含む指示を出す
- 期待: 安全な操作は承認カードを出さず自動で進む。危険と判定した操作の要求だけは自動で通らず、そのタスクが `waitingApproval` になって止まる

- 期待: 実行前に「既定の危険操作チェックを解除しているタスクがあります」旨の確認ダイアログが出る。取り消すと実行されない
