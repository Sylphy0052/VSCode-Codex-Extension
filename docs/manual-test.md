# 実機確認手順

実VSCodeでしか確認できない範囲のチェックリスト。ロジック層はユニットテスト（`npm test`）が担うため、ここでは**実際のCLIプロセス・Webview・タブ復元**が絡む挙動だけを対象にする。

対象CLI: Codex CLI 0.147.0 / Claude Code 2.1.227（確認時の版を各回の記録に残す）。`codex --version` / `claude --version` で確かめる。

## 進め方

1. 下の「準備」を済ませる
2. ケースを上から順に実行する。C群（Codex画面・44件）→ L群（Claude Code画面・40件）→ P群（ループ実行・5件）→ H群（履歴・復元・10件）→ A群（作業記録・4件）→ W群（ワークフロー・21件）
3. 各ケースの結果を「記録テンプレート」に写す。落ちたものはIssue化してから次へ進む

前提が崩れるケース（C-01・L-01）が落ちた場合、その群の残りは実行しても意味がないので中断して原因を先に潰す。

## 準備

```bash
npm run check     # 全緑であること
npm run build     # dist/extension.js を更新
```

- VSCodeで `F5`（Run Extension）。拡張機能ホストの新しいウィンドウが開く
- 開発ホスト側で確認用の作業フォルダを1つ開く。**ファイルを壊してよい捨てフォルダ**にする（承認の確認でコマンドを実際に実行させるため）
- コマンドパレット → `Agent: ログを表示`（`codex.showLog`）でOutputChannelを常時開いておく。以下「ログ」と書いたらこれを指す
- WSL Remoteの場合、拡張機能は `extensionKind: ["workspace"]` でリモート側に載る。CLIがリモート側のPATHにあることを `which codex` `which claude` で確認する

### 設定

承認カードを確実に出すため、確認中は次にする（`settings.json` またはサイドバーの設定パネル）。

| キー                        | 値                 | 理由                                 |
| --------------------------- | ------------------ | ------------------------------------ |
| `codex.sandbox`             | `read-only`        | 書き込みのたびに承認要求を発生させる |
| `codex.approvalMode`        | `on-request`       | 承認カードの経路を通す               |
| `claude.permissionMode`     | 空 または `manual` | control protocolの承認を通す         |
| `agent.activityLog.enabled` | `true`             | A群で使う                            |

`codex.approvalMode` が `never` だと承認要求そのものが発生せず、サンドボックスで弾かれた操作がそのまま失敗する。`danger-full-access` + `never` の組み合わせ、および `claude.permissionMode` の `bypassPermissions` も承認カードが出なくなるため、C群・L群の承認ケースでは使わない。`workspace-write` では作業フォルダ内の書き込みが承認なしで通るため、承認カードの確認には向かない。

**前提**: サンドボックスの実行には `bubblewrap` が要る。無いと `Codex could not find bubblewrap on PATH` が出てサンドボックス実行が失敗し、承認要求の内容が「サンドボックス無しで再試行するか」という異常系に変わる。

```bash
sudo apt install bubblewrap
```

- 操作: C-01の続き
- 期待:

### C-03 承認カード（許可）

- 操作: 「`test.txt` というファイルを作って」と指示する

### C-05 承認カード（このセッションでは許可）

- 操作: 「この会話では常に許可」（`acceptForSession`）を選び、続けて**まったく同じコマンド**を指示する（例: どちらも `touch same.txt`）
- 期待: 2回目は承認カードが出ずに実行される
- 注意: 記憶されるのは**コマンド単位**。`touch a.txt` を許可しても `touch b.txt` では再び聞かれる（app-serverへ直接問い合わせて確認済み）。引数違いで試すと「効いていない」ように見える

### C-06 保留中の承認を残したままタブを閉じる

- 操作: 承認カードが出ている状態でCodex画面のタブを閉じる

### C-07 中断

- 操作: 長めの作業を指示し、応答中に「中断」ボタンを押す。`Esc` でも同じことができる

### C-08 タブ名の自動追従

### C-11 タブ復元

### C-13 応答中の指示は割り込んで届く

- 操作: 長めの作業を指示し、応答中にさらに2件送る
- 期待: **応答が止まらない**まま指示が届く（`turn/steer`）。送った指示が会話に現れ、Codexがそれを踏まえて続きを進める

- 確認: 割り込めなかった場合（ターンが終わる直前など）は待ち行列に残り、ターンが終わってから送られる。項目は「取り消す」で個別に消せる。「今すぐ送る」は**中断しない**
- 落ちたとき: ログに「割り込めなかったため待ち行列へ積みます」が出ていれば `expectedTurnId` の不一致。出ていなければ `turn/steer` 自体が通っていない

- 期待: 待ち行列に積まれ、ターンが終わってから順に送られる（Claude側に割り込みの手段が無いため）
- 確認: 「今すぐ送る」は**応答を中断してから**送る。Codexとの違いはここだけ

### C-14 スラッシュコマンドの候補

- 操作: 入力欄で `/` を打つ
- 期待: 候補が一覧で出る。擬似コマンド（`/compact`）が先、スキルと `~/.codex/prompts/*.md` のカスタムが続く
- 確認: CLIの組込コマンド（`/review` `/status` など）は出ない。送っても効かないため（詳しくは L-13）
- 確認: 文字を足すと絞り込まれる。`↑` `↓` で選び、`Tab` か `Enter` で入力欄に入る（送信はされない）。`Esc` で閉じる

### C-17 画像を添えて送る

貼付・ドラッグ&ドロップ・ファイル選択の3経路。Claude Code画面でも同じ操作ができるので、L-16で同じことを確認する。

- 操作: 画面のスクリーンショットを撮り、入力欄で `Ctrl+V`
- 期待: 入力欄の上にサムネイルとファイル名・大きさが出る
- 確認: テキストを貼り付けたときは今までどおり入力欄へ入る（画像のときだけ横取りする）
- 操作: 画像ファイルを画面へドラッグ&ドロップ
- 期待: 同じようにサムネイルが増える。**画面が画像ビューアに置き換わらない**
- 操作: 「画像」ボタンからファイルを選ぶ
- 期待: 同じようにサムネイルが増える。同じファイルを続けて選べる
- 操作: サムネイルの「取り消す」を押す
- 期待: そのサムネイルだけ消える
- 操作: 「この画像に何が写っているか教えて」と書いて送る
- 期待: **モデルが画像の内容を答える**。送信後サムネイルは消える
- 操作: 本文を空のまま画像だけ送る
- 期待: 送れる（本文が無くても添付があれば送信できる）
- 操作: 5MBを超える画像を貼る
- 期待: サムネイルは出ず、「1枚あたり 5.0MB までです」と理由が出る
- 操作: 対応しない形式（svgなど）を貼る
- 期待: 理由が出て添付されない
- 操作: 6枚目を貼る
- 期待: 「一度に送れるのは 5 枚までです」と出る
- 操作: 応答中に画像を貼って送る
- 期待: 待ち行列に `（画像1枚）` 付きで並び、ターンが終わってから画像ごと送られる

### C-20 ファイル変更の差分

変更したファイルのパスだけでなく、中身の差分が読めること。Claude Code画面でも同じ描画を使うので、L-17で同じことを確認する。

- 前提: 承認カードで書き込みを許可できる状態（準備の設定のまま）
- 操作: 「`sample.txt` を作って、`hello` と書いて」と指示し、承認する
- 期待: 会話の `ファイル変更` の行に折りたたみが付き、開くと `sample.txt ・ 追加` の見出しと本文が出る
- 期待: 追加行が緑、削除行が赤、`@@` の行が別の色で出る
- 操作: 続けて「`sample.txt` の `hello` を `world` に変えて」と指示し、承認する
- 期待: 新しい行に `sample.txt ・ 変更` が出て、`-hello` と `+world` が並ぶ
- 確認: 差分を持たない変更（パスだけ届くもの）では折りたたみが出ず、行が消えたりしない
- 確認: 同じターンで複数ファイルを変えると、ファイルごとに折りたたみが並ぶ

### C-21 解決済みの承認カードが残らない

- 操作: Codex画面で承認カードを出したまま、同じスレッドをターミナルのTUIで開いて承認する
- 期待: 画面の承認カードが自動で消え、会話がそのまま続く
- 確認: 消えたカードに答えようとしてボタンが残っていない（押しても何も起きない状態にならない）

`src/orchestrator/*.ts` と専用Webview（`workflowView.ts`）が対象。並列実行・worktree隔離・危険操作の検知・View表示・ゴール文からのYAML生成に加え、**成果統合まわり（統合ブランチのマージ・衝突の自動解決・PR/MR自動作成・ロードマップの2段階生成・タスク間メッセージング）は実行への配線を含めて実装済みで、ここが最大の未実施範囲**（[docs/design.md](design.md) §16.13）。**この機能に対する実機確認は一度も行われていない。** ユニットテストとプロトコル上の実測までしか済んでいないため、W-15以降で通しの手順を確認する。

### W-01 並列実行が最後まで通る

- 操作: コマンドパレット `Agent: ワークフローを実行…`（`agent.workflows.run`）→ 準備のYAMLを選ぶ
- 期待: ワークフローViewが開き、T1が終わるとT2とT3が同時に開始する。タスク一覧の経過時間・開始/終了のタイミングから、**T2とT3の実行区間が重なっている**ことを確認する
- 期待: T2とT3がどちらも `done`（統合ブランチへのマージまで完了）になってからT4が始まる。最終的に全タスクが `done` になり、全体の進捗が100%になる
- 確認: 統合ブランチ（`wf/<runId>/integration`）をcheckoutして `git log` を見ると、各タスクのマージコミット（`Merge task <taskId> (run <runId>)`）が `--no-ff` で並んでいる

### W-06 危険と判定したコマンドでタスクが止まり、Viewからの許可で再開する

### W-15 統合の衝突が自動解決され、`blocked` からの再マージができる

- 期待: 先にマージされたタスクは通常どおり `done` になる。後からマージしようとしたタスクで衝突が起きると、統合worktreeを `cwd` にした解決用セッションが自動で開く。プロンプトに衝突したファイルの一覧・突き合わせる2つのタスクの `prompt` と `done`・未解決パスの一覧が含まれていることを会話で確認する

- 確認: 解決用セッションの承認カードは、対象タスクの `allow` / `autoApprove` を指定していても常に人の承認を求める（統合worktree向けの標準承認へ委ねる設計）

- 期待: 再マージが成功し、タスクが `done` になって統合ブランチへ入る

### W-16 PR/MRの作成順序（作成がマージより先であること）

- 確認: ホスト側でPR/MRを開き、作成された時点でbaseとheadの間に差分があったこと（先にマージ済みではないこと）を確認する。統合ブランチのpush後、そのPR/MRがホスト側でマージ済みとして扱われる
- 期待: ワークフローViewの統合状況に、タスクごとのPR/MRへのリンクが表示され、クリックでブラウザが開く
- 操作: 同じ手順をGitLab用の使い捨てリポジトリでも行う
- 期待: `glab api projects/:id/merge_requests --field description=@<path>` 経由で本文が渡り、`glab mr create` 相当のMRが作られる。GitHubと同じ順序で進む

### W-17 統合ブランチからmainへの最終マージ

### W-19 gitでないフォルダで疑似worktreeが使われる

- 期待: スナップショットとの差分から変更を検知し、反映されずに警告が出る（人の編集を上書きしない）

### W-20 タスク間メッセージングの往復と `waitingReply` の解除

- 期待: どちらの経路でも待ちが解け、全タスクが `running` へ戻り、ワークフローViewの警告欄に記録される
- 操作: 設定パネルからワークフロー用MCPサーバを無効化した状態（見えるなら）でタスクを実行する
- 期待: ツールが見えない旨がワークフローViewへ警告として出るが、通信なしでワークフロー自体は最後まで走る

### W-21 ロードマップ生成 → YAML変換 → 並列実行 → マージ → 片付けの一周

- 操作: コマンドパレット `Agent: ロードマップを生成…`（`agent.workflows.roadmap`）でゴールの文を入力する（例: `ドキュメント整備を段階的に進める`）
- 期待: `agent.workflows.roadmapDir`（既定 `docs/roadmap`）へMarkdownが生成される。フェーズごとのチェックリストに、項目間の依存と（取得できれば）Issue番号が入っている
- 操作: `Agent: ゴール文からワークフローを生成…`（`agent.workflows.plan`）→「ロードマップから生成」→生成したロードマップのファイルと1つのフェーズを選ぶ
- 期待: 選んだフェーズの項目だけが `tasks` に変換され、項目の `依存` が `dependsOn` に写る。Issue番号を持つ項目には `issue` フィールドが入る。**フェーズをまたいだ部分選択はできない**（QuickPickは単一フェーズのみ選べる）
- 操作: 生成されたYAMLを軽く見直してから「実行」する
- 期待: W-01と同じ形で並列実行→マージが進み、前提（remote・CLI・認証）が揃っていればPR/MRの作成まで進む
- 操作: runが終わったあと、元のロードマップファイルを開く
- 期待: そのrunで `done` になったタスクに対応する項目にだけチェックが入り、他の文面（人が書いた部分）は変わっていない
- 操作: ワークフローViewの「統合ブランチと残ったworktreeをまとめて片付ける」を押す
- 期待: 統合worktreeと、残っているタスクのworktreeがまとめて撤去される。ブランチ自体は消えない（PR/MRから辿れる状態を保つ）
- 確認: runが `running` の間は、この片付け操作が失敗として返り、何も撤去されない
